# i18n Spec

**Status:** Implemented; v0.24.0 decisions accepted, pending implementation ([plan](../plans/components-and-sequential-bootstrap.md)) **Implementation:** `internal/i18n/` and root package **ADR:** [ADR-013](../adr/013-internationalization.md)

## Detector contract

UseI18n is a framework-owned HTTP feature under the [HTTP contract](http-features.md#locale-and-transport-features): it installs no middleware. The one detector signature is `Detect func(*Context) string`. `Locale`, `T`/`TPlural` and automatic error/bind/validation/field translation share first-use resolution and request memo state, reset on pool reuse. The default reads Accept-Language; empty/unresolvable results select the configured default. Unused or inactive i18n never invokes the detector. The first result survives later auth, rewrites and request restoration; calling `Locale` immediately after auth preserves the user language for later errors, provided no earlier read fixed it.

Recursive `Locale`/translation from `Detect` is a programming panic. A detector panic caches the default fallback and prevents any repeated detection for the request, including during error rendering; with recovery enabled the request takes the 500 path, with recovery disabled the panic propagates after cleanup. Context-based access exposes `GetUser` at the time of detection without extending principal lifetime, so detectors must handle an absent principal.

## Public API

```go
type I18nMessages map[string]string
type I18nFields map[string]string

type MessageScope uint8

const (
    MessageScopeError MessageScope = iota
    MessageScopeValidation
    MessageScopeBind
)

type MessageRef struct {
    Scope MessageScope
    Code  string
}

type MessageKeyResolver func(MessageRef) string

type I18nConfig struct {
    Dir               string
    DirFS             fs.FS
    Default           string
    Detect            func(*Context) string
    Messages          I18nMessages
    Fields            I18nFields
    ResolveMessageKey MessageKeyResolver
}

func (app *App) UseI18n(cfg ...I18nConfig) error
func (ctx *Context) Locale() string
func (ctx *Context) T(key string, data ...map[string]any) string
func (ctx *Context) TPlural(key string, count any, data ...map[string]any) string
```

`UseI18n` accepts zero or one config, is frozen-guarded and succeeds at most once: a second call panics even when the first found no conventional catalogs (configured-but-inactive), while a load/validation error leaves the registration free for repair. `Default` is `en`. `Detect` defaults to `Accept-Language` and runs lazily (see below). `Locale` returns the matched canonical locale, or empty when i18n is inactive. Missing keys pass through from `T` and `TPlural`.

## Sources and precedence

`Messages` and `Fields` are a one-language programmatic base attached to the effective `Default`. `Dir`/`DirFS` provide file-backed multi-language catalogs. The framework copies maps and compiles templates during setup.

Load order:

```text
1. Messages / Fields for Default
2. Dir or DirFS catalogs, merged by language + exact key
```

The second layer overrides collisions; keys found only in the base survive. `Messages` and `Fields` are separate catalogs. Messages contain templates; fields contain technical-path-to-display-name mappings.

| Configuration | Result |
| --- | --- |
| zero config | RawConfig, then conventional `locales/` discovery |
| `Messages` | map-only default-language bundle |
| `Messages + Fields` | map-only field-aware bundle |
| maps + explicit `Dir`/`DirFS` | maps as base, files as override |
| `Fields` without any messages | setup error |
| `Dir` and `DirFS` together | setup error |
| absent conventional `locales/` | warning, i18n inactive |
| missing/empty explicit source | setup error, even with maps |
| malformed/read-denied source | setup error; nothing published |

RawConfig `i18n.dir` is explicit. Supplying a programmatic map without an explicit file source suppresses conventional directory discovery.

## Registration and start phase

**Accepted, pending implementation (v0.24.0, W5).** When it ships, this section replaces the `UseI18n` signature and its registration sentences under Public API, the "setup error" wording of the table above, and "after `UseI18n` completes" under Plurals and lookup. The rationale is in [ADR-013](../adr/013-internationalization.md#registration-and-the-start-phase).

```go
func (app *App) UseI18n(cfg ...I18nConfig)
```

`UseI18n` returns nothing. It validates what needs no I/O and records the configuration; the start phase reads the catalogs and publishes the bundle.

| Condition | Where it fails |
| --- | --- |
| more than one config; `Dir` and `DirFS` together; a second call; a call after preparation or shutdown | panic at the call |
| invalid `Default` tag; empty programmatic key or value; programmatic template that does not compile; `Fields` with no `Messages` and no file source; `i18n` RawConfig section that does not decode | panic at the call |
| absent conventional `locales/` | Warn from the start phase; i18n inactive; no failure |
| missing/empty explicit source (`Dir`, `DirFS`, `i18n.dir`), even with maps | start failure |
| malformed or read-denied source, invalid language directory, file template that does not compile; `Fields` whose file source holds no messages | start failure; nothing published |

A start failure rolls the App back like any other start failure and is reported in `Run`'s (or `App.Start`'s) error. The first call consumes the registration; there is no "free for repair" state. The bundle is published whole after every source validates and before the listener accepts, and is immutable afterwards; request handling performs no filesystem access. An App that called `UseI18n` has something to start, so `ServeHTTP` refuses it until `App.Start` has succeeded.

Tests: a missing explicit catalog directory fails the start, not registration; each misuse row panics with the call site's message; absent conventional discovery starts with the Warn and inactive i18n; `ServeHTTP` before `App.Start` panics with the named message for an App that called `UseI18n`.

## File format

```text
locales/
├── en/
│   ├── messages.json
│   └── fields.json
└── tr/
    ├── messages.json
    └── fields.json
```

`messages.json` accepts a string shorthand or CLDR plural object:

```json
{
  "required": "{{.field}} is required",
  "items": {
    "one": "{{.count}} item",
    "other": "{{.count}} items"
  }
}
```

`fields.json` is an exact map:

```json
{
  "email": "email address",
  "address.city": "city"
}
```

Programmatic strings fill only the CLDR Other form. Use `DirFS` when plural forms or multiple programmatic languages must be embedded in the binary.

Empty programmatic keys/values, invalid templates, invalid language tags, and malformed files are setup errors. Input maps are not retained.

## Message-key resolution

Framework error presentation never adds a namespace prefix. Exact key selection is:

1. explicit `HTTPError.MessageKey` or `ValidationError.MessageKey`;
2. `ResolveMessageKey` with a scope and code;
3. bare code/reason.

```go
ResolveMessageKey: func(ref credo.MessageRef) string {
    switch ref.Scope {
    case credo.MessageScopeValidation:
        return "validation." + ref.Code
    case credo.MessageScopeBind:
        return "request." + ref.Code
    default:
        return "problem." + ref.Code
    }
},
```

This callback is the opt-in namespace policy. A returned empty key is misuse and fails closed. An explicit key miss becomes its literal value for HTTP errors, allowing this without enabling i18n:

```go
return credo.NewHTTPError(http.StatusNotFound, "record_not_found").
    WithMessageKey("Kayıt bulunamadı")
```

Implicit error-key misses use built-in/HTTP status text. Validation and bind misses keep their safe source messages. Resolver-generated keys are never shown as messages merely because lookup missed.

## Validation, bind, and fields

Validation and bind translation happens in the root error pipeline, not inside the validation engine. The top-level keys use error scope with codes `validation_failed` and `bind_failed`. Nested validation uses validation scope; nested decode reason uses bind scope.

`ValidationError.MessageKey` is optional, exact, and `json:"-"`. The resolved wire entry remains:

```json
{"field":"email","code":"required","message":"email address is required"}
```

`field` remains technical. For template data, Credo looks up the exact field path in the selected locale's Fields catalog. A miss uses the raw path; there is no default-language field fallback because that would mix languages within one sentence.

## Plurals and lookup

`T` renders Other. `TPlural` uses CLDR cardinal rules from `golang.org/x/text/feature/plural`, adds `count` to a copied data map, and falls back to Other for an uninterpretable count. File messages support zero/one/two/few/many/other. Programmatic strings always render Other.

Message lookup tries the selected language then Default. Field lookup uses only the selected language. The engine is immutable and concurrency-safe after `UseI18n` completes; no request-time filesystem access occurs.

## Internal boundary

`internal/i18n` imports no root package. Its `Bundle` owns compiled templates, field maps, language matching, and key-level merge. Root code supplies strings at the boundary and performs error classification. The engine is adapted from go-i18n (MIT); BCP 47 and CLDR behavior comes from `golang.org/x/text`.
