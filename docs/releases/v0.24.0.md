# Credo v0.24.0

Credo v0.24.0 is the **lifecycle components** release. The App gets one lifecycle abstraction, the component — a value with `Shutdown(ctx) error` whose teardown the App owns, started when its binding's type shows `Start`, asked for readiness when it shows `Ready`, and stopped in two tiers after its consumers — and it replaces `Shutdowner`, `OnPreDrain`, `OnDrain` and `OnShutdown`. Bootstrap becomes sequential, with one phase for each kind of mistake: registration panics on misuse at the call, `Finalize` reports the whole dependency graph, and starting reports what touches the outside world. Stores, the WebSocket server, i18n and workers run on the components; the DI surface shrinks to seven methods and `Finalize`; a validation rule's plain error becomes an internal failure instead of a 422 violation; and `StatusHandler` refuses the codes it never consults. The release is breaking. Most of it is a compile error, but several changes compile unchanged and behave differently — read [Check this first](#check-this-first) before anything else. The component decisions are recorded in [ADR-024](../adr/024-lifecycle-components.md), and the [pre-v1 migration guide](../guides/pre-v1-migration.md#v0240-at-a-glance) gives every replacement. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.24.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.24.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.24.0
go get github.com/credo-go/credo/store/sqldb@v0.24.0
```

Applications that do not use SQL only need the root module. No dependency version changes in this release. `store/sqldb` changes only in its documentation and tests — `*sqldb.DB` is now described as a `credo.ResourceIdentifier`, through the `ResourceIdentity` method it already had — and its tag follows the lockstep policy.

## Lifecycle components

An App used to have five teardown mechanisms — `OnPreDrain` and `OnDrain` hooks, DI `Shutdowner`s, `OnShutdown` hooks and the cancellation of the context `OnStart` hooks received — each with its own order and deadline rule. Mixing them produced defects no single mechanism could fix: `OnShutdown` ran after DI teardown, so it could never use a singleton; workers stopped before the HTTP drain, so the last job a handler enqueued during the drain was lost; a pointer held by two bindings was shut down twice, the first time before its consumers; a shutdown during startup did not interrupt it; and an App served through `ServeHTTP` started nothing, silently.

They are replaced by one abstraction. `credo.Component` is a value with `Shutdown(ctx) error` whose teardown the App owns — a DI binding whose type shows the method, or a value or constructor handed to `app.Manage`. It grows through optional capabilities, each planned from the binding's type at registration: `credo.Starter` (`Start(ctx) error`, called once in dependency order before the App accepts requests), `credo.Readier` (`Ready(ctx) error`, aggregated by `/ready` under the component's name) and `credo.ResourceIdentifier` (`ResourceIdentity() any`, the resource a value holds). A value the App should start or ask for readiness is provided as its concrete type, with `Alias` for the interface the application uses.

```go
type OutboxRelay struct {
	db     *sqldb.DB
	cancel context.CancelFunc
	done   chan struct{}
}

// Start returns once the relay is usable; the loop outlives the call on a
// context derived from context.WithoutCancel, and Shutdown is its one stop signal.
func (r *OutboxRelay) Start(ctx context.Context) error {
	runCtx, cancel := context.WithCancel(context.WithoutCancel(ctx))
	r.cancel, r.done = cancel, make(chan struct{})
	go func() {
		defer close(r.done)
		r.loop(runCtx)
	}()
	return nil
}

func (r *OutboxRelay) Shutdown(ctx context.Context) error {
	r.cancel()
	select {
	case <-r.done:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

app.Provide[*OutboxRelay](NewOutboxRelay) // func(credo.Infra, *sqldb.DB) *OutboxRelay
```

Components stop in two tiers under one shared deadline. The **ingress** tier — where work enters the process: the WebSocket server, scheduled workers, consumers of an external queue — stops first, concurrently with the HTTP drain. The **internal** tier stops after it, in reverse dependency order, so an in-process consumer stops after the handlers that feed it and before the database it writes to. The tier is declared per registration with `credo.Ingress()`; `credo.Tier` with `TierIngress` and `TierInternal` spells it in configuration fields and reports. An internal component that depends on an ingress one fails `Finalize` with the dependency path and both remedies. Every context lives as long as its call: `Start`'s ends when `Start` returns, `Shutdown`'s carries the drain deadline, `Ready`'s belongs to the probe request.

Four registration options act on components, each checked at the call: `credo.Ingress()` places it in the ingress tier; `credo.Borrowed()`, on `ProvideValue`, keeps the binding and its readiness and leaves starting and stopping to the caller; `credo.Closer()` makes a binding whose type has `Close() error`, `Close()` or `Close(ctx) error` a component the App closes after its consumers — `Close` is never discovered without it; and `credo.Override()` replaces an earlier binding. `credo.Named(name)` names a component handed to `Manage`. A resource that several bindings hold is one component with one teardown, run once, through the holder registered first, after the consumers of every holder.

`OnStart(fn, opts...)` and `OnStop(fn, opts...)` are anonymous components of a tier, internal unless `credo.Ingress()` is passed: start hooks run FIFO after their tier's components have started, stop hooks LIFO before they stop, so a hook can use what the components provide. A hook is a leaf action; anything with its own teardown is a component.

```go
app.Provide[*Cache](NewCache, credo.Closer()) // closed after its consumers
app.OnStop(func(ctx context.Context) error { return flushMetrics(ctx) })
```

A failed start rolls back, in reverse dependency order, every component that was built except the one whose `Start` failed, and leaves the App stopped. A shutdown during the start phase — the first signal in `Run`, the context of `RunContext` or `ServeContext`, or `Shutdown` — interrupts it the same way, and `Run` returns nil after a clean rollback. `WithShutdownTimeout` bounds that rollback as it bounds the drain. A component whose `Start` or `Shutdown` has not returned at the deadline is abandoned and the components it depends on stay open. `Run`, `RunContext`, `ServeContext`, `App.Start` and `Shutdown` report all of this as one `*credo.LifecycleError`, which replaces `*DIShutdownError`: each `LifecycleEntry` names a component (its `credo.Named` name, its type name, `worker:<name>`, or `OnStart[i]`/`OnStop[i]`) with its tier, its phase (`start` or `shutdown`), its outcome (`failed`, `panicked`, `abandoned`, `kept_open`) and its error; a panicking `Start` is a `*credo.DIPanicError` with the new phase `credo.DIPanicStart`.

`app.Start(ctx)` runs the start phase without a listener — `Run`, `RunContext` and `ServeContext` are the calls that serve — for an App served through `ServeHTTP` by an external `http.Server` or in a test; `testutil.Start(t, app)` starts it and shuts it down when the test ends. `App.Start` is accepted once, while the App is building. Whoever owns the external server drains it before `app.Shutdown`:

```go
if err := app.Start(ctx); err != nil {
	log.Fatal(err) // a *credo.LifecycleError; what was built is rolled back
}
srv := &http.Server{Addr: ":8080", Handler: app}
go srv.ListenAndServe()
// …
_ = srv.Shutdown(ctx) // the owner's HTTP drain first
_ = app.Shutdown(ctx) // then the ingress and internal tiers
```

A Credo App mounted into another with `Mount` is handed to the parent with `parent.Manage(child)`, so it starts in the parent's start phase and stops after the parent's HTTP drain. The contract is the [lifecycle spec](../specs/lifecycle.md#components-and-the-start-phase); the [dependency-injection guide](../guides/dependency-injection.md#shutdown-and-lifecycle) and the [deployment guide](../guides/deployment.md#shutdown-and-readiness) show the calls. [ADR-006](../adr/006-application-lifecycle.md) records the call-scoped contexts and the drain in tiers.

## Sequential bootstrap and the three error phases

Registration is sequential: every call — dependency bindings, feature mounts, satellite registrations, routes and hooks — comes from the goroutine that builds the App, before it runs, and none is safe for concurrent use. The documented order is configuration (`New`), `Provide`/`ProvideValue`, feature mounts and satellite registrations in any order among themselves (`UseI18n`, `UseHealth`, stores, workers), `Finalize` with its error handled, then `Resolve`, routes and anything built from a resolved value, then `Run`:

```go
app, err := credo.New() // 1. configuration
if err != nil {
	log.Fatal(err)
}

app.ProvideValue(db) // 2. Provide (db is a *sqldb.DB)
app.Provide[*OrderService](NewOrderService)
app.Provide[*OrderController](NewOrderController)
app.Provide[*OutboxRelay](NewOutboxRelay)

app.UseHealth()                  // 3. feature mounts and satellites
store.Register[*sqldb.DB](app)   //    pinged in the start phase, reported by /ready
worker.Use(app).ContinuousProvided[*OutboxConsumer]("outbox-consumer")

if err := app.Finalize(); err != nil { // 4. every missing dependency and cycle
	log.Fatal(err)
}

orders := app.MustResolve[*OrderController]() // 5. resolve and route
app.GET("/orders/{id}", orders.Show)

if err := app.Run(); err != nil { // 6. start, serve, drain
	log.Fatal(err)
}
```

Each mistake surfaces in one phase. **Registration** panics on misuse known at the call site — a constructor of the wrong shape, a duplicate binding, an `Alias` or `BindMany` whose types do not fit, a dependency registration after `Finalize` or after shutdown began, a `Resolve` before `Finalize` — with a message that names the App method, its type arguments and the remedy. `Provide`, `ProvideValue`, `Alias`, `BindMany` and `UseI18n` therefore return nothing. **`Finalize`** returns what only the whole graph reveals: every missing dependency with its whole path from the registration that needs it, every cycle, constructors that take a `context.Context`, and an internal component that depends on an ingress one — joined in registration order, with the same text on every run. **Starting and serving** return errors for what touches the outside world: a store's ping, a locale file, a component's `Start`. Every new error or panic message names what failed, the phase and the remedy, and its test asserts those parts. The [bootstrap spec](../specs/bootstrap-and-di-lifecycle.md#sequential-bootstrap) and [ADR-022](../adr/022-bootstrap-and-di-ownership.md#sequential-bootstrap-and-three-error-phases) record the contract.

## Stores, health, WebSocket and i18n on the components

Registering a store, the WebSocket server or i18n does no I/O and panics on misuse; what touches the outside world runs in the start phase and fails the start instead.

**Stores.** A store is bound where its ownership is decided, and `store.Register[R]` names that binding; it takes no value and returns nothing. A registration whose `R` has no binding fails `Finalize`. The start phase resolves `R` once — after every override — and pings it as its first start step, before the components that depend on it start; that value is what `/ready` reports with its typed health, so a readiness request resolves nothing. The binding is a component like any other: the App shuts it down after its consumers unless it is borrowed, and a `*sqldb.DB` bound raw and through a wrapper that embeds it is shut down once. Both registrations of one database are now accepted and reported under their own names.

```go
db, err := sqldb.Open(cfg)
if err != nil {
	log.Fatal(err)
}
app.ProvideValue(db)           // the App owns db from here on
store.Register[*sqldb.DB](app) // pinged in the start phase, reported by /ready
```

From the binding on, a composition root that fails before `Run` releases the store with `app.Shutdown(ctx)`, which tears down an App that never ran. See the [store spec](../specs/store.md#registration), the [data-access guide](../guides/data-access.md#what-storeregister-does) and [ADR-015](../adr/015-data-access.md#registration).

**Health.** `/ready` aggregates three sources with no DI resolution per request: the components' `Ready`, from the values built when the App entered running; each registered store's health, from the value the start phase pinged; and the application's checks. The store and worker readiness seams that the health engine resolved from DI on every probe are gone, and a worker's readiness conditions reach `/ready` through its component's `Ready` under `worker:<name>`. During the drain `/ready` still answers 503 `shutting_down` ([ADR-016](../adr/016-health-checks.md#readiness-from-the-kernels-registries)).

**WebSocket.** `websocket.Use` is replaced by `websocket.New(infra, cfg...)`, which registers nothing. The application registers the server as an ingress component, so it starts with the App — its `Start` opens admission — and drains beside the HTTP drain, before the internal components its handlers use. A server that was never started refuses every upgrade with a 500 and logs the missing registration.

```go
ws := websocket.New(app.NewInfra("websocket"), websocket.Config{})
app.Manage(ws, credo.Ingress()) // or bind it with credo.Ingress() when controllers take it
app.GET("/ws", ws.Handler(chat))
```

See the [WebSocket guide](../guides/websocket.md#registering-the-server) and [ADR-019](../adr/019-websocket-integration-and-drain.md).

**i18n.** `UseI18n` returns nothing: it validates the configuration and compiles the programmatic catalog at the call, panicking on misuse — more than one config, `Dir` with `DirFS`, an `i18n` section that does not decode, an invalid `Default` or programmatic message, a second call. A framework start step reads the locale files first in the start walk; a missing explicit source or a malformed file fails the start. Conventional discovery may still find nothing and stay inactive ([localization guide](../guides/localization.md#enabling-i18n), [ADR-013](../adr/013-internationalization.md#registration-and-the-start-phase)).

## Workers as components

`worker.Use(app)` returns a `*worker.Supervisor`, a registry with no lifecycle of its own: no `Start`, no `Shutdown`, no DI binding. Its registration method chooses the worker's kind, and each registration adds one component named `worker:<name>`: its `Start` launches the loop, its `Shutdown` cancels the worker's context and waits for `Run`, and its `Ready` — only when a readiness condition is set — reports the worker's state.

```go
workers := worker.Use(app)

app.Provide[*OrderConsumer](NewOrderConsumer) // func(*sqldb.DB) *OrderConsumer
workers.ContinuousProvided[*OrderConsumer]("order-consumer", worker.ContinuousConfig{
	Restart: worker.Restart{Limit: 5},
})

app.Provide[*Cleanup](NewCleanup)
workers.ScheduledProvided[*Cleanup]("cleanup", "@every 5m", worker.ScheduledConfig{
	RunOnStart: true,
	RunTimeout: time.Minute,
})
```

Scheduled workers default to the ingress tier, so no run starts during the drain; continuous workers default to the internal tier, so they drain what HTTP handlers enqueued before the components they depend on stop. A provided worker is a constructor over `T`: the start walk builds it after `T`'s component dependencies have started, and the worker stops before them. A worker registered by value has no edges the graph can see and takes its place in its tier by registration order, so a worker that uses infrastructure is registered in its provided form. Workers start in the start phase, before their tier's `OnStart` hooks.

Configuration is a per-kind struct in code — `ContinuousConfig{Tier, Restart, UnreadyWhenFailed}` with `Restart{Disabled, Limit, MinDelay, MaxDelay}`, and `ScheduledConfig{Tier, RunOnStart, RunTimeout, MaxConsecutiveFailures, UnreadyWhenFailed, UnreadyUntilFirstSuccess, UnreadyAfterSuccessAge}` — and the `worker` configuration section is no longer read. `Restart.Disabled` is new: the first failed run is terminal. Registration misuse panics at the call; `worker.ParseSchedule` returns the error for an expression that comes from configuration. `Snapshot()` and `Lookup(name)` report the resolved configuration and the statuses `pending`, `running`, `backoff`, `waiting`, `stopped` and `failed`; `worker.CurrentRun(ctx)` replaces the three run-context accessors; the log vocabulary has one terminal `worker failed` line with its reason. The restart backoff, the run-outcome classification and the scheduling rules of v0.20.0 and v0.21.0 are unchanged. The [worker spec](../specs/worker.md#components) is the contract, the [worker guide](../guides/worker.md#tiers) shows the calls and [ADR-023](../adr/023-worker-system.md) records the decisions.

## The seven-method DI surface

The container's public surface is `Provide`, `ProvideValue`, `Alias`, `BindMany`, `Has`, `Resolve` and `ResolveAll`, plus `Finalize`; `MustResolve` and `MustResolveAll` stay as resolve conveniences. Nothing framework-owned is bound in the application's container any more — stores are named through the store registry, workers and the WebSocket server are components — so the methods that existed to defend framework values in it are removed: `ProvideProtectedValue`, `ProtectBinding`, `AdoptValue`, `CanProvideValue`, and `Replace`/`MustReplace` with their superseded-component warning. The `Must*` registration twins go too, since the plain calls already panic on misuse.

An override is `credo.Override()` before `Finalize`, or `testutil.WithOverride` in tests. Both panic when there is no earlier binding of the type, so an override that no longer matches the wiring fails instead of adding a binding nothing resolves. Nothing is handed back: the replaced value never becomes the App's, so whoever built it releases it.

```go
app.Provide[*HTTPPayments](NewHTTPPayments)
app.ProvideValue[*HTTPPayments](stub, credo.Override()) // before Finalize
```

`Has[T]` is the one non-resolving presence probe: it never constructs and reserves nothing. The [container spec](../specs/container.md#the-surface) is the contract, the [dependency-injection guide](../guides/dependency-injection.md#replacing-a-binding) shows the calls and [ADR-004](../adr/004-dependency-injection-and-infra.md#the-public-surface) records the decision.

## Rule errors and explicit status

A validation rule reports a client-visible failure with a `*validation.ValidationError`, which the new `validation.NewError(code, message)` builds, or with `validation.Errors`. Any other error a rule returns is internal: validation stops and the error leaves `Validate`, `BindBody` and `BindQuery` unchanged, so the error pipeline renders a plain error as a 500 whose text is only logged, and a fault with its mapped status. Rendering it as a 422 violation told the client its input was wrong when the server had failed, and put internal text — a driver error, a hostname — into the response body.

```go
validation.Field(&c.Country, validation.By(func(code string) error {
	if len(code) != 2 {
		return validation.NewError("country_code", "must be a 2-letter code")
	}
	return nil // a lookup error returned here would be a 500, not a violation
}))
```

An explicitly constructed `HTTPError` now wins over validation errors wrapped inside it: `credo.NewHTTPError(http.StatusConflict, "tenant_conflict").WithInternal(vErrs)` renders 409, and the wrapped errors stay in `ErrorInfo.Err` for a renderer or the log. A single `*validation.ValidationError` that no `HTTPError` wraps renders 422 `validation_failed` with one violation, like `validation.Errors`. To migrate, search for `validation.By(` and for custom rules' `Validate(value` methods, turn each `errors.New`/`fmt.Errorf` that carries a message for the client into `validation.NewError` with a lowercase snake-case code, and keep returning a plain error where the failure is the server's. The default error envelope is unchanged. See [ADR-011](../adr/011-validation-strategy.md#rule-errors-client-messages-and-internal-failures), [ADR-009](../adr/009-handler-and-error-handling.md#an-explicit-status-wins) and the [error-handling guide](../guides/error-handling.md#rule-errors-client-messages-and-internal-failures).

## StatusHandler accepts 404 and 405

`StatusHandler(code, h)` panics at registration for any code but 404 and 405. Only those two are looked up — for no matching route, and for a matching path without the method — so a handler for 403 or 500 was accepted and silently never called. Supporting more codes is not the remedy, because a 5xx handler would re-enter application code inside error rendering:

```go
app.StatusHandler(http.StatusForbidden, h)
// panic: credo: App.StatusHandler(403): only 404 (http.StatusNotFound) and 405 (http.StatusMethodNotAllowed) are consulted; return an error from the handler and shape its body with App.UseErrorRenderer instead
```

Delete such a registration rather than porting it — it never ran — and shape that response through `app.UseErrorRenderer`. See the [router spec](../specs/router.md#statushandler-system-goyave-inspired) and [ADR-007](../adr/007-router-and-routing.md#status-handlers).

## What an application keeps

After the deletions, an application writes four things it did not write before: two calls for a store (a binding where its ownership is decided, and `store.Register[R](app)`); a registration for a WebSocket server (`app.Manage(ws, credo.Ingress())`); the concrete type and an `Alias` for a value the App should start or ask for readiness; and, for an App served by an external server, `app.Start(ctx)` and the server's own drain before `app.Shutdown`. Everything else in v0.24.0 removes API, states the bootstrap order, or adds an option an application reaches for only when it needs one. The migration guide lists them under [What an application keeps](../guides/pre-v1-migration.md#what-an-application-keeps-v0240).

## Internal

- The test that asserts a 431 header-limit rejection is never logged matched the digits `431` anywhere in the captured log, so an ephemeral port such as 43163 or a timestamp's milliseconds failed it; this is what stopped the v0.23.0 release gate until a rerun. The matching now removes network addresses and the time attribute first, and its helper is tested against both false alarms and real mentions of the rejection.
- Two lifecycle acceptance scenarios are pinned by tests and added to the v1 Gate in [TODO.md](../../TODO.md#v1-gate): the last job an HTTP handler hands to a worker before the drain reaches the database, and a failed start that stops exactly the components that were built, except the one whose `Start` failed.
- The release cadence in the v1 Gate is relaxed: a security fix ships at once as a patch; otherwise a minor collects what is ready when it is cut and names each break under its own CHANGELOG heading.
- [CONTRIBUTING.md](../../CONTRIBUTING.md#coding-standards) gains the message rule: an error or panic message is part of the API — it names what failed, the phase and the remedy — and the test that triggers it asserts those parts.
- The concurrent-registration machinery is deleted with the concurrent-registration tests: `Use*` registrations check their phase once instead of re-checking under the preparation lock.
- Two rejections that no tracked document recorded are written down: the release gate's synthetic-tag invariant and its rejected alternatives (in `scripts/releasegate`), and why no test pins the standard library's handling of QUERY in `CrossOriginProtection` ([middleware spec](../specs/middleware.md#csrf)).
- `examples/saas` follows the documented bootstrap order with every satellite in it — `UseI18n`, `UseHealth`, a store named with `store.Register`, a provided scheduled worker and a WebSocket server managed as an ingress component — and a custom rule that returns `validation.NewError`. The guides lead with the common path, and the README gains the bootstrap snippet and an API summary.

## Unchanged

Routing apart from `StatusHandler`, the middleware chain and the built-in HTTP features, the default error envelope (RFC 9457 stays opt-in through `RFC9457ErrorRenderer`), binding, configuration loading, reload and its hooks, TLS, `httpclient`, authentication and the `store/sqldb` query API are as in [v0.23.0](v0.23.0.md). The worker's restart backoff, run outcomes, run timeouts and scheduling keep their v0.20.0 and v0.21.0 behavior under the new registration calls. The full list of changes is in the [CHANGELOG](../../CHANGELOG.md).
