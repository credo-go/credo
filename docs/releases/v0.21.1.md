# Credo v0.21.1

Credo v0.21.1 is a security and bug-fix release. It closes a fail-open defect in `middleware.ContractGuard`, fixes eight defects — in routing, mounting, multipart cleanup, lifecycle hooks, the stdlib middleware adapter, error logging, dependency-injection diagnostics and `testutil` — and moves YAML decoding to the maintained `go.yaml.in/yaml/v3` module. No exported API is added, removed or renamed. Some of the fixes change what a request does — read [Check this first](#check-this-first). Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.21.1` |
| `github.com/credo-go/credo/store/sqldb` | `v0.21.1` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.21.1
go get github.com/credo-go/credo/store/sqldb@v0.21.1
```

Applications that do not use SQL only need the root module. `store/sqldb` has no code changes; its `go.mod` follows the root module.

## Check this first

| If your application… | Before v0.21.1 | From v0.21.1 |
| --- | --- | --- |
| declares a `ContractGuard` contract with a value outside the documented types — a named string type, a `nil`, a `uint` | the contract was skipped: the handler ran without the declared check | the request is rejected with 500 and the log names the route and the fix — see [Security](#security-contractguard-no-longer-skips-a-contract-it-cannot-read) |
| has a route that matches a path for one method and a less specific route that serves another (`GET /users/new` and `POST /users/{id}`) | `POST /users/new` answered 405 | the less specific route answers, behind its own middleware |
| mounts a handler under a prefix with parameters (`Mount("/t/{tenant}", h)`) | the handler saw the path `/` for every request, and no parameter | it sees the real remainder and reads the parameter as a path value |
| reads an uploaded multipart file after its handler has returned — a goroutine that outlives the request — in a mounted handler, behind `middleware.Timeout` or after `ctx.SetUser` | the temporary file stayed on disk, so the late read worked | the file is removed when the handler returns, as `net/http` does for the request it created; copy what has to outlive the request |
| has tests that build an App with `testutil.NewApp` and `testutil.WithConfig` and rely on a `.env` file or `CREDO_*` variables | the environment was merged on top of the test's values | only the `WithConfig` values are loaded |

## Security: ContractGuard no longer skips a contract it cannot read

`middleware.ContractGuard` read a contract value from route metadata as `string`, `[]string` or `[]any` (`int`, `int32` or `int64` for `MetaMaxBody`) and treated a value of any other type as "no requirement". The route then ran without the check it declared, and nothing was logged. `SetMeta` takes `any`, so the mistake compiles:

```go
type Scope string

const ScopeAdmin Scope = "admin"

api.GET("/reports", listReports).SetMeta(middleware.MetaScope, ScopeAdmin)
```

With this declaration every request passed the scope contract — 200 where the plain string `"admin"` answers 403. `MetaRequireHeaders` and `MetaRequireQuery` were skipped the same way, a `MetaMaxBody` given as `uint`, `float64` or a string was ignored, a route-level `nil` silently switched off the contract inherited from its group, and a `[]any` lost its non-string elements. `MetaAccept` and `MetaAPIVersion` were not skipped: an unreadable value already rejected requests, with 415 and 400; they now answer 500 like the others.

**Who is affected.** Applications that use `ContractGuard` and declare at least one contract with a value outside the documented types, on every release up to v0.21.0. Contracts declared with `string` or `[]string` values (`int`, `int32`, `int64` for `MetaMaxBody`) were enforced and still are.

**After upgrading.** A contract value the guard cannot read rejects the request with the generic 500 instead of calling the handler. The reason reaches the `credo: server error` log record and never the response:

```
contractguard: route GET /api/reports: meta "scope" has unsupported type main.Scope; use string or []string (convert a named type, e.g. string(v); …); request denied
```

Each such record names a route that had been running without its declared contract.

**What to change.** Convert the value where the contract is declared — `SetMeta(middleware.MetaScope, string(ScopeAdmin))`. Replace a `nil` that was meant to lift an inherited contract with the value that requires nothing: `[]string{}` for `MetaScope`, `MetaRequireHeaders` and `MetaRequireQuery`, `"*/*"` for `MetaAccept`, a negative `MetaMaxBody`. The accepted types themselves are unchanged ([middleware spec](../specs/middleware.md#framework-meta-keys)).

## Fixed: a less specific route that serves the method answers

A route that matched the path but not the method ended the search with 405, even when a less specific route served the method:

| Routes | Request | Before | From v0.21.1 |
| --- | --- | --- | --- |
| `GET /users/new`, `POST /users/{id}` | `POST /users/new` | 405 | the parameter route, `id` = `new` |
| `GET /api/users`, `Mount("/api", h)` | `POST /api/users` | 405 | the mounted handler |

This is how chi and `net/http.ServeMux` resolve the same routes, and it holds for regex and catch-all candidates as well. The route that answers runs its own group and route middleware, which may differ from the more specific route's. A request is a 405 only when no route matching the path serves its method, and `Allow` then lists the methods of all of those routes instead of the most specific one's ([router spec](../specs/router.md#matching-order-and-method-not-allowed)).

## Fixed: `Mount` under a prefix with parameters

`Mount("/t/{tenant}", h)` was accepted, but the mounted handler was handed the path `/` for every request and no parameter. It now receives the real remainder and each parameter of the prefix as a path value:

```go
app.Mount("/t/{tenant}", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	tenant := r.PathValue("tenant") // "acme" for /t/acme/x/y
	path := r.URL.Path              // "/x/y"
	// …
}))
```

`credo.URLParam(r, "tenant")` reads the same value — it returned `""` in every mounted handler before. A mounted Credo app reads it with `ctx.Request().PathValue("tenant")`; its `RouteParam` keeps returning its own route parameters only. Several parameters, also within one segment (`/v/{major}.{minor}`), and regex-constrained ones are supported; an encoded slash inside a parameter stays data (`/t/ac%2Fme/x` gives `tenant` = `ac/me`); nested parametric mounts add up, so the innermost handler sees every prefix. The values are set on a clone of the request, so a request the caller still holds — an `http.ServeMux` in front of the app — keeps its own path values. Mounts under a static prefix are unchanged ([router spec](../specs/router.md#sub-router-mounting)).

## Fixed: multipart temporary files are removed when the form was parsed on a copy of the request

`net/http` removes the temporary files of a multipart form only for the request it created. After `ctx.SetUser`, behind `middleware.Timeout` or a `WrapStdMiddleware` middleware that substitutes the request, and inside a handler attached with `Mount`, the form lives on a copy, so every upload beyond the in-memory threshold left its `multipart-*` file in the temporary directory.

The files of the form `BindBody` parsed and of the current request's form are now removed on every way out of the handler — normal completion, a returned error, a panic, a failed compressor. The layers that substitute the request hand a form parsed below them to the request that outlives them, and `Mount` removes the form a mounted handler parsed on its child request. As under `net/http`'s own cleanup, an uploaded file is gone once the handler has returned ([context spec](../specs/context.md#bindbody)).

## Fixed: a panic in an `OnStart` or `OnShutdown` hook is that hook's error

Panics in `OnPreDrain`, `OnDrain` and reload hooks were already recovered; these two were not.

| Hook | Before | From v0.21.1 |
| --- | --- | --- |
| `OnStart` panics | the panic unwound past the teardown: under `Run` the process ended with the listener bound and no hook, drain or DI shutdown run | startup fails like a returned error: the full teardown runs, the listener is released, and `Run` returns `credo: Run: OnStart hook [1]: panic: …` |
| `OnShutdown` panics | the remaining hooks were skipped and the App stayed short of `stopped` | the remaining hooks run and `Shutdown` returns the joined errors |

Each recovered panic is logged once at Error (`credo: OnStart hook panic` / `credo: OnShutdown hook panic`) with `hook_index`, the panic value and the stack. The order of the hooks is unchanged ([lifecycle spec](../specs/lifecycle.md#apponshutdownfn-funcctx-contextcontext-error)).

## Fixed: a response written by an adapted stdlib middleware is recorded

A stdlib middleware adapted with `WrapStdMiddleware` that answered by itself — a 401, a redirect, a file — reached the client correctly but left `Response` uncommitted. The access record said `status=200 bytes=0`, and an error returned further up the chain, or a panic in the middleware after it had answered, appended an error envelope to the response already sent.

Once the middleware returns, `Response.Status()`, `Size()` and `Committed()` report what it wrote, the access record carries it, and a later error is logged as `credo: error after response committed`. A connection the middleware hijacks is reported by `Response.Hijacked()`, and an error returned afterwards is logged as `credo: error after response hijacked` instead of being written to that connection. The body of a response the middleware wrote is still the middleware's own; it does not pass the error pipeline. The adapter allocates one small writer per request for this ([middleware spec](../specs/middleware.md#stdlib-adapter)).

## Fixed: the internal cause of a client error is logged at debug level

The `BindError.Internal` godoc, the error-handling guide and the CSRF documents said that the cause attached to an error — `HTTPError.WithInternal`, the decoder error behind a `BindError`, the reason of a CSRF rejection — "is logged". Below 500 the error pipeline wrote nothing at any level. A 4xx `*HTTPError` or `*BindError` that carries an internal cause now writes one `credo: client error` record at Debug with the status and the cause. Nothing is added at the default level, and client errors without such a cause — a fault provider, an `HTTPStatus()` error, validation errors — still write nothing ([error-handling guide](../guides/error-handling.md)).

## Fixed: `Finalize` reports validation errors in registration order

The container walked its registration map, so the same broken wiring listed its missing dependencies in a different order on every run, and with more than one dependency cycle it was random which one was reported and at which member its text began. The report now follows registration order and reads the same on every run ([container spec](../specs/container.md)).

## Fixed: `testutil.WithConfig` values are the only ones loaded

`testutil.NewApp` promises a test App that never loads configuration from disk. The document built from `WithConfig` values nevertheless went through the loader with its default sources on: a `.env` file in the test's working directory and `CREDO_*` variables in the environment were merged on top of the test's values, and a `CREDO_ENV_FILE` naming a missing file failed the test. The loader now runs with `config.WithoutDotenv()` and `config.WithoutProcessEnv()`, so a test behaves the same in a developer's shell and in CI. A test that relied on the environment reaching its App sets the value with `WithConfig` instead. `NewApp` without `WithConfig` is unchanged.

## Changed: YAML is decoded with `go.yaml.in/yaml/v3`

`config` imports `go.yaml.in/yaml/v3` v3.0.5 instead of `gopkg.in/yaml.v3` v3.0.1. It is the same decoder under the module path of the YAML organization, which took over its maintenance after the original author labelled the project unmaintained in April 2025. No Credo API changes, and the two modules coexist in one build, so an application that imports `gopkg.in/yaml.v3` itself is unaffected.

One decoding difference reaches `config.Load`: a mapping with a non-string key that merges (`<<`) a mapping keyed by a sequence or a mapping made the old decoder panic; the load now fails with an error. The new module requires nothing, so the root module's three indirect requirements (`gopkg.in/check.v1`, `github.com/kr/pretty`, `github.com/rogpeppe/go-internal`) are gone.

## Documentation

- The `StatusHandler` godoc, the router spec and ADR-007 state what the code does: a custom status handler is consulted for 404 (no route matches) and 405 (the path matches, the method does not) only. The documents promised handlers for "404, 405, 500" and "other status codes"; a handler registered for another code is accepted and never called, and an error a route handler returns — `credo.ErrNotFound` included — goes through the central error pipeline, not through the custom 404 handler ([router spec](../specs/router.md#statushandler-system-goyave-inspired)).
- `CONTRIBUTING.md` no longer says that the root package has zero external dependencies. Its own imports are the standard library and in-module packages; through `config` and `internal/i18n` it links three modules — `go.yaml.in/yaml/v3`, `github.com/go-viper/mapstructure/v2` and `golang.org/x/text` — which is what an application importing `github.com/credo-go/credo` alone builds in. An architecture test now fails when that set changes without its allowlist changing in the same commit.

## v0.21.0 documentation correction: static files

The v0.21.0 notes on the static-file fix said two things the fix does not support. Nothing in the behavior shipped in v0.21.0 changes; the [CHANGELOG](../../CHANGELOG.md) entry and the in-repository [v0.21.0 release notes](v0.21.0.md#fixed-static-files-whose-names-contain-) now read:

| The v0.21.0 notes said | Accurate statement |
| --- | --- |
| `/static/%252e%252e/secret` answers 404 | the request reaches the literal path `%2e%2e/secret`: it serves that file when it exists and answers 404 when it does not |
| the listed outcomes, without a condition | they are the outcomes with SPA fallback disabled |
| "no path ever escaped the served directory" | the second decode did not bypass the lexical traversal checks — null bytes, backslashes and explicit `..` segments were and are rejected with 400 |

Protection against symlink escape was never a property of that fix. It depends on the filesystem passed to `app.Static`: `os.DirFS` does not provide it; use `os.Root.FS()` or `credo.DirFS` for production disk serving ([static-files guide](../guides/static-files.md#osroot-production-symlink-safe)).

## Unchanged

The accepted `ContractGuard` value types, mounts under a static prefix, the order of lifecycle hooks, the error envelope, and the configuration sources and their precedence are as in [v0.21.0](v0.21.0.md). The full list of changes is in the [CHANGELOG](../../CHANGELOG.md).
