# Credo v0.13.0

Credo v0.13.0 adds first-class support for the HTTP QUERY method standardized
by RFC 10008. QUERY is available across routing, middleware, mounted handlers,
and the outbound HTTP client without introducing GET twins or a second route
configuration model. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.13.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.13.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.13.0
go get github.com/credo-go/credo/store/sqldb@v0.13.0
```

Applications that do not use SQL only need the root module.

## First-class QUERY routes

Register explicit QUERY routes through the same fluent surface as the other
HTTP methods:

```go
app.QUERY("/products", func(ctx *credo.Context) error {
    var query ProductQuery
    if err := ctx.Request().BindBody(&query); err != nil {
        return err
    }
    return ctx.Response().JSON(http.StatusOK, searchProducts(query))
})
```

`App.QUERY` and `Group.QUERY` both return `*Route`, so names, metadata, route
middleware, host routing, URI generation, introspection, and trailing-slash
handling work exactly as they do for existing route methods. Mounted
`http.Handler` applications also receive QUERY.

Credo deliberately does not create GET or HEAD twins for QUERY. GET query
parameters and a QUERY request representation are distinct input contracts and
must be registered explicitly.

## Required Content-Type

RFC 10008 requires QUERY request content to be labelled. Every matched QUERY
request must therefore carry a non-blank `Content-Type`, including an empty-body
request and a request dispatched to a mounted handler. Missing or blank values
fail before the application handler through the normal error pipeline:

```json
{
  "success": false,
  "code": "content_type_required",
  "message": "Content-Type is required for QUERY requests."
}
```

The guard runs inside the ordinary middleware chain, so authentication,
request IDs, access logging, and route middleware retain their established
ordering. Once the header is present, `BindBody` keeps ownership of media-type
support, decoding, strict-body behavior, and validation: unsupported types
return 415 and malformed supported content follows the existing bind-error
contract.

English and Turkish starter catalogs under `examples/references` include the
new bare `content_type_required` key.

## Browser middleware

QUERY is included in CORS's default allowed-method set, enabling a default
preflight to authorize it. It is also treated as safe by `middleware.CSRF`.
These are separate properties: QUERY is safe and idempotent under RFC 10008,
but it is not a browser CORS-safelisted method, so a cross-origin fetch still
requires preflight.

Applications must never mutate state from a QUERY handler.

## Outbound retries and redirects

`httpclient.DefaultRetryIf` now recognizes QUERY as idempotent. A body is
retried only when `http.Request.GetBody` can recreate it, preserving the
existing replay-safety rule.

Clients returned by `httpclient.New` also prevent Go's historical 301/302
rewrite from silently changing QUERY to GET:

- replayable QUERY method, body, and body headers are preserved across 301/302;
- a non-replayable QUERY returns the 3xx response unchanged;
- 303 intentionally becomes GET;
- 307/308 retain the standard library behavior;
- cross-origin sensitive-header stripping and the ten-redirect limit remain
  enforced.

Assigning `client.CheckRedirect` after `httpclient.New` replaces this policy
and is the full-control escape hatch.

## Deliberately small API surface

This release adds no QUERY-specific route options, exported method constant,
automatic `Accept-Query` header, automatic OPTIONS handler, response cache, or
GET-to-QUERY twin. Applications may emit `Accept-Query` with an ordinary
response header. Existing `middleware.ContractGuard` plus `MetaAccept` remains
the optional generic media-type contract when one is needed.

Before enabling QUERY in production, verify that proxies, WAFs, CDNs, API
gateways, and observability pipelines preserve and record the method and its
request content. A QUERY-aware cache must include request content and relevant
metadata in its cache key; use `Cache-Control: no-store` where the deployment
chain cannot guarantee this.
