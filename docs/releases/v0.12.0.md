# Credo v0.12.0

Credo v0.12.0 replaces the default RFC-shaped error body with a compact,
application-oriented JSON envelope and completes the framework's configurable
i18n message-resolution model. It also fixes release recovery validation and
publishes versioned configuration and locale reference files. Credo remains
Beta and pre-1.0. This release contains intentional breaking changes described
below.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.12.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.12.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.12.0
go get github.com/credo-go/credo/store/sqldb@v0.12.0
```

Applications that do not use SQL only need the root module.

## Breaking: compact default error envelope

The default error response is now ordinary `application/json`:

```json
{
  "success": false,
  "code": "validation_failed",
  "message": "Validation failed",
  "errors": [
    {"field": "email", "code": "required", "message": "is required"}
  ]
}
```

`details` and `errors` are omitted when empty. Success responses do not gain a
framework-owned `success:true`; applications that want a symmetric success
envelope can continue to use `SuccessRenderer` with `Context.Render`.

`ErrorRenderer` now receives a request-scoped pointer:

```go
type ErrorRenderer func(ctx *credo.Context, info *credo.ErrorInfo) any
```

The normalized value exposes `Err`, `Status`, `Code`, `MessageKey`, `Message`,
`Details`, and `Errors`. A renderer may override the response status by mutating
`info.Status` before returning its body. Status, JSON encoding, HEAD behavior,
and the final write remain framework-owned unless the renderer commits the
response itself.

RFC 9457 remains available as a first-party opt-in:

```go
app, err := credo.New(
    credo.WithErrorRenderer(credo.RFC9457ErrorRenderer()),
)
```

`ProblemDetails` and `RFC9457Config.ResolveType` support applications that keep
the standards-based representation.

## Breaking: bind error classification

Bind failures now use `bind_failed` as their top-level code. The exact decode
reason such as `syntax`, `type_mismatch`, or `unknown_field` is preserved in
`errors[0].code`.

Consumers that previously switched on the top-level bind reason should move
that branch to the nested error entry.

## Breaking: exact i18n message keys

Credo no longer prepends hidden `errors.`, `http.`, `v.`, or `bind.` prefixes.
An explicit `HTTPError.MessageKey` or `ValidationError.MessageKey` is resolved
exactly. Without an explicit key, Credo passes the message scope and machine
code to `I18nConfig.ResolveMessageKey`; when no resolver is installed, the bare
code is used.

```go
app.UseI18n(credo.I18nConfig{
    ResolveMessageKey: func(ref credo.MessageRef) string {
        switch ref.Scope {
        case credo.MessageScopeError:
            return "errors." + ref.Code
        case credo.MessageScopeValidation:
            return "validation." + ref.Code
        default:
            return ref.Code
        }
    },
})
```

Rename existing catalog entries or install a resolver that preserves the old
namespace policy.

## Programmatic default-language catalogs

`I18nConfig.Messages` and `I18nConfig.Fields` provide copied programmatic
catalogs for the effective default language. They may be used alone or as a
base over which `Dir` / `DirFS` catalogs merge key by key. Messages and field
display names stay separate, and files win on collisions.

Explicit file sources remain fail-loud: an explicitly configured `Dir`,
`DirFS`, or RawConfig `i18n.dir` must exist and contain messages even when a
programmatic catalog is present. Only a missing conventional `locales/`
directory discovered by zero-config setup remains an inactive warning.

## Reference files

[`examples/references`](../../examples/references/README.md) now contains:

- equivalent, tested `config.yaml` and `config.json` files;
- an `.env.example` override template;
- complete English and Turkish `messages.json` and `fields.json` starter
  catalogs.

These are versioned copyable references, not framework-embedded runtime data.
The runnable `hello` and `saas` examples remain separate and contain only the
configuration they actually consume.

## Release recovery fix

The release candidate gate now moves inherited lockstep version refs to the
candidate HEAD with `git update-ref`. A recovery dispatch therefore validates
the intended release content even when the real tags already exist; it neither
fails on duplicate tags nor silently validates stale tagged content.
