# Credo v0.22.0

Credo v0.22.0 is the **Bun v1.3.0** release. `store/sqldb` moves from Bun v1.2.18 to v1.3.0 (`github.com/uptrace/bun` and its three dialect modules) and from pgx v5.10.0 to v5.11.0. The curated `store/sqldb` API keeps its signatures, so an application that stays on `SelectQuery`, the typed terminals and `Migrate` compiles unchanged. The release is breaking where an application reaches Bun directly and in what the database accepts — read [Check this first](#check-this-first). It also inherits three upstream security fixes ([Security](#security-inherited-from-bun-v130)) and removes one exported error. The root module has no code changes; its tag follows the lockstep policy. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.22.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.22.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.22.0
go get github.com/credo-go/credo/store/sqldb@v0.22.0
```

Applications that do not use SQL only need the root module. The dependency moves of this release are in `store/sqldb` alone:

| Dependency | v0.21.1 | v0.22.0 |
| --- | --- | --- |
| `github.com/uptrace/bun` and `dialect/{pgdialect,mysqldialect,sqlitedialect}` | v1.2.18 | v1.3.0 |
| `github.com/jackc/pgx/v5` | v5.10.0 | v5.11.0 |

## Check this first

| If your application… | Before v0.22.0 | From v0.22.0 |
| --- | --- | --- |
| passes an `int` variable to Bun's `Limit` or `Offset`, or assigns Bun's `Count` to an `int` — inside an `Apply` closure, through `Unwrap`, `db.Conn(ctx)`, `RequireTx` or `Client()` | compiled | does not compile: Bun takes and returns `int64`. An untyped constant (`q.Limit(10)`) is unaffected; write `int64(n)` and convert the count. Credo's curated `Limit`, `Offset`, `Page` and `Count` keep `int` |
| checks `errors.Is(err, sqldb.ErrInvalidLimitOffset)` | compiled; the curated `Limit`/`Offset` returned it for values outside the signed 32-bit range | does not compile: the error is removed and every value reaches the database |
| stores a string that contains a NUL byte (`0x00`) | stored with the byte removed, on every database | SQLite and PostgreSQL reject the statement; MySQL still strips the byte — see [NUL bytes](#changed-a-nul-byte-in-a-string-argument-fails-the-statement) |
| has two migration files with the same numeric prefix under different names | the later file replaced the earlier one's `Up`/`Down` silently | `Discover` returns `migrate: duplicate migration ID …` |
| combines `WhereOr` with a soft-delete model or `WherePK` | `WHERE a OR b AND deleted_at IS NULL` | `WHERE (a OR b) AND deleted_at IS NULL`; a query that relied on the old precedence changes its result set |
| relies on a `.tx.up.sql` migration being marked applied even when its COMMIT failed | marked applied | the COMMIT error reaches `Migrate` and the migration stays unapplied |
| scans a text-format `timestamptz` with pgx and compares the `Location` | differed from the binary format | both return `time.Local` (or the codec's `ScanLocation`); `date` rejects impossible dates such as `2024-02-30` |

## Security: inherited from Bun v1.3.0

No Credo code had a defect of its own; applications upgrade to inherit the fixes.

**Line-comment injection with negative numbers** (CVE-2024-44906 class, [uptrace/bun#1396](https://github.com/uptrace/bun/issues/1396)). Credo hands every query argument to Bun's SQL formatter rather than to driver placeholders. A negative number rendered right after a `-` in the SQL text formed a line comment and cut the statement short:

```go
db.Select().Model(&rows).Where("balance > -?", n) // n = -5 rendered "balance > --5"
```

Bun v1.3.0 separates the two with a space (`- -5`). Any Credo query with that shape — a `-` immediately before a placeholder that can receive a negative number — was affected.

**NUL bytes** ([uptrace/bun#1406](https://github.com/uptrace/bun/pull/1406)). A string argument carrying a NUL byte is rejected instead of silently shortened; the per-database behavior is under [Changed](#changed-a-nul-byte-in-a-string-argument-fails-the-statement).

**`pgdriver` TLS** ([uptrace/bun#1402](https://github.com/uptrace/bun/pull/1402)). Bun's own PostgreSQL driver now verifies the server certificate under `WithInsecure(false)`. Credo's PostgreSQL driver is pgx, so this fix does not reach a Credo application.

## Changed: Bun stores and returns `int64` for `Limit`, `Offset` and `Count`

Bun v1.3.0 changes `SelectQuery.Limit`, `Offset`, `Count` and `ScanAndCount` (and `UpdateQuery`/`DeleteQuery.Limit`) from `int` to `int64`. Credo's curated `SelectQuery.Limit`, `Offset` and `Page` keep `int` parameters and `Count` keeps its `int` result, so code written against them compiles unchanged. Code that reaches the native query changes:

```go
// Before v0.22.0
q.Apply(func(q *bun.SelectQuery) *bun.SelectQuery { return q.Limit(n) })   // n int

// From v0.22.0
q.Apply(func(q *bun.SelectQuery) *bun.SelectQuery { return q.Limit(int64(n)) })
```

`Count` returns an error instead of a truncated total when the `int64` count does not fit in `int`, which is possible on 32-bit platforms only. The private-field compatibility layer behind `Count` and `Page` is taught the new field types; its layout test pins Bun v1.3.0.

## Changed: every `Limit`/`Offset` value reaches the database

Bun v1.2.18 stored `LIMIT` and `OFFSET` in `int32` fields, so the curated `Limit` and `Offset` rejected values outside the signed 32-bit range with `ErrInvalidLimitOffset` before the query ran, and `Page` rejected such windows with `pagination.ErrInvalidPageRequest`. With `int64` storage there is no range to guard: `Limit` and `Offset` forward every value, and `Page` executes any window whose offset fits in `int`. `ErrInvalidLimitOffset` is removed; an `errors.Is` check against it stops compiling and can be deleted.

Unchanged: `Page` still rejects a nil request, a non-positive `Page` or `PerPage` and a native `int` offset overflow with `pagination.ErrInvalidPageRequest` before COUNT, and zero or negative `Limit`/`Offset` values still omit the clause ([pagination spec](../specs/pagination.md)).

## Changed: a NUL byte in a string argument fails the statement

Bun v1.2.18's dialects dropped a NUL byte (`0x00`) from a string argument, so a value the application had validated — `"admin\x00x"`, distinct from `"adminx"` — was persisted as another value. Bun v1.3.0's base dialect refuses to render it: on SQLite and PostgreSQL the statement fails with an error that `store.KindOf` leaves unmapped, and nothing is persisted. MySQL is unchanged — its dialect still strips the byte ([uptrace/bun#1443](https://github.com/uptrace/bun/issues/1443)) — which a canary subtest of the real-MySQL job pins so that the documents are updated when upstream changes it. Reject NUL at the validation boundary ([data-access guide](../guides/data-access.md#nul-bytes-in-strings)).

## Changed: duplicate migration IDs are rejected at `Discover`

`migrate.Migrations.Discover` returns `migrate: duplicate migration ID …` when two migration files share a numeric prefix under different names ([uptrace/bun#1357](https://github.com/uptrace/bun/pull/1357)). Bun v1.2.18 let the later file replace the earlier one's `Up`/`Down` silently, so one of the two never ran. `RegisterMigrations` is not reached with such a set; rename the file.

## Changed: soft-delete `WhereOr` is parenthesized

A top-level `WhereOr` on a soft-delete model, or next to `WherePK`, renders `WHERE (a OR b) AND deleted_at IS NULL` instead of `WHERE a OR b AND deleted_at IS NULL` ([uptrace/bun#1321](https://github.com/uptrace/bun/issues/1321)). A query that relied on the old precedence — a soft-deleted row reachable through the OR branch — changes its result set. `SelectQuery.Clone` carries the OR state along.

## Changed: pgx v5.11.0

On Go 1.27 pgx scans PostgreSQL types through `database/sql` directly (`driver.RowsColumnScanner`). Combined with Bun v1.2.18 that deadlocked every scan of a `jsonb`, `bytea` or `numeric` column into `map[string]any` ([uptrace/bun#1434](https://github.com/uptrace/bun/issues/1434)); Bun v1.3.0 fixes it and a real-PostgreSQL subtest pins the fix under a deadline. pgx's own behavior changes that reach an application through `sqldb`: a `timestamptz` scanned from the text format is returned in `time.Local` (or the codec's `ScanLocation`), as the binary format always was; `date` rejects impossible dates such as `2024-02-30` instead of normalizing them; the OS user account is looked up only when the connection string, environment and service file name no user ([pgx v5.11.0 release notes](https://github.com/jackc/pgx/releases/tag/v5.11.0)).

## Fixed: a transactional SQL migration reports its COMMIT error

The COMMIT or ROLLBACK error of a `.tx.up.sql` migration reaches `Migrate`, so a commit that fails — a deferred constraint violated at COMMIT, a serialization failure — leaves the migration unapplied and eligible for the next run. Bun v1.2.18 discarded that error ([uptrace/bun#1389](https://github.com/uptrace/bun/issues/1389)), and the documents advised a Go migration with an explicit transaction wherever the commit result had to gate the applied marker; that advice is withdrawn. The contract is pinned by a conformance test — a deferred foreign key violated at COMMIT — on SQLite and PostgreSQL ([data-access guide](../guides/data-access.md#migrations)).

## Documentation

- Every Bun reference in the tracked documents and package comments is re-pinned to v1.3.0 after re-verification against its source. The `SelectQuery.Clone` compatibility layer restores execution state that Bun v1.3.0's `Clone` now copies itself; the layer stays, pinned to the v1.3.0 layout, until a later minor removes it.
- The [pre-v1 migration guide](../guides/pre-v1-migration.md#data-access) gains a Data access section with the consumer-visible changes of this release in one table.

## Unchanged

The curated `store/sqldb` API, the typed terminals, the transaction model, error mapping, the logical-count contract of `Count` and `Page` (standalone `Having` and a direct compound root still return `ErrUnsupportedCountQuery`), and every root-module package are as in [v0.21.1](v0.21.1.md). The full list of changes is in the [CHANGELOG](../../CHANGELOG.md).
