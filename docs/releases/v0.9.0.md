# Credo v0.9.0

Credo v0.9.0 finishes the response-envelope story. The error renderer becomes a shape-only hook — it returns the response body and the framework does everything else — and its pairing with the success-side `SuccessRenderer`/`Context.Render` seam is now documented as the way an application applies one envelope to every response it produces. The project remains Beta and pre-1.0. **This release contains a breaking change** to the `ErrorRenderer` signature; migration is mechanical.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.9.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.9.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.9.0
go get github.com/credo-go/credo/store/sqldb@v0.9.0
```

Applications that do not use SQL only need the root module.

## Breaking: `ErrorRenderer` is shape-only

The renderer's job was always the body's shape, but the old contract made it write the response itself — every custom renderer repeated `WriteHeader` and encoding by hand, and a renderer that wrote nothing hit a warn-and-fallback path. The new signature returns the body instead ([ADR-009](../adr/009-handler-and-error-handling.md)):

```go
type ErrorRenderer func(ctx *Context, info ErrorInfo) any
```

- A **non-nil return** is encoded with the application's JSON profile and written with `info.Problem.Status`. Mutate `info.Problem.Status` before returning to change the status — it is the renderer's one status seam.
- **nil** keeps the default RFC 7807 Problem Details body. Headers-only and side-effect-only renderers (Sentry reporting, `Retry-After`, `WWW-Authenticate`) become a plain `return nil`; the warn-and-fallback path is gone because nil is now the documented signal.
- Classification, logging, Content-Type, HEAD handling, and committed-response guards stay framework-owned. The renderer is still called for HEAD so it can set headers; the returned body is discarded and a status-only response goes out.
- Full control remains available: a renderer may commit the response itself through the `Context` (e.g. for a non-JSON error body), after which its return value is ignored — so a renderer can no longer double-write.

### Migration

Add `any` to the signature and replace the final write with a return:

```go
// before
app.SetErrorRenderer(func(ctx *credo.Context, info credo.ErrorInfo) {
    ctx.Response().JSON(info.Problem.Status, myShape(info))
})

// after
app.SetErrorRenderer(func(ctx *credo.Context, info credo.ErrorInfo) any {
    return myShape(info)
})
```

A renderer that only set headers now ends with `return nil`. A renderer that wrote a non-JSON body keeps its own write and adds `return nil`.

## Response envelopes, documented

`ErrorRenderer`'s success-side mirror — `app.SetSuccessRenderer` consulted only by `ctx.Render(status, data)` — has shipped since the early releases but was documented only in passing. The [error-handling guide](../guides/error-handling.md) now has a **Response Envelopes** section showing the pair applied together: one application-defined envelope for every response, success and failure alike (404/405/panic/bind included), with no handler ever constructing it, and the raw `Response` helpers still bypassing it for webhooks and health probes. Credo continues to ship no envelope shape of its own — both renderers are opt-in and nil by default.

## Also in this release

Merged since v0.8.0:

- The `examples/saas` example failed at startup with a config-key mismatch; it is repaired, each example now settles on a single config format (hello = JSON, saas = YAML), and the README's claims were brought back in line with what is implemented.
- CI now *runs* every example — build, poll a real endpoint to 200, then assert a clean SIGTERM shutdown — instead of only compiling them, and `examples/hello` no longer reports a graceful shutdown as exit 1.
- Where the error pipeline begins is documented: 404/405, bind failures, 413, and panics all render as RFC 7807 through `ErrorRenderer`, while `net/http`'s own pre-routing rejections (431, malformed-request 400, unsupported-transfer-encoding 501) are plain text written straight to the connection — see the guide's "What the Pipeline Does Not Cover".

## Upgrade notes

The only source change is the `ErrorRenderer` signature above; applications using the default renderer are unaffected on the wire. A custom renderer that previously wrote the RFC 7807 problem itself can usually shrink to `return info.Problem` — note the body is then encoded with the application JSON profile and `application/json` (the default nil path keeps `application/problem+json`).

The required test, race, real-database, lint, release-gate, examples, and CodeQL checks pass for the release candidate. An additional full-lint canary remains non-blocking while third-party analyzer IR support catches up with Go 1.27.
