# Credo v0.18.0

Credo v0.18.0 is the **lifecycle coordination** release: it closes the runtime findings of the September 2026 architecture review. Workers now finish their cleanup before any DI resource is shut down, a reload can no longer outlive the infrastructure it runs against, termination signals are serviced while a reload is in progress, and the worker registration window is enforced uniformly. There are no breaking changes; every entry is a behavioural fix under the existing API. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.18.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.18.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.18.0
go get github.com/credo-go/credo/store/sqldb@v0.18.0
```

Applications that do not use SQL only need the root module.

## Workers drain before DI teardown

`worker.Register` now attaches the pool to `App.OnDrain`. The bounded cleanup a worker performs after its context is cancelled (the "write the last batch" pattern) completes concurrently with the HTTP drain and **before any DI singleton's `Shutdown` runs**, whatever the order in which the worker and the resource were registered.

Previously the pool was stopped only by the container's reverse-registration `Shutdowner` pass. A resource registered after the pool was closed first, so a worker could observe a closed database or client while flushing.

The shutdown sequence is now:

```
mark unready -> OnPreDrain -> cancel lifecycle ctx -> HTTP drain || OnDrain (workers stop here)
  -> await in-flight reload -> DI Shutdown (reverse order) -> OnShutdown (LIFO)
```

`Pool.Shutdown` is idempotent with a stable result: nil once every worker has returned, whatever the caller's context state; `ctx.Err()` only while workers are still running. `Start` is refused after `Shutdown`, and a `Start` racing a direct `Shutdown` is ordered under the pool mutex, so no worker goroutine can be launched past a wait that already began.

A worker that ignores cancellation past the shutdown deadline is reported as an incomplete `OnDrain` task, once, and teardown continues with the same expired context. This is the same contract as any over-deadline `OnDrain` hook.

## Reload and shutdown are coordinated

A `Reload` in flight when `Shutdown` begins now has its participants, subscribers and `OnReload` hooks cancelled: their context is bound to both the caller's context and the application lifecycle. `Shutdown` waits for the reload to return after the HTTP/`OnDrain` phase and before DI teardown, then keeps the reload slot so no later reload can start.

Previously a reload callback could keep running against already-closed DI infrastructure and the reload completed without error.

Queueing semantics are explicit:

- A `Reload` whose context is already cancelled, on arrival or by the time it acquires the slot, returns `ctx.Err()` before loading a candidate or running any callback.
- A `Reload` queued behind an in-flight one returns its own `ctx.Err()` if its context ends first, and the not-running error, without reloading, if shutdown begins while it waits.

The guarantee is bounded by the shutdown deadline. Cancellation is cooperative: a callback that ignores its context can still overlap DI teardown, in which case `Shutdown` logs and returns `credo: shutdown: reload still in flight` and proceeds. ADR-020 records this decision and the rejected hard-barrier alternative.

## Termination signals are serviced during a reload

Under `Run`, signal-triggered reloads now run off the signal loop's goroutine. A `SIGINT`/`SIGTERM` arriving during a long or cancellation-ignoring `OnReload` hook starts the drain immediately and resets signal delivery at once; a second signal force-kills as before.

Previously the loop ran the reload synchronously, so a termination signal was neither acted on nor reset until the reload returned, leaving `SIGKILL` as the only way to stop the process. Coalescing is unchanged: at most one reload runs at a time and signals arriving mid-reload produce exactly one follow-up.

## Worker registration window and pool binding

- Every `worker.Register` call after `App.Finalize` returns `worker: Register after app.Finalize`. Previously only the first registration, the one creating the pool, was rejected; later ones were silently accepted and never started.
- The pool is published with `ProvideProtectedValue`, so `Replace[*worker.Pool]` is rejected and the pool wired into the lifecycle and readiness seam cannot diverge from the one DI hands out. A `*worker.Pool` provided outside `worker.Register` is refused with an error.

## Internal clean-up

A pre-release sweep removed code that only tests kept alive: the unused i18n `Localizer`, dynamic HTTP method registration in the radix tree, several single-call-site wrappers, and duplicate tests. None of it was reachable through the public API; the Content-Encoding identity check is now shared by `Request.BindBody` and `middleware.Decompress` through one internal helper.

## Unchanged

Routing, context, the error envelope, configuration loading, store contracts and the public worker API carry over as they are. `store/sqldb` participates in this release only through the lockstep version bump and a boundary test that confines `unsafe` to the documented Bun compatibility file.
