# Credo v0.25.0

Credo v0.25.0 is the **bootstrap simplification** release. The composition root shrinks to what only the application knows. A bound store is an ordinary component: `app.ProvideValue(db)` alone pings a `*sqldb.DB` at start, reports it in `/ready` and shuts it down after its consumers, and `store.Register` goes. The first `Resolve` finalizes the container. `Provide` takes its binding's type from the constructor, and an interface is bound with `Alias`. A WebSocket server declares its own tier. Framework modules log through the App's logger, with one key, `component`, naming the application part. Workers move into the root package under `app.Workers()`, and rate limiting moves into `middleware/ratelimit`. Two defects of nested validation are fixed. The release is breaking. Most of it is a compile error, but several changes compile unchanged and behave differently — read [Check this first](#check-this-first) before anything else. The decisions are recorded in [ADR-004](../adr/004-dependency-injection-and-infra.md), [ADR-015](../adr/015-data-access.md), [ADR-016](../adr/016-health-checks.md), [ADR-022](../adr/022-bootstrap-and-di-ownership.md), [ADR-023](../adr/023-worker-system.md) and [ADR-024](../adr/024-lifecycle-components.md), and the [pre-v1 migration guide](../guides/pre-v1-migration.md#v0250-at-a-glance) gives every replacement. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.25.0
go get github.com/credo-go/credo/store/sqldb@v0.25.0
```

Applications that do not use SQL only need the root module. `store/sqldb` now imports the root package, for `credo.InfraFrom`, so it requires `credo v0.25.0` exactly. The dependency moves of this release:

| Module | Dependency | From | To |
| --- | --- | --- | --- |
| root | `golang.org/x/text` | v0.41.0 | v0.43.0 |
| root | `go.yaml.in/yaml/v3` | v3.0.5 | v3.0.6 |
| `store/sqldb` | `github.com/jackc/pgx/v5` | v5.11.0 | v5.12.0 |
| `store/sqldb` | `github.com/go-sql-driver/mysql` | v1.10.0 | v1.10.1 |

An application that imports `middleware` without `middleware/ratelimit` no longer links `github.com/sethvargo/go-limiter`; the module stays a requirement of the root module.

## A store is an ordinary component

A store needed two calls in v0.24.0: a binding, and `store.Register[R](app)` to name it, ping it and report it. The second call was a second place to get the first wrong, and a database bound without it was neither pinged nor reported. In v0.25.0 the binding does it all. `*sqldb.DB` implements `Start`, which pings under `sqldb.Config.PingTimeout` (default `sqldb.DefaultPingTimeout`, 5 s) and then logs each pool warning once, and `Ready`, which is nil while `Health` is UP. The lifecycle starts it, asks it for readiness and shuts it down after its consumers, as it does every component ([store spec](../specs/store.md)).

Two options cover a database whose outage must not stop the service. `credo.OptionalReadiness()` on the binding reports its entry in `/ready` without gating readiness. `sqldb.WithOptionalStart()` on `Open` logs a failed ping at `Start` and lets the start go on, leaving the pool open since `database/sql` opens connections on demand. The two are independent: a database opened with `WithOptionalStart` still gates readiness until it answers, unless it is bound with `OptionalReadiness` ([data-access guide](../guides/data-access.md#a-database-that-must-not-gate-readiness-or-stop-the-start)).

## Readiness: latency, `degraded` and optional entries

Every readiness entry carries its `latency`, a named check's included, and a failure is logged in the check shape with it. An entry registered with `credo.OptionalReadiness()` — on `Provide`, `ProvideValue` or `Manage`, or on `AddReadinessCheck`, which gains a variadic option parameter — is reported and logged without gating: while every gating entry is up and an optional one is not, `/ready` answers 200 with the top-level status `degraded`. During the drain `/ready` answers 503 `shutting_down` as before. A resource held by several registrations has one entry, its holder of record's, and the registrations agree on the options that shape it ([health spec](../specs/health.md)).

## The first `Resolve` finalizes

`app.Finalize()` becomes an optional early check. The first `Resolve`, `ResolveAll`, `MustResolve` or `MustResolveAll` finalizes the container when nothing has; a failure is that call's error, and every later `Resolve` returns it. `Has`, `GetConfig`, `MustGetConfig` and `ConfigExists` never finalize. A registration after the freeze panics with the trigger — `Finalize`, the first resolving call with its type, `Run`, `RunContext`, `ServeContext`, `Start` or the first `ServeHTTP` — its site and up to three callers:

```text
credo: App.Provide[*app.Mailer]: called after the container was finalized by Resolve[*app.Hub] at /src/wiring/wiring.go:17 (called from /src/main.go:31); register before that call
```

## `Provide` binds what its constructor returns

`App.Provide(constructor, opts...)` has no type parameter: the binding's type is the constructor's first result type. An interface is bound with `Alias`, which becomes a binding of its own: a direct binding of an aliased interface panics as a duplicate, and `Alias` accepts `credo.Override()` to point the interface at another type. A component whose binding's type hides its value's `Start`, `Ready` or `IngressTier` is refused, where the capability was skipped without a word; a borrowed binding is exempt, and a view of a resource whose holder of record plans the capability is accepted. A registration option a call does not accept is refused, naming the options it accepts ([dependency-injection guide](../guides/dependency-injection.md#interface-wiring-with-alias)).

`credo.Named` and `credo.Closer` are renamed `credo.ComponentName` and `credo.CloseOnShutdown`. `ComponentName` labels a component in logs, `/ready` and lifecycle errors, is not a DI key, and now also applies to `Provide` and `ProvideValue`.

## What each registration claims

A value handed in — a binding, or a value passed to `Manage` — is the holder of record of what it holds. A value a constructor builds — a constructor handed to `Manage`, or a worker's constructor — claims nothing: when it holds a resource a holder of record also holds, it adds no readiness entry and never runs the teardown, whatever the registration order. Registrations of one resource agree on its tier and on the options of its one readiness entry, or are refused, naming both. The dependency-injection guide gains a [table of what each registration form claims](../guides/dependency-injection.md#what-each-registration-form-claims).

## WebSocket and framework module logging

`credo.IngressComponent` lets a type declare its tier: a registration whose type implements it is planned in the ingress tier without `credo.Ingress()`, which stays accepted and redundant. `websocket.Server` implements it, so `app.Manage(ws)` is the whole registration. `websocket.New(cfg...)` takes no `Infra`: the server settles its logger in `Start`, from `Config.Logger`, else the App's, and refuses upgrades until then ([WebSocket guide](../guides/websocket.md#registering-the-server)).

`credo.InfraFrom(ctx)` returns the scoped `Infra` the App puts in the context of every call it makes on a component and of every `OnStart` and `OnStop` hook, so a framework module whose value is built outside the App logs through the App's logger. One key, `component`, names the application part — the binding's full type name, a `credo.ComponentName` name, or `worker:<name>` — and `module` names the framework package that writes the record (`module=websocket`, `module=sqldb`, `module=net/http`, `module=worker`). `sqldb.WithLogger(l)` gives the database a logger of its own, used unscoped.

## Workers in the root package

The `worker` package is deleted, with no aliases. `app.Workers()` returns the App's one registry, created on first use and not bound in DI, whose `Snapshot` and `Lookup` cover every worker of the App. A registration takes one of three forms: a worker value — a `credo.Worker` or a `func(context.Context) error`; a run function, whose parameters besides the context are resolved from the container after their components have started, so that the method expression `(*OutboxRelay).Run` registers a worker that stays a binding other code uses; or a constructor, which the start walk builds after its dependencies and which never becomes a binding. `ContinuousProvided` and `ScheduledProvided` go with the "one type under two names" rule they needed. The engine moves to `internal/worker`, and `internal/kernel` is deleted ([worker guide](../guides/worker.md#three-forms), [ADR-023](../adr/023-worker-system.md)).

## Rate limiting in `middleware/ratelimit`

`ratelimit.Middleware(cfg...)` is the one constructor, in its own package, so that importing `middleware` for `CORS` no longer links go-limiter. The rate limiter owns nothing the App must release or prepare, so it is no longer a component: `NewRateLimiter`, the `RateLimiter` type and its `Close` and `Shutdown` go. One returned value attached to several routes shares one store and spends one budget per key; a store passed in through `Config.Store` stays its owner's ([middleware spec](../specs/middleware.md)).

## Nested validation

A nil nested pointer, or nil interface, checked by `validation.Field(&r.Address)` with no rules is valid and its `Validate` is not called, as in ozzo-validation; it panicked when `Validate` read a field, and the request answered 500. A nested struct whose `Validate` has a pointer receiver is validated through the field's own pointer, so what `Validate` normalizes is kept, and the copy's allocation goes ([validation spec](../specs/validation.md)).

## What an application keeps

After the deletions, an application's composition root holds: a database bound, not registered — `app.ProvideValue(db)`; a WebSocket server handed over with `app.Manage(ws)`; workers registered through `app.Workers()`, as a value, a run function or a constructor; `Provide` with the constructor alone, and `Alias` for an interface; and `Finalize` only where an early check helps. The migration guide lists them under [What an application keeps](../guides/pre-v1-migration.md#what-an-application-keeps-v0250).

## Internal

- ADR-002 records the root package's module allowlist as a decision, and the rule that places a package: a subsystem the App holds one of and reaches through `app.` lives in the root package, a value the application builds and hands to the App lives in a package. ADR-004 records why DI stays in the root package and why DI and the lifecycle stay one package, `internal/di`.
- The ADRs and specs state the current design and nothing else; `docs/adr` and `docs/specs` gain an index each, the bootstrap lifecycle spec folds into the container and lifecycle specs, and the health spec is new.
- The root package's documentation is grouped by subject — DI, components, workers — while its symbol index stays alphabetical.
- `examples/saas` binds its opened store stand-in with `ProvideValue` and `credo.ComponentName`, hands the WebSocket server to `app.Manage(ws)` without an option and registers its worker through its constructor on `app.Workers()`.
- In DI and lifecycle messages a worker's units are named by its registration call, such as `Workers.Continuous("orphan")`.
- The CI lint build's `x/tools` override moves to v0.52.0, which reads Go 1.27.3 export data, and the CodeQL action moves to its current release.

## Unchanged

Routing, the middleware chain apart from rate limiting, the built-in HTTP features, the error envelope, binding, configuration loading, reload, TLS, `httpclient`, authentication and the `store/sqldb` query API are as in [v0.24.1](v0.24.1.md). The two-tier drain, resource identity, the worker's restart backoff, run outcomes, run timeouts and scheduling keep their v0.24 behavior under the new registration calls. The full list of changes is in the [CHANGELOG](../../CHANGELOG.md).
