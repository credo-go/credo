# Credo v0.14.0

Credo v0.14.0 restructures the default error envelope: the top level now
carries only the `success:false` discriminator, everything about the error
itself lives in a nested `error` object, and the validation/bind entry array
is renamed from `errors` to `violations`. This is a breaking wire change and
gets its own minor per Credo's pre-1.0 release policy. Credo remains Beta and
pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.14.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.14.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.14.0
go get github.com/credo-go/credo/store/sqldb@v0.14.0
```

Applications that do not use SQL only need the root module.

## Breaking: nested default error envelope

Before:

```json
{
  "success": false,
  "code": "validation_failed",
  "message": "Validation Failed",
  "errors": [
    {"field": "email", "code": "required", "message": "email is required"}
  ]
}
```

After:

```json
{
  "success": false,
  "error": {
    "code": "validation_failed",
    "message": "Validation Failed",
    "violations": [
      {"field": "email", "code": "required", "message": "email is required"}
    ]
  }
}
```

The flat shape mixed envelope-level (`success`) and error-level
(`code`/`message`) fields at one altitude. Nesting separates them and mirrors
a symmetric success envelope pairing `success` with a data payload: clients
read `success`, then take `data` or `error` as one unit, and the `error`
object can be passed around or extended without touching the top level.

Clients that parsed top-level `code`, `message`, `details`, or `errors` must
switch to `error.code`, `error.message`, `error.details`, and
`error.violations`. Applications that need the old flat shape during a
migration window can reproduce it with a custom shape-only `ErrorRenderer`:

```go
app.SetErrorRenderer(func(_ *credo.Context, info *credo.ErrorInfo) any {
    return map[string]any{
        "success": false,
        "code":    info.Code,
        "message": info.Message,
        "details": info.Details,
        "errors":  info.Violations,
    }
})
```

## Why `violations`, not `errors` or `fields`

The array carries two kinds of entries through one client contract:
field-scoped validation failures (`validation_failed`, 422) and
document-scoped bind failures (`bind_failed`, 400) whose `field` may be empty
when the violation concerns the whole body — a JSON syntax error, for
example. `fields` would misname the document-scoped entries, and
`error.errors` stutters. `violations` is honest for both: rule violations and
body-contract violations (compare Google AIP-193 `field_violations`). The
entry shape (`field`, `code`, `message`, `params`) is unchanged.

## Go API changes

- `ErrorResponse` now nests a new `ErrorBody` under its `Error` field instead
  of carrying flat `Code`/`Message`/`Details`/`Errors` fields.
- `ErrorInfo.Errors` is renamed to `ErrorInfo.Violations`. Custom
  `ErrorRenderer` implementations reading `info.Errors` must switch to
  `info.Violations`; the renderer contract is otherwise unchanged.

## RFC 9457 opt-in renderer

`RFC9457ErrorRenderer` keeps its Problem Details document shape (`type`,
`title`, `status`, `detail`, `instance` plus `code` and `details` extension
members), but its validation extension member is renamed from `errors` to
`violations` (`ProblemDetails.Violations`) so the extension vocabulary stays
consistent with the default envelope.

## Unchanged

Top-level codes (`validation_failed`, `bind_failed`) and their status
mapping, the violation entry shape, i18n message-key resolution and scopes,
deterministic encoding of framework-owned error bodies, HEAD/bodiless
handling, and the `ErrorRenderer` nil-keeps-default contract all carry over
as they are. `store/sqldb` participates in this release only through the
lockstep version bump.
