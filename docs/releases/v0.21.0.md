# Credo v0.21.0

Credo v0.21.0 has three changes. Continuous workers back off between restarts instead of restarting at a fixed rate, the managed start line lists the built-in HTTP features in effect, and static files whose names contain `%` are served again. The restart backoff compiles unchanged but behaves differently — read [Check this first](#check-this-first). The decisions are recorded in [ADR-023](../adr/023-worker-system.md#restart-backoff) and [ADR-010](../adr/010-middleware-architecture.md#startup-visibility-of-effective-features). Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.21.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.21.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.21.0
go get github.com/credo-go/credo/store/sqldb@v0.21.0
```

Applications that do not use SQL only need the root module. `store/sqldb` is unchanged apart from its root-module requirement.

## Check this first

**Continuous worker restarts back off.** Every restart used to wait the fixed restart delay, 3 s by default. A worker whose dependency stayed unreachable, and whose `Run` therefore failed immediately, restarted about 28,800 times a day, wrote as many Error lines and reconnected to the dependency at the same rate. The first restart still waits the restart delay; repeated failures now wait longer, with jitter, up to a one-minute cap — about 1,920 restarts a day once the cap is reached. This applies to workers registered without any restart option too.

| Before v0.21.0 | From v0.21.0 |
| --- | --- |
| every continuous restart waits the fixed restart delay (3 s by default) | the first restart waits the restart delay; repeated failures back off with jitter up to the cap (`DefaultMaxRestartDelay`, 1 min, or `worker.max_restart_delay`), and a run that lasted at least the cap resets the sequence |
| `WithMaxRestarts(N)` reaches `failed` after N fixed waits (15 s for N = 5 with the defaults) | the waits back off, so `failed` — and a `FailWhenFailed` readiness drop — comes later: roughly 48–93 s for N = 5 with the defaults |

To keep a fixed delay, set both options to the same value:

```go
worker.MustRegister(app, "poller", poller,
	worker.WithRestartDelay(10*time.Second),
	worker.WithMaxRestartDelay(10*time.Second),
)
```

A restart delay above one minute, per worker or per pool, also stays fixed unless a larger cap is configured. Scheduled workers are unchanged: their cadence is the schedule.

## Restart backoff

After a failed run for which a restart is planned, the k-th failure in a row waits a uniform pick from a window that doubles up to the cap:

```text
ceiling = min(base × 2^(k−1), cap)
delay   = uniform in [max(base, ceiling/2), ceiling]
```

| Failure in a row | Wait with the defaults |
| --- | --- |
| 1st | 3 s |
| 2nd | 3–6 s |
| 3rd | 6–12 s |
| 4th | 12–24 s |
| 5th | 24–48 s |
| 6th and later | 30–60 s |

- **Floor.** The first wait is exactly the restart delay, and no wait is shorter than it or longer than the cap. Full jitter could pick a near-zero wait and bring back the tight loop the restart delay exists to prevent.
- **Reset.** A run that lasted at least the cap resets the sequence, so a worker that runs for hours and fails once a day restarts after the restart delay, not after a minute. The reset affects only the wait; `Restarts` and the `WithMaxRestarts` budget keep counting.
- **Base.** `WithRestartDelay` → `worker.restart_delay` → `DefaultRestartDelay` (3 s), as before; it is now the first and the shortest wait.
- **Cap.** `WithMaxRestartDelay(d)` per worker, `worker.max_restart_delay` per pool, `DefaultMaxRestartDelay` (1 minute) otherwise. An omitted option takes the pool value or the default, raised to the worker's restart delay when that is longer. An explicit `WithMaxRestartDelay(0)` skips the pool value and selects `max(DefaultMaxRestartDelay, restart delay)`. An explicit positive cap below the restart delay, a negative value, or the option on a scheduled worker is a registration error.
- **Trade-off.** The cap also bounds the wait before the next attempt once a dependency is back. Raise it for dependencies that tend to stay down for long; lower it where a minute without the worker is too long.

The policy is visible without reading code. `Info.Config.MaxRestartDelay` (`max_restart_delay` in JSON; zero for scheduled workers) reports the effective cap next to `RestartDelay`, and the continuous `worker run failed` line carries `next_restart_in`, the selected wait, when a restart is planned. The attribute is omitted when the failure exhausted `WithMaxRestarts` and when shutdown was already observed.

```yaml
worker:
  restart_delay: "5s"
  max_restart_delay: "5m"
```

The [worker guide](../guides/worker.md#restart-backoff) walks through the waits and the fixed-delay recipe; the [worker spec](../specs/worker.md#restart-backoff) is the contract.

## Startup features

The managed start line, `credo: server started`, carries a `features` attribute listing the built-in HTTP features in effect:

```json
{"level":"INFO","msg":"credo: server started","label":"Run","addr":"127.0.0.1:8080","features":["recover","request_id","access_log","compress"]}
```

- The order is fixed: `recover`, `request_id`, `access_log`, `decompress`, `compress`, `i18n`, `error_renderer`, `success_renderer`, `health`.
- The list comes from the App's effective state after preparation, not from the registration calls: a `UseI18n` whose conventional discovery found no catalogs is not listed, and neither is a `UseHealth` that registered no probe route.
- A default App reports `["recover"]`. With every feature off the value is an empty array, never `null`, and the summary adds no Warn for features that are off.
- `Run`, `RunContext` and `ServeContext` write the line; an application that serves `app` from its own `http.Server` gets none.

This makes the v0.19.0 switch of RequestID and AccessLog to default-off visible at startup. The reliable check is still a request to an ordinary route whose response carries a request ID and produces an access record with the same ID ([HTTP features spec](../specs/http-features.md#startup-visibility)).

## Fixed: static files whose names contain `%`

Since v0.19.0 the router decodes every route parameter once, and `app.Static` decoded the captured path a second time:

| Request | Before | From v0.21.0 |
| --- | --- | --- |
| `/static/100%25.txt` | 400 | serves `100%.txt` |
| `/static/a%252Fb.txt` | served `a/b.txt` | serves a file literally named `a%2Fb.txt`, or 404 when there is none |
| `/static/%252e%252e/secret` | 400 | 404, as the static-files guide documents |

The `Browse` link for a file whose name contains `%` answered 400 the same way and now opens the file. Sanitization is unchanged — null bytes, backslashes and explicit `..` segments are still rejected with 400 — and no path ever escaped the served directory.

## Documentation

- The routing guide's new section [Route Parameters Are Not File Names](../guides/routing.md#route-parameters-are-not-file-names) warns that a decoded route parameter can contain `/` or `..`: a handler that opens files confines the access with `os.Root` or the `fs.FS` from `credo.DirFS`. The router spec states the boundary, and the canonical-form sentence is corrected: escapes of all RFC 3986 reserved characters and of `%` are kept.
- The worker guide, worker spec and ADR-023 state that cron schedules have no per-worker time zone: the process's local zone applies.

Worker registration, the other options, run timeouts, run-outcome classification, scheduled workers and readiness integration are as in [v0.20.1](v0.20.1.md). The full list of changes is in the [CHANGELOG](../../CHANGELOG.md).
