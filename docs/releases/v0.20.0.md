# Credo v0.20.0

Credo v0.20.0 is the **worker contract** release. The `worker` package gets the contract it will carry into v1: DI-provided workers, a snapshot that reports the effective configuration, one ordered classification of run outcomes, cooperative per-run timeouts, permanent continuous workers, and a fixed set of lifecycle log lines. The release is breaking, and one change compiles unchanged but behaves differently — read [Check this first](#check-this-first). Decisions and rejected alternatives are recorded in [ADR-023](../adr/023-worker-system.md); the [worker spec](../specs/worker.md) is the contract and the [worker guide](../guides/worker.md) shows the new calls. Credo remains Beta and pre-1.0.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.20.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.20.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.20.0
go get github.com/credo-go/credo/store/sqldb@v0.20.0
```

Applications that do not use SQL only need the root module.

## Check this first

**A continuous worker whose `Run` returns nil while the application is running is restarted.** Before v0.20.0 it stopped silently and permanently, and readiness never noticed. Now the early return is a failure: it is logged at Error as `worker run failed` with `unexpected_exit=true`, `LastError` reads `worker: Run returned nil before shutdown; a continuous worker must run until its context is cancelled`, and the worker is restarted after the restart delay (3 s by default) — indefinitely unless `WithMaxRestarts` is set, and marked failed once a positive limit is exhausted, which `ReadinessPolicy.FailWhenFailed` observes.

This compiles unchanged, so look for continuous workers that return nil on purpose before upgrading. Move finite work to `app.OnStart` when startup should wait for it, or end `Run` with `<-ctx.Done()` after the work when it should run in the background. Returning nil after the context is cancelled remains a graceful stop.

## Migration

| v0.19 and earlier | v0.20.0 |
| --- | --- |
| `worker.Register(app, w, opts...)` | `worker.Register(app, "name", w, opts...)` |
| `worker.Func("name", fn)` | `worker.Func(fn)`, name passed to `Register` |
| `Name() string` on worker types | delete (harmless if kept) |
| construct by hand before `Finalize` | `app.Provide[T](ctor)` + `worker.RegisterProvided[T](app, "name", opts...)` |
| **continuous `Run` returns nil → worker stops** | **restarted like a failure; end finite work with `<-ctx.Done()` or move it to `OnStart`** |
| `WithMaxRestarts(N)`, `N > 0` → `Failed` after N failures (N−1 restarts) | first run + N restarts → `Failed` after N+1 failures |
| `WithMaxRestarts(0)` → unlimited restarts | unchanged: unlimited restarts |
| `info.Schedule` | `info.Config.Schedule` |
| `info.Kind == "scheduled"` | still compiles; prefer `worker.KindScheduled` |
| `info.Attempts` | `info.Restarts` / `info.ConsecutiveFailures` |
| `worker.Attempt(ctx)` | removed; use `RunID`/`ScheduledAt`, and `Info` for counters |
| `LastSuccess` on continuous workers | never set |
| scheduled `Run` returns nil during shutdown → stamps `LastSuccess` and resets `ConsecutiveFailures` | when shutdown cancellation came first, graceful stop with both values unchanged; status becomes `Stopped` |
| a graceful stop clears `LastError` | a graceful stop changes only the status; `LastError` keeps the most recent failure until a successful scheduled run clears it |
| hand-rolled `context.WithTimeout` in `Run` | `worker.WithRunTimeout(d)`; a timed-out run is a failure even if it returns nil |
| `@every 0s` / negative / `1500ms` silently became 1 s | `Register` error |
| `LastError` may contain a stack trace | no stack; the stack is the `stack` log attribute |
| log `worker stopped during scheduled run` | `worker stopped` with `reason=shutdown` |
| log `worker tick skipped` (one per activation) | `worker ticks skipped` with `skipped=N` |
| log attribute `restart` on `worker run failed` (failed runs, `1` on the first failure) | `restarts` = `Info.Restarts` (started restarts, `0` on the first failure) |
| names silently trimmed | surrounding whitespace and control characters are rejected |
| untagged JSON field names from `pool.Workers()` | snake_case |
| `worker.Definition` (exported, returned by no API) | removed; `info.Config` is the public view of a registration |
| a continuous worker reported `Running` as soon as the pool started | `Idle` until its first run is admitted |

The [pre-v1 migration guide](../guides/pre-v1-migration.md#workers) carries the same table with more context.

## DI-provided workers

```go
app.MustProvide[*InvoiceWorker](NewInvoiceWorker) // func(credo.Infra, InvoiceRepository) *InvoiceWorker
worker.MustRegisterProvided[*InvoiceWorker](app, "invoice-worker",
	worker.WithSchedule("@every 1m"),
	worker.WithRunTimeout(15*time.Second),
)
```

`RegisterProvided[T]` records the type; `T` is resolved once when the pool starts, in the `OnStart` phase — after `Finalize`, before the server accepts traffic. It may come before or after the matching `Provide`, and `T` may be an interface bound with `Alias`. Start is all-or-nothing: a missing provider, a constructor error or panic, or a nil result fails startup with an error naming the worker and the type, and no worker runs. Workers constructed by hand keep using `Register` with a value.

## Run outcomes and timeouts

Every run is admitted in one step — cancellation check, then one commit of `running`, `LastRun` and (for a continuous restart) `Restarts` — so no run starts once shutdown has been observed. After the run, the outcome is classified in a fixed order: a panic is a failure; a run whose context was cancelled by its timeout is a failure; a nil or context-error return while the pool is stopping is a graceful stop; any other error is a failure; a scheduled nil return is a success; a continuous nil return while the application runs is a failure. The loop exit is decided only afterwards, so a timeout followed by shutdown is recorded as a timed-out run and a shutdown exit.

`worker.WithRunTimeout(d)` bounds every run of a scheduled worker, including the `WithStartImmediately` startup run, by cancelling the run context with the cause `worker.ErrRunTimeout`. A run cut short by its budget is a failure even if it returns nil — it can never stamp `LastSuccess` or open a `RequireFirstSuccess` barrier — and `errors.Is(context.Cause(ctx), worker.ErrRunTimeout)` inside `Run` tells the budget from a shutdown. The timeout is cooperative: at most one run per worker is ever active.

Recovered panics are recorded as `worker: run panicked: <value>`; the stack is the `stack` attribute of the failure log line and never appears in `Info.LastError` or readiness failure text.

## Snapshots and logs

`Pool.Workers()` returns `Info{Name, Kind, Config, Status, Restarts, ConsecutiveFailures, LastRun, LastSuccess, LastError}`. `Config` is the effective configuration — the restart delay after config and defaults, the run timeout, the limits, the schedule and a copy of the readiness policy — both before and after the pool starts, so a registration test can assert every worker's policy without running it. The JSON shape is snake_case, omits empty timestamps, errors and readiness, and encodes durations as integer nanoseconds.

Each worker writes exactly one `worker started` and one `worker stopped` line (`reason=shutdown` or `reason=failed`) at Info. Failure lines carry `run_id` — the value `worker.RunID(ctx)` returns inside the run — and `duration`, plus `timed_out`, `unexpected_exit` or `stack` when they apply. The continuous failure line's `restart` attribute is now `restarts` and equals `Info.Restarts`: restarts that actually started, so `0` on the first failure where it used to be `1`. Successful scheduled runs log `scheduled worker run completed` at Debug, and skipped activations are reported by one `worker ticks skipped` line per resumption.

## Fixed

- `WithMaxRestarts(N)` allowed only N−1 restarts; it now allows the first run plus N restarts, and `Restarts` counts only restarts that actually started.
- A scheduled run could start with an already cancelled context when the activation timer and shutdown were ready together.
- A continuous worker that returned nil early disappeared without a log line and stayed invisible to readiness.
- Exit logging depended on the exit path; the recommended `case <-ctx.Done(): return nil` logged nothing.
- `@every` silently turned zero, negative and sub-second durations into a one-second period; they are now registration errors.

## Unchanged

Routing, configuration, DI, validation, the error envelope, health probes and store contracts carry over as they are. `store/sqldb` participates in this release only through the lockstep version bump. Skip-only overlap, the `OnStart`/`OnDrain` lifecycle integration, the registration window, readiness policies and the `worker.restart_delay` configuration key keep their v0.19.0 behavior.
