# Credo v0.10.0

Credo v0.10.0 is the response-contract release: the success and error sides of the response-envelope pair now share one shape-only contract, machine-readable error codes and structured details become first-class RFC 7807 extension members, body-forbidding statuses (1xx/204/304) are handled correctly by every response helper, and a debug-mode diagnostic detects handlers that bypass the application's envelope. The project remains Beta and pre-1.0. **This release contains two breaking changes** — the `HTTPError.Code` → `Status` rename and the `SuccessRenderer` signature; both fail loudly at compile time and migration is mechanical.

The root module and Bun SQL wrapper are published in lockstep:

| Module | Version |
| --- | --- |
| `github.com/credo-go/credo` | `v0.10.0` |
| `github.com/credo-go/credo/store/sqldb` | `v0.10.0` |

## Requirements and installation

This release requires Go 1.27.

```sh
go get github.com/credo-go/credo@v0.10.0
go get github.com/credo-go/credo/store/sqldb@v0.10.0
```

Applications that do not use SQL only need the root module.

## Breaking: `HTTPError.Code` is renamed to `Status`; `Code` becomes the machine-readable string code

"Code" is what the industry's error envelopes call the machine-readable string identifier, so the HTTP status keeping that name would have forced the string code into an awkward synonym forever. The rename changes the field's type together with its name — code reading `.Code` as an int fails to compile, so nothing breaks silently ([ADR-009](../adr/009-handler-and-error-handling.md)):

```go
type HTTPError struct {
    Status     int    // was: Code int
    Code       string // NEW: machine-readable error code
    MessageKey string
    Details    any    // NEW: structured client-safe detail
    Internal   error
}
```

`NewHTTPError`, the sentinels, and the `HTTPStatus()` method are unchanged.

### Machine-readable codes and details on the wire

`ProblemDetails` gains `code` and `details` extension members (RFC 7807 explicitly permits them; both `omitempty`):

```json
{
    "type": "about:blank",
    "title": "user.email_exists",
    "status": 409,
    "code": "dup_email",
    "details": { "field": "email" }
}
```

- **Explicit:** `NewHTTPError(409, "user.email_exists").WithCode("dup_email").WithDetails(v)` — both builders are copy-on-write like `WithInternal`, so sentinels stay immutable.
- **Derived:** when `Code` is empty, the pipeline uses the message key's last dot-segment — `"user.email_exists"` → `"email_exists"`, built-in `"http.not_found"` → `"not_found"`. A dotless key is a literal human message and yields no code. What used to be a convention consumers reverse-engineered from `ErrorInfo.MessageKey` is now a framework guarantee.
- **Validation and binding:** validation failures carry `"code": "validation_failed"`; bind failures carry the decode reason (`"syntax"`, `"type_mismatch"`, …) as the top-level code, matching their `errors[]` entry.
- `ErrorInfo` deliberately gains no duplicate fields: renderers read `info.Problem.Code` / `info.Problem.Details`, keeping the classified `ProblemDetails` the single source of truth.

Default problem bodies for built-in keys now include `"code"` (e.g. every 404 carries `"not_found"`) — an additive, RFC 7807-conformant wire change.

### Migration

Replace `.Code` (int) reads with `.Status` or `HTTPStatus()`. That is all; the compiler finds every site.

## Breaking: `SuccessRenderer` is shape-only

v0.9.0 made `ErrorRenderer` shape-only; the success side kept the old write-it-yourself contract and the documentation had to explain the asymmetry. The pair is now symmetric ([ADR-009](../adr/009-handler-and-error-handling.md)):

```go
type RenderInfo struct {
    Status     int
    Data       any
    MessageKey string // via credo.RenderMessageKey(key)
    Meta       any    // via credo.RenderMeta(v)
}
type SuccessRenderer func(ctx *Context, info RenderInfo) any
```

- A **non-nil return** is the body, written by the framework with `info.Status` and the application JSON profile; the bodiless-status rule below applies centrally.
- **nil** writes `info.Data` plain — the escape for a renderer that envelopes selectively.
- A renderer that **commits the response itself** keeps full control; its return value is ignored. A renderer panic hits the built-in recovery layer like any handler panic.
- `Context.Render(status, data, opts...)` stays call-compatible and gains the two side channels every envelope eventually needs: `credo.RenderMessageKey("user.created")` (resolved by the renderer, typically via `ctx.T`) and `credo.RenderMeta(page)` for pagination-style metadata. With no renderer installed the side channels are silently dropped and `Render` remains plain JSON.

### Migration

Build the envelope and return it instead of writing:

```go
// before
app.SetSuccessRenderer(func(c *credo.Context, status int, data any) error {
    return c.Response().JSON(status, Envelope{Data: data})
})

// after
app.SetSuccessRenderer(func(c *credo.Context, info credo.RenderInfo) any {
    return Envelope{Data: info.Data}
})
```

A renderer that wrote a non-JSON response keeps its own write and returns nil after committing. Note the nil semantics: under the old contract `return nil` meant "done"; under the new one it means "write `Data` plain" — a renderer that committed the response is detected via the committed state, not the nil.

## Fixed: body-forbidding statuses are status-only

`Response.JSON(204, body)` used to commit the header and then fail inside net/http ("response status code does not allow body"), surfacing as a spurious `credo: error after response committed` warning — with a misleading `Content-Type: application/json` left on the bodiless response. Every body-writing helper (`JSON`, `Text`, `HTML`, `XML`, `Blob`, `Stream`) now treats RFC 9110's body-forbidding statuses — 1xx, 204, 304 — as status-only: body and Content-Type are skipped, the call returns nil, `Stream`'s reader is never read, and handler-set headers (ETag, Cache-Control on a 304) are preserved. Handlers no longer special-case 204 themselves.

## Added: envelope-bypass diagnostic

With a `SuccessRenderer` installed **and** debug mode on (`WithDebug()` / `server.debug`), a handler that writes a body-carrying JSON response through raw `Response.JSON` instead of `Render` triggers `WARN "credo: response bypassed the success envelope"` with the route pattern and name. It is a leak detector, not a rule — the raw helpers remain the documented escape hatch; deliberate raw endpoints silence it with the new `credo.MetaRawResponse` route meta (group-inheritable, route overrides group). Framework-internal writes and the non-JSON writers never trigger it; non-debug runs pay nothing.

## Upgrade notes

Applications using neither a custom `SuccessRenderer` nor `HTTPError.Code`-as-int compile unchanged. On the wire, default error bodies gain the `code` member and bodiless statuses lose their spurious `Content-Type` — both strictly corrective or additive.

The required test, race, real-database, lint, release-gate, examples, and CodeQL checks pass for the release candidate. An additional full-lint canary remains non-blocking while third-party analyzer IR support catches up with Go 1.27.
