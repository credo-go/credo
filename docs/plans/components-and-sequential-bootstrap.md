# Components, Kernel Registries and Sequential Bootstrap — Delivery Plan

**Status:** Decisions accepted 2026-10-07; W1 promotes them into the ADRs and specs; implementation pending. **Release:** v0.24.0. **Progress source:** [TODO.md](../../TODO.md#components-kernel-registries-and-sequential-bootstrap). This plan defines scope, sequence and acceptance; progress checkboxes live only in TODO. When the last work item has shipped, fold what remains into the ADRs and specs, repoint every link to this file, and delete it.

v0.24.0 gives the App one lifecycle abstraction and one ownership rule. Five teardown mechanisms — `OnPreDrain`, `OnDrain`, DI `Shutdowner`s, `OnShutdown` and the cancellation of the lifecycle context that goroutines launched from `OnStart` watch — become graph-ordered **components**, and three readiness paths become one aggregate. Framework infrastructure leaves the application's DI container for kernel-owned registries, and the container's public surface shrinks to seven methods and `Finalize`. Bootstrap is stated to be sequential, and the machinery that defended a concurrent bootstrap nobody promised is deleted. Workers attach as components. Four defects ship in the same release: a custom validation rule's error text reaching the client, `OnShutdown` running after DI teardown, `StatusHandler` accepting codes it never consults, and an explicit status losing to a wrapped validation error.

## Sequence

W0 is the first commit of `release/v0.24.0`. W1 lands before any code: it writes the decisions into the ADRs and specs, each promoted section marked pending until its work item ships, and adds the TODO section. The two acceptance scenarios of W4 are then written as failing tests. They are written against the accepted contract and build only under the tags `pending_w4` (the failed start) and `pending_w6` (the drain through a worker), so every commit stays green; the work item that makes a scenario pass removes its tag — W4 removes it from the shared helpers as well. The code follows the dependency order W2 → W4 → W5 → W6 → W3. The registration options act on components, so they land with W4; W3 deletes the DI methods that the framework's own registrations used, and each goes only after its last caller has moved — `testutil.WithOverride` in W4, `store.Register` in W5, the worker registry in W6 — so every commit builds. The work items keep their numbers, so that references to them stay stable. W7 and W8 touch separate code and may land at any point after W1; W9 closes the branch. Each work item is one or more theme commits, each green on its own; the branch ends with the release preparation commit and becomes one pull request, rebase-merged after review and the required checks, and the `Release` workflow tags the preparation commit ([CONTRIBUTING](../../CONTRIBUTING.md#releasing)).

**Messages.** An error message is part of the API. Every error and panic this release adds names what failed — the component, binding or call — the phase, and the remedy: a missing dependency with its path, an internal component with the ingress path it depends on and both fixes, `ServeHTTP`'s refusal with `App.Start` and the `testutil` helper, a misused option with the call that misused it, two values of one resource that disagree on its owner or on its teardown, with both bindings and the remedies, a failed start with each component's phase and outcome. Each test that triggers one asserts those parts of its message, so a message changes only on purpose.

Every commit runs `go vet`, the shadow analyzer, `gofmt` and `go test -race` over all packages except the ignored `tmp/` tree. Commits that change the lifecycle also run the root package's lifecycle tests with `-race -count=20`, and worker commits run `go test ./worker/... -race -count=20`.

## W0: the flaky header-limit test

**Change.** `TestMaxHeaderValueCount_RejectsAndStaysSilent` (`httpserver_test.go`) asserts that the captured log contains no `431`, but the log carries the listener's address, and an ephemeral port can contain those digits — port 43163 stopped the v0.23.0 release gate — as can a timestamp's milliseconds. Remove every network address (`host:port`) and the `time` attribute from the captured text before matching, keeping the assertion that net/http's 431 rejection reaches no log record; the matching moves into a small helper.

**Test.** The helper is checked against the line that stopped the gate: a log carrying the address `127.0.0.1:43163`, `[::1]:43163` or a timestamp ending in `.431` passes, and one carrying a 431 status line, a `status=431` attribute or "too large" fails.

**Promotion.** Each decision is written into its canonical ADR and its detailed spec (the contract map), with a pending marker naming v0.24.0 that the implementing work item removes:

a teardown-function option; promising that a component is constructed only after its dependencies have started; a value with no edges that resolves its dependencies in `Start`; a `Start` that blocks for the component's lifetime; ## W2: sequential bootstrap and the three error phases

**Change.**

- The root states the contract in `doc.go`, ADR-022 and the bootstrap spec: registration calls come from the goroutine that builds the App, before it runs, and are not safe for concurrent use. The documented order names every satellite: configuration → `Provide` → feature mounts and satellite registrations, in any order among themselves (`UseI18n`, `UseHealth`, workers, stores, `Manage`) → `Finalize` → `Resolve`, routes and anything built from a resolved value, a readiness check included → `Run`. There is no resolve-then-provide step: a value that needs a resolved dependency and I/O to exist is a component whose `Start` does that work. `credo.New()`, routes and `Run()` stay the minimal shape.
- Three error phases extend `doc.go`'s "Panics and Errors": registration performs no I/O and panics on misuse known at the call site; `Finalize` returns what only the whole graph reveals — missing dependencies, cycles and, with W4, an internal component that depends on an ingress one — joined in registration order; `Start` returns I/O errors.
- Consequently `Provide`, `ProvideValue`, `Alias` and `BindMany` panic on misuse and return nothing, and `Resolve` before `Finalize` panics instead of returning a "not finalized" error. A DI or component registration — `Manage` and the worker registrations included — after `Finalize` panics, as does any registration after the App is prepared or shut down, each with the call site's message.
- A missing dependency is reported with its whole path, for example `OrderService → PaymentClient → *http.Client (not registered)`.
- The concurrent-registration machinery goes: `installFeature`'s double check around `prepMu` and the container's freeze flags as public states here; `CanProvideValue`, `AdoptValue`, `registrationProbe`, `ensurePool`/`adoptPool`, `ensureRegistry`/`adoptRegistry` and `store.Register`'s reservation with W3, W5 and W6.
- Unchanged: after `Finalize`, `Resolve` stays safe for concurrent use — first resolutions of one singleton share one construction, and a resolution that races the drain returns an error wrapping `ErrDIClosed`. The one-time preparation that concurrent first `ServeHTTP` calls share stays synchronized; it belongs to the running App, not to registration.

**Tests.**

- A table of registration misuse, each panicking with the call site's message: a constructor of the wrong shape, a duplicate binding, `Resolve` before `Finalize`, each DI and component registration after `Finalize`, and each registration after shutdown.
- `Finalize` with two missing dependencies and a cycle returns all three, in registration order, each missing dependency with its full path.
- The documented order, every satellite included, as an `Example` that runs.
- The concurrent-resolution tests keep passing under `-race`; tests of concurrent registration are deleted, not loosened.

**Documentation.** ADR-022, the bootstrap spec and `doc.go` flip; the getting-started and dependency-injection guides print the order. Migration rows: registration calls return no error and panic on misuse; `Resolve` before `Finalize` panics; bootstrap is sequential.

## W3: the DI surface

W3 lands last, after W6: each method it deletes goes once its last caller has moved.

**Change.**

- The container's public surface is `Provide`, `ProvideValue`, `Alias`, `BindMany`, `Has`, `Resolve` and `ResolveAll`, plus `Finalize`. `Has` stays as the one non-resolving presence probe — "is the optional module present?" is a composition-root question with no other answer. `MustResolve` stays until the pre-v1 pruning judges it.
- Deleted: `ProvideProtectedValue`, `ProtectBinding`, `AdoptValue`, `CanProvideValue`, `Replace` and `MustReplace` with the superseded-instance warning, and the `Must*` twins of the registration calls. Nothing framework-owned lives in the container any more (W5, W6), so nothing needs protecting, and what protection guaranteed — that no integration keeps monitoring one value while DI resolves another — holds by construction: a component is its binding (W4), and the store registry names a binding, not a value (W5).

**Tests.** `Has` reports presence without constructing. The tests of the deleted methods are deleted with them, not rewritten against something else.

**Documentation.** ADR-004's surface and the container spec's surface flip. Migration rows: each deleted method with its replacement — `Replace` becomes `credo.Override()` or `testutil.WithOverride` (W4), protected bindings have no successor because nothing framework-owned is bound, and a `Must*` registration twin becomes the plain call, which panics on misuse (W2).

## W4: lifecycle components and the registration options

The contract is ADR-024 and the lifecycle spec; this section lists what the code must do.

**Change.**

- **The type.** `type Component interface { Shutdown(ctx context.Context) error }` replaces `Shutdowner` with the same method set, so every `Shutdowner` is a component without a change. `Component` never gains a method; it grows only through optional capabilities, each with a small exported interface — `Starter` for `Start(ctx) error`, one for `Ready(ctx) error` and one for `ResourceIdentity() any`, the capability `store`'s `LifecycleIdentityProvider` becomes (Registration), whose names ADR-024 settles. `Start`, `Ready` and the tier are planned once, at registration, from the binding's type, and an absent capability has a documented default; the teardown follows the value the App owns (Registration). A capability added after v1 takes a Credo-owned type in its signature, so no method an application already has matches it by accident; a richer report is a typed error, not a second method.
- **Registration.** A DI singleton the App owns is a component when it has `Shutdown` — its binding's type shows the method at registration, or its value has it once built — because ownership, not the view its consumers take, decides the teardown, as the container decides it today (`internal/di/shutdown.go`). `Start`, `Ready` and the tier are planned from the binding's type, since the start walk is planned before any constructor runs: a `Start` or `Ready` that only the value has is neither called nor asked, while a value the App owns is still shut down — releasing is the owner's obligation, starting a capability the binding shows — and a type that has only `Start` is not a component, so it is never started. A value behind an interface that an `OnStart` hook starts today therefore keeps working, and the App never starts it a second time; to have the App start or ask a value, provide the concrete type and `Alias` the interface the application uses. A component found only on its built value is internal, and one that depends on an ingress component fails its construction with `Finalize`'s path and remedies, since `Finalize` cannot see it. `app.Manage(v, opts...)` adds a value, or a constructor over DI parameters that the start walk builds and that never becomes a binding, with `credo.Named("…")` — defaulting to the type name, a duplicate panics — and `credo.Ingress()`. The registry keys components by resource identity within one App: the token a value's `ResourceIdentity()` returns — `*sqldb.DB` returns itself, and a wrapper that embeds it inherits the method — otherwise the value itself when it is comparable, a pointer or a struct over one, and otherwise its binding alone. One resource has one teardown: the values that share an identity — one pointer under several bindings, the interface view an adapter constructor returns, a wrapper and the handle it embeds, two wrappers over one handle, a value that a constructor returns after `Manage` received it — are shut down once, when the last holder retires, so the consumers of every holder stop first. Today's container calls `Shutdown` once per holder, the first time while consumers of another holder may still run. The application chooses that teardown, not the order of construction: the holders that have one agree on its kind — `Shutdown`, or `Close` through `credo.Closer()` — and a disagreement panics at the later `ProvideValue` call when both values are given, and otherwise fails the construction of the holder built later, naming both bindings and both remedies: drop `credo.Closer()`, or bind the holder that has `Shutdown` under a type that shows `Close` and not `Shutdown`, with `credo.Closer()`. Among holders of one kind, the one registered first runs it, whichever is built first. Kinds are all the registry can compare — Go does not tell a `Shutdown` that a wrapper inherits from one it declares — so the choice rests on a contract: only a value without state of its own to release may share an identity. A wrapper that embeds a handle which identifies itself inherits that identity, so one that releases state of its own holds the handle in a named field instead, and a wrapper that forwards an identity promises that it keeps none. A holder without a teardown takes no part in the choice, and the resource still waits for its consumers. A `ResourceIdentity()` that panics or returns a token that is nil, not comparable or not equal to itself panics at the call for `ProvideValue` and `Manage` and fails a constructor's construction. `Manage` of a value whose resource a `ProvideValue` binding holds panics, and so does a resource handed to `Manage` twice. A borrowed resource is torn down through none of its holders: a holder that claims the teardown — a component bound with `ProvideValue`, a value handed to `Manage`, a binding with `credo.Closer()` — disagrees with `credo.Borrowed()` on the owner and panics at the later call or fails its construction, while a value that a constructor builds over a borrowed resource without `credo.Closer()` stays the caller's even when it has `Shutdown`, since a `Shutdown` found on a value is no claim. The root exports `credo.Tier` with `TierIngress` and `TierInternal` for configuration fields and reports.
- **Registration options.** `Provide` and `ProvideValue` take registration options, each checked at the call; misuse panics:
  - `credo.Ingress()` places a component in the ingress tier. It panics on a binding that is not a component at registration — whose type shows no `Shutdown` and that carries no `credo.Closer()` — since the tier is planned before the value exists.
  - `credo.Borrowed()`, on `ProvideValue` only, keeps the binding and the value's readiness contribution and leaves starting and shutting it down to the caller — for a pool that two Apps in one process share, or a fixture a test suite reuses across the Apps it builds. It is accepted on a binding whose type does not show `Shutdown`: that is how a caller keeps the teardown of a value that has the method behind an interface.
  - `credo.Closer()` makes a binding whose type has a `Close` method — `Close() error`, `Close()` or `Close(ctx) error`, the last receiving the drain deadline — a component the App closes after its consumers, abandoned at the deadline like any shutdown. It panics on a type with none of the three, on a type that is already a component, and beside `credo.Borrowed()`. It decides its binding's teardown: a built value that also has `Shutdown` is closed once, with `Close`, and a holder of the same resource whose teardown is `Shutdown` is refused (Registration). `Close` is never discovered on its own: the method is too common to mean that the App owns the value.
  - `credo.Override()` replaces an earlier binding of the same type before `Finalize` and panics when there is none, so an override that no longer matches the wiring fails instead of adding a binding nothing resolves.
- A teardown that is not a `Close` — a client's `Disconnect(ctx)`, a `Drain` that must be waited for — belongs to a type that embeds the client and implements `Shutdown`, registered as the binding itself; its constructor's parameters give the teardown's own dependencies their edges. There is no teardown-function option: Go cannot tie its type parameter to `Provide`'s at compile time, and the function's own dependencies would have no edges. A constructor returning `(T, func(context.Context) error, error)` is deferred until a type proves costly to wrap; adding it later breaks nothing, because a three-value constructor is rejected today.
- `testutil.WithOverride[T]` builds on `credo.Override()` and becomes strict: without an earlier binding of `T` it panics. Adding a binding is `WithWiring`'s job.
- **Hooks.** `OnStart(fn, opts...)` and `OnStop(fn, opts...)` are anonymous components of a tier, internal unless `credo.Ingress()` says otherwise. Start hooks run FIFO after the tier's components have started; stop hooks run LIFO before they stop. A hook is a leaf action: anything with its own teardown is a component, and process-level cleanup that must outlive every component belongs after `Run` returns. `OnPreDrain`, `OnDrain` and `OnShutdown` are deleted. A shutdown hook's slot moves from after DI teardown to before its tier's components, and the new name makes that move a compile error rather than a silent change.
- **Start.** The internal tier starts in dependency order, then the ingress tier, then the listener accepts. A component with `Start` or `Ready` that is still unbuilt is built by the start phase, and a constructor error there is a start failure; a component with neither stays lazy and is shut down only if built. `Start` returns once the component is usable and never blocks for its lifetime, and Credo cancels its context when it returns: work that outlives the call runs on a goroutine whose context derives from `context.WithoutCancel(ctx)` with its own cancel, which `Shutdown` calls. `OnStart` receives the same call-scoped context. A failure after `Start` has returned is reported through `Ready`; no component ends the App, except the App's own listeners. That is a deliberate policy, not a recovery guarantee: a failing readiness probe takes the instance out of rotation and restarts nothing, so a component that has stopped for good leaves the process alive, unready and never restarted. An application that wants a restart ties a liveness check to the component itself, knowing that one failing because of a shared dependency restarts every replica; ADR-024 and the deployment guide state both, and no fatal-error API is added.
- **A failed start** stops, in reverse dependency order, every component that was built — one that never started included — except the one whose `Start` failed, which has released what it opened. A `Start` that panics is reported, and the rollback continues.
- **A shutdown requested during the start phase** — the first signal in `Run`, the context of `RunContext` or `ServeContext`, or `Shutdown`, which is now accepted while the App is starting and waits for the rollback within its own context — cancels the running `Start`, starts nothing further and rolls back under the drain deadline counted from the request. A `Start` that ignores the cancellation is abandoned like a `Shutdown` that misses the deadline. `Run` returns nil after a clean rollback and logs the interrupted `Start`'s error; "server started" is never logged, and the listener never accepts.
- **Shutdown.** The ingress tier stops first, concurrently with the HTTP drain, and its components that no edge orders stop concurrently with each other. The internal tier then stops in reverse dependency order — the Kahn order of `internal/di/shutdown.go` — with values that have no edges in reverse registration order. No dependency crosses the tiers backwards: a component of the internal tier that depends on one of the ingress tier, directly or through bindings that are not components, fails `Finalize` with the path and both remedies — declare the dependent ingress, or split the ingress component so that what internal components use is an internal part — so the dependency order holds for every component, and the tiers order only components that no dependency path connects. One drain deadline serves both tiers and is spent in order, so a long HTTP drain leaves less for what follows; the spec states that cost. A `Shutdown` that misses it is abandoned: its dependencies are not stopped, and every component it kept open is reported. A `Shutdown` that returns an error promptly is reported, and its dependencies are still stopped. Every `Start` and `Shutdown` is panic-isolated. A construction still running when the drain reaches it blocks its dependencies and is shut down in order when it completes; one that completes after the drain deadline gets today's single bounded late attempt, logged and not reported — for a component its binding's type shows and for one found only on its built value alike.
- **One error.** `Run` reports a start or shutdown failure as one error naming each component, its phase and its outcome — failed, panicked, abandoned at the deadline. It generalizes `*DIShutdownError`, an immutable per-component snapshot with `Unwrap() []error`; ADR-024 settles its name.
- **Readiness.** `/ready` aggregates the `Ready` capabilities under the components' names, and the application's checks, with no DI resolution per request.
- **Every way of serving starts the components.** `App.Start(ctx)` prepares the App and runs the start walk without a listener, for an App served through `ServeHTTP` by an external `http.Server` or in a test; `App.Shutdown` stops what it started. `testutil` gains a helper that starts the App and leaves its shutdown to the end of the test: an App built by `NewApp` already registers that cleanup first, so it runs after every cleanup the test adds later, and the helper adds none; any other App gets one when it starts, so its test server is created after the helper or closed with `defer`, as the godoc says. An App that has anything to start — a component with `Start` or `Ready`, a start hook, a store registration, i18n catalogs — refuses to serve until the start phase has completed successfully: before `App.Start` is called or while it runs, `ServeHTTP` panics with a message naming `App.Start` and the helper, as it does today for a stored preparation error, so a handler never runs against dependencies that were not started. A failed `App.Start` rolls back, drains and leaves the App stopped, as a failed `OnStart` hook does today, and a stopped App answers with the 503 envelope without touching DI, since the caller already has the error; a preparation error still panics on every request. `App.Start` is accepted only while the App is building: a second `App.Start`, or `Run`, `RunContext` or `ServeContext` after it, returns the state error, since the App is single-use. An App with nothing to start serves through `ServeHTTP` as before. Whoever serves the App through `ServeHTTP` owns that server's admission and drain and completes them before `App.Shutdown`, as the godocs of `ServeHTTP` and `App.Shutdown` already say: the internal tier stops after the HTTP drain only if that drain has happened, so `App.Start`'s godoc, the lifecycle spec and the deployment guide state the rule beside the order it protects. `App.Start`'s godoc opens with "Start runs the start phase without a listener; Run, RunContext and ServeContext serve.", because `Start(addr)` listens in other frameworks. `*App` already has `Shutdown(ctx) error`, so `Start` makes it a startable component: an App mounted into another with `Mount` is handed to `parent.Manage(child)`, starts in the parent's start walk before the listener accepts, and stops after the parent's HTTP drain — the internal default is the right tier, since that drain first finishes the requests that run the child's handlers. That is also how a mounted child meets the `ServeHTTP` rule and the owner's drain, the parent's server being the owner.
- Godoc that uses "component" loosely — `NewInfra` and `HealthChecker` — is reworded, so the word names only this abstraction. The log attribute `component` stays: it names the subsystem that logs, and log queries depend on it.

**Tests.** The two acceptance scenarios come first, as failing tests:

1. The last job an HTTP handler hands to a worker before the drain reaches the database: a handler enqueues to an in-process continuous worker that writes through a database component; a request accepted just before shutdown completes, its job is written, and the database shuts down after the worker.
2. A failed start stops exactly the components that were built, except the one whose `Start` failed.

Then:

- start and stop orders across both tiers with edges; ingress components without edges stop concurrently, each blocking until the other has begun; an internal component that depends on an ingress one, directly and through a binding that is not a component, fails `Finalize` with the path, and an ingress component that depends on an internal one starts after it and stops before it;
- the start-phase shutdown matrix — a signal, a cancelled `RunContext` context and `Shutdown`, each at every position of a three-component start: the running `Start`'s context is cancelled, nothing further starts, the rollback stops what was built, `Run` returns nil, no start line is written and a dial to the listener is refused; a `Start` that ignores the cancellation is abandoned at the deadline and reported;
- the contexts of `Start` and `OnStart` are cancelled when they return;
- an abandoned `Shutdown` keeps its dependencies open, and the error names it and every component it kept open;
- panics in `Start` and `Shutdown` are isolated and reported;

## W5: stores, health, WebSocket and i18n on the kernel

**Change.**

- **Stores.** `store.Register` stops binding into the container and names a binding instead of taking a value: `store.Register[R store.Lifecycle](app, opts...)`. The application binds the store — `ProvideValue`, or `Provide` with a constructor — where ownership is decided, `credo.Borrowed()` for a handle it shares, and `store.Register` adds `R` to the kernel's store registry with its name. The start phase resolves `R` once, after `Finalize` and therefore after every override, pings that value as `R`'s start step, before its consumers start — a failed ping is a start failure — and keeps it for `/ready`, which reports its typed health without resolving anything per request. The registry's store is thus the value DI hands its consumers, in tests too: an override of `R` is what gets pinged, reported and shut down, which keeps the guarantee protected bindings gave by forbidding the override. A registration whose `R` has no binding fails `Finalize`, and an `R` that does not implement `Lifecycle` does not compile. A store therefore takes two calls where it took one, each with one job, and registration does no I/O. `store.Register` returns nothing and panics on misuse. `WithCallerOwnedLifecycle`, `WithLifecycle`, the reservation and the `Registry` type with its DI binding are deleted: `Registry`'s one public method, `HealthAll`, reports what `/ready` reports, and an application that needs one store's health calls the value's own `Health`. `LifecycleIdentityProvider` becomes the root's identity capability (W4), and `*sqldb.DB` keeps returning itself from `ResourceIdentity()`, so a wrapper that embeds it stays one resource with it: the identity check the reservation made becomes the component registry's teardown rule and keeps its refusal of mixed ownership. Two registrations of one resource are no longer refused — each is pinged and reported, and the resource is still shut down once. A separate health handle passed as a value would drift from an override the same way, so a value that does not implement `Lifecycle` is registered through a wrapper type that does — the rule W4 gives a teardown that is not a `Close`. The registry is reached through an internal seam between the root and `store`, not through the container.
- **Health.** `/ready` reads the kernel's registries — the components' `Ready`, the store registry — and the application's checks. The `internalhealth` `StoreFunc` and `ReadinessFunc` seams and their per-request DI resolution are deleted. During the drain `/ready` returns 503 `shutting_down` as today.
- **WebSocket.** `websocket.Use` becomes `websocket.New(infra credo.Infra, cfg ...Config) *Server`: it validates the configuration, builds the server and registers nothing — `Use` names a call that attaches to the App, and this one no longer does, while today's took the App only for its logger, which `credo.Infra` carries. The server adds today's `module` attribute to the logger it is given, so log queries do not change. `worker.Use` keeps its name, because the `Supervisor` it returns registers each worker as a component of that App (W6). The application registers the server as an ingress component — `app.Manage(websocket.New(app.NewInfra("websocket"), cfg), credo.Ingress())`, or, when controllers take it as a dependency, a binding with `credo.Ingress()`: `ProvideValue`, or `Provide` with a constructor over `credo.Infra`. An internal component that depends on the server fails `Finalize` (W4): a consumer that broadcasts depends on the application's own connection registry, which the server's handlers fill and its drain empties. The server's `Start` derives its context from `context.WithoutCancel`; its `Shutdown` is today's drain. A server that was never started refuses upgrades with an error naming the missing registration, so a forgotten registration fails at the first upgrade instead of silently skipping the drain.
- **i18n.** `UseI18n` returns nothing and panics on misuse, like every other `Use*`; its catalogs are read in the start phase, and a read failure is a start failure.
- **The rate limiter.** `RateLimit`'s godoc and the middleware package doc point a caller who releases a `RateLimiter`'s store to `app.Manage(limiter)` instead of `OnShutdown`.

**Tests.**

- A bound and registered store is pinged at start — a failing ping fails the start and rolls back — reported by `/ready` with its typed health, and shut down after its consumers; a borrowed store is pinged and reported but never shut down; a store whose binding a test overrides is pinged, reported and shut down as the override, and the original value is never pinged; a store bound through a constructor is built by the start phase; a registration whose type has no binding fails `Finalize` with a message naming the type and `store.Register`.
- A `*sqldb.DB` bound raw and through a wrapper that embeds it, or through two wrapper types, is shut down once, after the consumers of every binding; two store registrations of it are each pinged and reported.
- `/ready` resolves nothing from the container per request and returns 503 `shutting_down` during the drain.
- A WebSocket server drains in the ingress tier, concurrently with the HTTP drain; a server never registered refuses an upgrade with the named error; a server bound with `ProvideValue` and `credo.Ingress()` is one component.
- An internal consumer that broadcasts through an application-owned connection registry finds no peers after the WebSocket drain for what it still sends, and stops before the registry.
- A missing i18n catalog directory fails the start, not registration; `UseI18n` misuse panics.

**Documentation.** ADR-013, ADR-015, ADR-016, ADR-019 and the store, WebSocket and i18n specs flip; the data-access guide, whose multiple-databases section is rewritten for the two calls — a wrapper type per database beyond a default `*sqldb.DB`, bound once and registered by its type; an interface view through `Alias`; the raw handle unwrapped inside the constructor that needs it rather than bound again; a generic repository instantiated per wrapper; and one collection type that owns the databases whose number comes from configuration — and the WebSocket and localization guides. Migration rows: the store binding the application now writes and `store.Register[R]` without a value; a store value without `Lifecycle` behind a wrapper type that implements it, since `WithLifecycle` is deleted; a named-field wrapper's `store.LifecycleIdentityProvider` becoming the root's identity capability, with the same method; `websocket.Use` becoming `websocket.New`, with the registration the application writes; `UseI18n` without an error.

## W6: workers as components

**Change.** ADR-023 and the worker spec, rewritten in W1, are the contract:

- `worker.Use(app)` returns a `*Supervisor` (was `Pool`): a registry and reporting object with no `Start`, no `Shutdown`, no hooks and no DI binding. Each registration adds one component, named `worker:<name>`, whose `Start` launches the loop, whose `Shutdown` cancels the worker's own context and returns when `Run` has returned, and whose `Ready` reports the worker's readiness conditions.
- The registration method chooses the kind: `Continuous(name, w, cfg...)`, `Scheduled(name, expr, w, cfg...)`, and the DI-provided `ContinuousProvided[T](name, cfg...)` and `ScheduledProvided[T](name, expr, cfg...)`, which add a constructor over `T`, so the worker starts after `T`'s component dependencies and stops before them. One `T` under two names panics.
- Per-kind configuration, zero meaning the default: `ContinuousConfig{Tier, Restart, UnreadyWhenFailed}` and `ScheduledConfig{Tier, RunOnStart, RunTimeout, MaxConsecutiveFailures, UnreadyWhenFailed, UnreadyUntilFirstSuccess, UnreadyAfterSuccessAge}`; each method takes its configuration variadically, and more than one panics. `Restart{Disabled, Limit, MinDelay, MaxDelay}`: `MinDelay` defaults to 3 s; a zero `MaxDelay` resolves to the larger of one minute and `MinDelay`; a positive `MaxDelay` below the resolved `MinDelay` panics, and so does `Disabled` beside any other field. The tier defaults to ingress for a scheduled worker and to internal for a continuous one. The `worker` configuration section, the functional options, the presence flags and the cross-kind validation are deleted.
- `Snapshot() []Info` and `Lookup(name) (Info, bool)`. `Info` holds `Continuous` or `Scheduled` — the resolved configuration — and `Schedule`, with flat live state and `LastStartedAt`/`LastSucceededAt`; the statuses are `pending`, `running`, `backoff`, `waiting`, `stopped` and `failed`.
- One log vocabulary: `worker started`, `worker run failed` for both kinds with `kind`, `worker run completed`, `worker activations skipped`, a single terminal `worker failed` with `reason` (`restart_limit`, `restart_disabled`, `failure_limit`, `schedule_exhausted`), and `worker stopped`.
- `worker.CurrentRun(ctx) (RunInfo, bool)` replaces `RunID`, `WorkerName` and `ScheduledAt`.
- Registration misuse panics, and the `Must*` twins go; `ParseSchedule` stays for configuration-supplied expressions.
- Unchanged: `Worker`, `Func`, the loop, the outcome classifier, restart backoff's shape, serial skip-only scheduled runs, and cooperative run timeouts with `ErrRunTimeout`.

**Tests.** The spec's tables rewritten for the configurations; the resolution of `Restart`; golden JSON for `Info`; the log vocabulary per event; the two timing changes — a continuous worker's context is cancelled in its tier's turn, after the HTTP drain for the internal default (acceptance scenario 1), and a `Run` that ignores cancellation past the deadline keeps its dependencies open and makes `Run` return the error.

**Documentation.** The worker guide is rewritten, adding that a continuous `Run` must be re-enterable, that every replica runs every schedule, how to report a cancelled client call at shutdown without masking a real error, how to escalate a terminal failure through a liveness check built on `Lookup`, and that a worker registered by value has no edges and stops in registration order, so one that uses infrastructure is registered in its provided form. The migration section carries the naming table and puts first the changes that compile: the removed configuration section, the snapshot's JSON fields and statuses, the log messages, panicking registration, and the two timing changes.

## W7: rule errors are internal; an explicit status wins

**Change.**

- A validation rule that wants a client-visible message returns a `*ValidationError`, or builds one with its small constructor. Any other error is internal: validation stops, and the error leaves `Validate` as it would leave a handler, so the error pipeline classifies it — a plain error is a 500 whose text is logged, not rendered, and a fault keeps its mapped status, `store`'s unavailable kind a 503. Rendering such an error as a generic 422 violation was rejected: it tells the client its input was wrong when the server failed, and a client that trusts the status does not retry. `By`'s example returns a `*ValidationError`.
- An explicitly constructed `HTTPError` wins over a validation error wrapped inside it: `NewHTTPError(409, "tenant_conflict").WithInternal(vErrs)` renders 409.
- Both are the error model's final rules, so they do not change again when the rest of that work lands.

**Tests.** A `By` rule returning `errors.New("pq: connection refused")` yields 500 with the default envelope and the text only in the log; one returning a `*ValidationError` yields 422 with its message; a `store` unavailable error inside a rule yields 503; the explicit 409 wrapping validation errors renders 409; an unwrapped validation error still renders 422 `validation_failed`.

**Documentation.** ADR-011, ADR-009, the validation spec and the error-handling guide flip. Both migration rows come first among the behavior changes, because they compile unchanged.

## W8: `StatusHandler` refuses the codes it never consults

**Change.** `StatusHandler(code, h)` panics at registration for any code but 404 and 405: only those are looked up, and a 5xx handler would re-enter application code inside error rendering.

**Tests.** 404 and 405 register and are consulted; 403, 500 and any other code panic with a message naming the two supported codes.

**Documentation.** ADR-007 and the router spec flip. Migration note: the panic turns a silent no-op into a startup failure, so a registration for any other code — 403 is the likely one — is deleted rather than ported; a 404 or 405 handler that only returns the matching sentinel (`ErrNotFound`, `ErrMethodNotAllowed`) equals the default and can go in the same change.

## W9: examples, guides and the release

**Change.** Every example migrates and runs (`go run .`, not only build and vet); `examples/saas` shows the documented bootstrap order with every satellite in it. The getting-started, dependency-injection, deployment, data-access, WebSocket, worker, localization and error-handling guides, README's API summary, and the migration guide's v0.24.0 section are brought up to date.
