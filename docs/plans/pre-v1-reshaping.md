# Pre-v1 Reshaping — Delivery Plan

**Status:** Decisions accepted 2026-10-13, R13 and R14 on 2026-10-25, R10's and R12's open points on 2026-10-26, the revised R9 and R13 on 2026-11-07, and R15 and the additions to R2, R4, R8, R12 and R13 on 2026-11-08, and R15's two open points and the additions to R2, R12 and R14 on 2026-11-09; R1 promotes them into the ADRs and specs; implementation pending. **Release:** v0.26.0 and the minors after it, before v1.0.0. **Progress source:** [TODO.md](../../TODO.md#pre-v1-reshaping). This plan defines scope, sequence and acceptance; progress checkboxes live only in TODO. When the last work item has shipped, fold what remains into the ADRs and specs, repoint every link to this file, and delete it.

Before v1 freezes the public surface, the reshaping changes the signatures and the normative behaviour that v1 would otherwise freeze in a shape that should not last. An error's status reaches the client through one channel, a service names an error code of its own without naming a status, and a message key is a catalog key, never rendered as text and never carrying client input. Configuration decodes strictly by default, and a section is named once, by a typed descriptor that every reader of it takes. A section is a snapshot unless it is declared live: a reload replaces a live section's value whole once every live section it changes has validated, and reports, to its caller and in its log, every other change since the start as needing a restart. Certificate files rotate when they change on disk, without a reload. Request-scoped values and route meta are typed keys over the request's own `context.Context`, so a value set inside a layer reaches the layers outside it, the handler sees a deadline or span that stdlib middleware added, and stdlib code reads a value with the standard `Value` and its key. Validation names fields as the client sent them, validates slices of structs, and runs a nested value's `Validate` after its field's rules. `middleware.Rewrite` matches the wire form the router matches. An application can be split into modules whose services all register before any of their handlers. `sqldb` stops writing Bun's private fields; a paginated total is Bun's own count, the caller's, or an error, and a tenant scope is applied through a filter of Credo's own. JWT moves into `auth/jwtauth`, so that only an application that verifies tokens compiles golang-jwt. A middleware can run on every route, mounts included, without running for the router's own 404 and 405; the tier before routing is named for when it runs, and a guard registered there fails closed. The specs v1 freezes separate their normative contract from current behaviour, and the deprecated APIs, the parallel ones and three leftovers of earlier shapes go. The Context is no longer pooled, so a `*Context` kept past its request cannot read another request's state, and observers see the final response, reading the request's values as the Context does.

Breaking changes are allowed before v1. Following the release cadence, a minor collects the work items that are ready when it is cut, names each break under its own CHANGELOG heading and in the migration guide, and puts first in its release notes the changes that compile unchanged but behave differently; no item waits for another without a reason in the sequence below. The breaking items are R2–R7, R9 and R11–R15. R8 is additive, and R10 changes no API. The implementation does not reopen the accepted decisions by adding options, modes or parallel APIs, and nothing deprecated is kept beside its replacement.

## Sequence

R1 lands before any code: it writes the decisions into the ADRs and specs, each promoted section marked pending until its work item ships, and adds the TODO section. The work items are then independent, with these exceptions:

- R12 follows R2, because the classified error code an observer reads is the code R2's single channel produces, and R4, because an observer reads the request's values through R4's head.
- R10 follows R4, so that the measurement prices the Context's final layout, not the one R4 replaces.
- R15 follows R5, whose descriptor declares a section live.
- R9 lives in the `store/sqldb` module and depends on no root work item. Until R9 has landed, a Bun upgrade inside the module passes CONTRIBUTING's layout gate; after it, the conformance tests of R9's acceptance.
- R14 follows the work items whose specs it splits, so that each spec is split once, in its final form, and it is the last breaking root item: its prunings break, and its split fixes what v1 promises.

The v1 Gate's stability window — two minors without breaking changes — opens after the last breaking root item of this plan has shipped. R9 may land on either side of it: `sqldb` is released in lockstep with the root, and its `beta` label keeps it outside the v1 compatibility promise while its work remains.

Each work item is one or more theme commits, each green on its own, on the release branch of the minor that carries it. Work items keep their numbers, so that references to them stay stable.

**Messages.** An error message is part of the API. Every error and panic this plan adds or changes names what failed and the remedy, and the test that triggers it asserts those parts:

- a message key missing from the catalog, in debug, with the key, the code and the route (R2);
- `testutil`'s message-key scan: a key no catalog defines, and a key whose value is not a literal, each with its file and line (R2);
- `fault.New` with an undeclared kind, an invalid machine code or a second code, naming the declared kinds, the machine-code grammar or the single-code rule (R2);
- a configuration value strict decoding refuses: the key path, the conversion refused, and `config.WithWeakDecoding()` (R3);
- `Section.Decode` with an empty key (R5);
- `UseModules` called a second time, with the remedy of passing every module to one call (R8);
- `ErrUnsupportedCountQuery`: the rule that made the query unknown, its culprit, and the remedy, `PageWithCount` (R9);
- `ContractGuard` without a route, logged once beside the 500, naming its registration before routing and the remedy (R13);
- `StaticRoute.BuildURI` with a file path it cannot represent, naming the path and the reason (R14);
- a live section that fails to decode or validate at a reload, with its key, the error, and that nothing was published (R15);
- `Section.Live` over a configuration that cannot reload, and `App.Reload` with one, each naming the configuration's type and `config.Load` (R15);
- a reload's report: the keys changed since the start that no live section covers, with the remedy, a restart, and the changed file keys a later source keeps, with that source (R15);
- a certificate pair that fails to load after a change on disk, logged once per change with both files and the error, the old pair kept (R15).

**Verification.** Every commit runs `go vet`, the shadow analyzer, `gofmt`, the CI linter configuration and `go test -race` over every package except the ignored `tmp/` tree; R9's commits run `store/sqldb`'s tests in its own module, against SQLite, PostgreSQL and MySQL. R4 and R10 carry benchstat tables (`-count=10 -benchmem`, CONTRIBUTING's "Performance Changes"); R10's measurement is recorded in ADR-008.

## R1: promotion and the decisions that change no code

**Promotion.** Each decision is written into its canonical ADR and its detailed spec (the contract map), with a pending marker that the implementing work item removes. While an ADR section this plan writes carries its pending marker, it states two parts, *Problem* and *Removes*. The work item that removes the marker turns Problem into the Context's design forces and failure modes, stated without the previous design, and moves Removes into the migration guide and the CHANGELOG entry, so the released ADR states the current design only.

- **ADR-009: R2.** Preserved: the nested `{success: false, error: {...}}` envelope as the default body, RFC 9457 as the one-line opt-in renderer, and success envelopes only through `SuccessRenderer` and `Render`. Changed: one status channel, without `store`'s `HTTPStatus` bridge, a `Code*` constant for each code of the framework's own and none for a code derived from a status, a message key of its own named string type that is never rendered as text (declared in `validation` and aliased by the root, so that a violation's key has it too), literal messages, client input in `Details` only, the fault kind as the default code, and `fault.Error`, the carrier through which a service names a code of its own. Rejected: an opaque key type that only a constructor builds, which refuses at compile time the untyped literal that the removed text fallback, the debug warning and the scan already catch, at the price of a conversion in every renderer and in the resolver, whose computed keys the scan would report; a process-wide key registry, since catalogs are per application and one test process runs many applications; and a hand-maintained key list as the primary check, since it duplicates the catalog and leaves a forgotten key unchecked. Rejected for the carrier: mapping each domain error to an `HTTPError` in the handler, which every transport would repeat; an optional `FaultCode()` method beside `FaultKind()`, which a misspelled method passes unnoticed; a message key or a literal message on it, since `fault` cannot name the root's key type, the code already is the catalog key and literal client text is the boundary's choice; and kinds added before a domain error needs them, since each kind is a status mapping and an unknown kind already fails closed. Rejected for the constructor: `New(kind)` beside `NewCode(kind, code)`, or `New(kind, WithCode(code))`, since `New(kind, code...)` mirrors `NewHTTPError(status, code...)`, so the two carriers are built alike, while a second constructor or an option would be a second way to set one field.
- **ADR-005: R3 and R5.** Strict decoding becomes the default and mapstructure's weak coercion the opt-in, whose contract is that one sentence. Rejected: a normative coercion rule set with a conformance suite. ADR-001's automatic loading and the rejection of `IOptions<T>` are preserved: R5's descriptor binds the section's `T` unwrapped, and only a section declared live is wrapped (R15). The descriptor is a named string type with a `Decode` method, and a section is bound through `Provide` with that method. Rejected: an App method that binds a section, which `Provide` with `Decode` already does; a descriptor type that refuses a literal key, which would break every `GetConfig` call written with one, for a check decoding already makes; reporting unknown top-level keys by recording the sections a run decodes, which would flag a section first decoded after the start, one only another deployment reads and, under `WithPrefix("")`, every process variable; and configuration as an `Infra` field, which could carry only the untyped `RawConfig` and would put string keys into business code, the service locator ADR-004 rejects.
- **ADR-020: R15.** The ADR states live sections: a section is a snapshot unless it is declared live, and a reload replaces a live section's value whole once every live section it changes has validated against the candidate. A section is static or live within one configuration, never both. Kept: the operator's trigger, validation before publish, no rollback, the report of the changes that need a restart, and its rejected alternatives, whole-configuration reload, restart-on-reload and watching configuration files among them. Replaced: per-key subscribers, generic hooks and framework participants. Its rejection of polling is reopened for certificate files only, with the evidence that a Kubernetes Secret update sends the process no signal: the check at the handshake adds no dependency and no goroutine, a partial write fails to load and keeps the old pair, and `os.Stat` follows the link swap of a Secret volume. Rejected: removing runtime reload, which would leave an application whose operational values — a log level, a rate limit, a timeout, a maintenance flag — must change without a restart to build the trigger, the staging, the validation and the drain's step itself, the toolkit answer the all-in-one framework exists to spare it, while ConfigMap and Secret volume files change in place under Kubernetes too; `OnConfigChange` taking the descriptor, which keeps a callback that applies the fields it chooses while its whole section counts as covered, and the holder each subscriber builds; `OnReload`, or a component capability run at every reload, since derived state follows its section through `OnChange` and a refresh unrelated to configuration installs its own SIGHUP handler, which `signal.Notify` serves beside Credo's; every section live, which makes every read an atomic load and hides from the constructor which values can change; liveness per field, since the value a consumer holds is a copy and applying part of a section is the defect live sections remove; the live sections held by the App, with `Stager` kept for a custom configuration, which needs the configuration bound through a wrapper that `Resolve[RawConfig]` would return in place of the caller's value, for an extension only a test implements; and `Get` for the read, a name Credo gives lookups by key.
- **ADR-008: R4 and R10.** The Context holds the request's current `context.Context` as its head; values are typed keys over it, which stdlib code reads with `Value` and the key; `Request.Std()` is the one accessor for the standard request, and `Context.Within` the one way a layer opens a scope. Rejected: `WithContext` as the scope method's name, a construction verb in Credo and a copy in the standard library; a mutable store behind `Value`, which does not conform to the `context` contract however it is documented; a chain of the Context's own, rooted once at the request's context, which a deadline or span added later never reaches; values that end with their scope, today's behaviour, which loses a user set inside `middleware.Timeout` or a wrapped stdlib middleware; values in a table of the Context's own, which a repository given `c.Context()`, a mounted stdlib handler and a wrapped stdlib middleware would no longer reach; and keeping the embedded request in step on every `Set`, a request copy per value. Rejected for the keys: string keys with a type argument at each call, which bind no type to the name and let two packages share one value; methods on the key beside the Context's, a second path to one value; converting between `T` and `*T` on a mismatch, which loses the caller's writes and which a typed key cannot produce; a typed reader for a `context.Context`, a second path for code that holds the Context, and its user form, the accessor ADR-012 refuses; and `NewValue` with `SetValue`/`GetValue`, whose constructor makes a key, not a value. R10: the Context is not pooled, and its measurement is recorded with the expectation stated in advance. Rejected for R10: keeping the pool when the unpooled build is more than 5% worse, which would price a read of another tenant's user against throughput, while a larger cost is answered in the layout; and detecting use after release instead, which a counter inside the object cannot do, since a retained bare pointer reads the reused object's new counter.
- **ADR-007 and ADR-012: R4's typed meta and user accessors.** Untyped meta and string-meta RBAC give way to typed keys, `LookupMeta` becomes `GetMeta`, and the allocation claim on `SetUser` goes with the request copy behind it. The user's key stays unexported, so the user keeps no `context.Context` accessor. ADR-012 also records R11's `auth/jwtauth`.
- **ADR-011: R6. ADR-018: R7. ADR-003: R8**, with R8's rejected alternatives. **ADR-010: R13**, with its rejected alternatives. **ADR-007, ADR-008, ADR-015 and ADR-018: R14's prunings**, with the APIs kept and their reasons.
- **ADR-010 and ADR-014: R12.** Observers are added with `app.AddObserver`, and the access log's `ResultFilter` takes the `*Exchange`, which replaces `AccessLogEntry`. An observer reads the request's values as the Context does: `Exchange.Context()` returns R4's head as it stands when the response is final, `Exchange.Get` reads a typed key's value from it as `c.Get` does, and `Exchange.GetUser[T]` reads the user, whose key stays unexported (ADR-012). Rejected: reading a value only through `ex.Context().Value(key)`, a type assertion where the handler's `c.Get` needs none, for a record that already reads the user through a method; typed keys alone, which would leave a metrics observer without a context to record through, so the OpenTelemetry SDK, which takes the span for an exemplar from that context, would attach none.
- **ADR-015 and ADR-002: R9.** The private-field layer, its "temporary pinned-Bun workaround" paragraph and the hook paragraph are rewritten; the curated forwarders are the thin adapter and stay, and `ApplyFilter` takes `ApplyQueryBuilder`'s place. Rejected: the derived-table count as the fallback for queries the wrapper cannot prove, which carries their sort and any lock clause; a derived count for a raw `ColumnExpr`, even with the sort held back until the data query, a second count path, which on MySQL fails with error 1060 for a projection that repeats a column name; `COUNT(*) OVER()`, which adds a column the model scan cannot place and miscounts under `DISTINCT`; making a model's `BeforeAppendModelHook` turn its query unknown, which takes the automatic total from Bun's timestamp idiom, although the hook never sees a counted query; treating every query with a filter callback as unknown, which sends the tenant pattern down the explicit path on every page; handing the callback a builder that embeds Bun's `bun.QueryBuilder` interface, on which a method a later Bun adds runs where Credo cannot see it, so that it needs a method-set comparison, a log at `Open` and a classification at every Bun upgrade, while an application that minimal version selection gives a newer Bun fails its filtered pages at request time; tracking `Unwrap` on Bun's own builder, which a type assertion passes unseen; and implementing Bun's builder interface method by method, which breaks every application that upgrades Bun before Credo does.
- **ADR-007: the path as received.** The router matches the path the client sent: it removes no dot-segment and merges no empty segment, so `/a/../b` is not `/b` and `//a` is not `/a`. Browsers and HTTP clients remove dot-segments before they send a request, so a `..` on the wire was sent deliberately; matched as received, it never reaches a handler other than the one for the path a proxy or a guard in front judged. A parameter may capture `..` as its value, which is the handler's input like any other, and static files are served through `os.Root`, which refuses to leave its root. Rejected: cleaning the path, or redirecting to its clean form as `http.ServeMux` does, which makes two spellings of a path reach one handler. R1 adds tests that pin it, and the router spec states it beside its rule that a decoded value is data, not a path.
- **ADR-008: no stdlib path values.** The dispatcher does not set the standard request's path values for a route; Credo code reads parameters through `Request.RouteParam` and `Request.PathValue`, and a handler mounted under a parametric prefix keeps receiving the prefix's parameters as path values. Rejected: populating them on every request, which would allocate a map per request outside a `ServeMux` pattern and share that map between a request and its `WithContext` copy, so that a value set on one shows through the other.
- **ADR-011: `Validate` takes no context.** `Validatable.Validate() error` stays: validation checks a decoded value, and a context invites I/O into it — a uniqueness check belongs to the service, which returns a `fault.Error`. A context-taking interface could be added beside it later without a break, as ozzo-validation v4 added `ValidatableWithContext`, so nothing is reserved for it now.
- **ADR-003: the App stays the one facade.** No `Router` is exported. Handler tests run the real pipeline — `testutil.NewApp`, the route under test, and `app.ServeHTTP` with an `httptest` recorder — so route parameters come from the path, meta from the route, and a returned error is rendered as in production. Rejected: an exported `Router` with `testutil` helpers that set parameters and meta and render errors without DI or the lifecycle, a second public way to build a routing tree whose helpers would reimplement the dispatch and the error pipeline.
- **Specs:** context, HTTP features, i18n, config, router, middleware, auth, validation, container, store and pagination.
- **Guides:** the routing guide gains a section on testing handlers through `NewApp` and `ServeHTTP`, and its section on route parameters and file names opens with the path as received: the router removes no dot-segment, so a `..` reaches a handler only as a parameter's value, never as a resolved path.

## R2: one error channel; keys, messages and fault codes

**Change.**

- **One status channel.** The legacy `HTTPStatus() int` interface goes, with its implementations on `*HTTPError` and `*BindError` and its deprecated bridge in `store`: `(*store.Error).HTTPStatus`, the kind sentinels' `HTTPStatus` and `legacyHTTPStatus` (`store/errors.go`). A store error keeps its status through `FaultKind`, which the pipeline already reads before `HTTPStatus`. An error's status comes from `*HTTPError`, from the validation errors, from `*BindError` as a classified bind failure, or from `fault.Provider`; anything else is a 500. An explicit `HTTPError` keeps winning over what it wraps.
- **The message key is a catalog key only.** `credo.MessageKey` is a named string type, `type MessageKey string`, declared in `validation` and aliased by the root, `type MessageKey = validation.MessageKey`, as `credo.RawConfig` aliases `config.RawConfig`: the root imports `validation`, whose violations carry a key too. `HTTPError.WithMessageKey`, `HTTPError.MessageKey`, `ErrorInfo.MessageKey`, `RenderMessageKey`, `RenderInfo.MessageKey` and `validation.ValidationError.MessageKey` take it, and `I18nConfig.ResolveMessageKey` keeps returning a `string`, since it computes keys. A catalog miss never renders the key as text: it falls back to the built-in message for the code and then to the status text. In debug the pipeline warns with the key, the code and the route.
- **The message is literal text.** `HTTPError.WithMessage(text)` sets the client message directly, never looked up.
- **Client input goes into `Details` only.** The framework keys that embed it change: an unsupported content encoding (`request.go`, `decompress.go`) and an unsupported content type (`request.go`) carry the value in `Details`, and so does a missing scope in `ContractGuard`. An unsupported bind field type is a developer error: it becomes a 500 with the reason logged, as an invalid bind target is, instead of a 400 whose key names the field.
- **The framework's own keys follow the rule.** Beside the keys above, the framework passes literal text as a key: `ContractGuard`'s rejections of a missing or unaccepted content type, a missing header or query parameter, an API version and a body over its limit (`middleware/contractguard.go:238-339`), the decompressor's size limit (`decompress.go:152`) and `Redirect`'s invalid status (`response.go:488`). Each drops its key and renders its code's built-in message, with its value in `Details`: the rejected content type, which is client input, and the header or query parameter the route requires. An invalid redirect status is a developer error, a 500 with the reason logged. With the key typed, a key built by concatenation no longer compiles, so the compiler finds any this list misses.
- **Constants name codes.** The `MsgKey*` constants are codes, not keys: `NewHTTPError(status, code...)` takes one as its code, and the lifecycle's 503 body sets one as `Code` (`prepare.go`). The thirteen that repeat the code `NewHTTPError(status)` derives from a status go; `MsgKeyValidationFailed` and `MsgKeyBindFailed` become `CodeValidationFailed` and `CodeBindFailed`, beside `CodeUnsupportedContentEncoding` and `CodeInvalidBindTarget`. A code derived from a status needs no constant, and a framework code has a `Code*` one. The lifecycle's 503 takes its code from the status, and `middleware.Timeout` drops its `WithMessageKey`, whose key repeats its code, `request_timeout`, so `I18nConfig.ResolveMessageKey` maps the timeout's code as it maps every other, where the explicit key bypassed it.
- **The fault kind is the default code.** A fault without an explicit code renders its kind as the code — `already_exists`, `constraint`, `serialization`, `deadlock`, `contention`, `conflict` — so a duplicate stays distinguishable from a retryable serialization or deadlock failure. The statuses do not change.
- **A service names its own code.** `fault.Error` is the carrier a domain layer returns without naming a transport status:

  ```go
  var ErrDomainTaken = fault.New(fault.KindAlreadyExists, "tenant_domain_taken")

  return nil, ErrDomainTaken.WithDetails(map[string]any{"domain": in.Domain}).WithInternal(err)
  ```

  Its fields are `Kind`, `Code`, `Details` and `Internal` — `HTTPError`'s, with the kind in place of the status and without the message key. `New(kind, code...)` mirrors `NewHTTPError`: without a code the kind is the code, and an undeclared kind, `KindUnknown` included, an invalid machine code or a second code panics; during a request, recovery turns the panic into a generic 500. `WithDetails` and `WithInternal` return copies, so a sentinel is never mutated, and `Is` matches another `fault.Error` of the same kind and code, so a derived copy still matches its sentinel. The kind gives the status, as for every fault; `Code` is the code; `Details` render as `details`; `Internal` is logged and never rendered; the message is resolved from the code as for an `HTTPError` without a key. Like an `HTTPError`, an explicit `fault.Error` wins over a validation or bind error it wraps, so a cause given as `Internal` never reaches the client: the classification order becomes `*HTTPError`, `*fault.Error`, the validation errors, `*BindError`, any other `fault.Provider`, then 500. A value built without `New` whose kind is unknown or whose code is invalid fails closed to a generic 500, as an invalid `HTTPError` does. `Code` is the client-visible machine code, as on `HTTPError`; `store.Error`'s `Code` is the driver's and stays unrendered. `fault` stays transport-neutral — no status, no message key — and shares the machine-code grammar with `HTTPError` through one internal check, since it cannot import the root.
- **`testutil`'s message-key scan.** `testutil.CheckMessageKeys(tb, catalogDir, sourceRoots...)` parses the sources with `go/parser`, collects the keys written as literals — a literal argument of `WithMessageKey` or `RenderMessageKey`, a literal given to a `MessageKey` field, a constant or variable declared with type `MessageKey`, a conversion to it — reports a key whose value is not a literal, and fails the test for a key the catalogs do not define. The application chooses its catalog, so the check stays per application. A key that reaches `WithMessageKey` through an untyped constant is outside the scan, so key constants are declared with their type.

**Tests.**

## R3: strict configuration decoding by default

**Change.**

- `config.Load` decodes strictly unless told otherwise: an unknown key is an error, and a value is not coerced across kinds. That covers `Unmarshal`, `Get`, the decoding of a reload's candidate, and the framework's own `server` section in `credo.New`, as `WithStrictDecoding` does today.
- **Strings parse into basic types.** Process environment and `.env` values are strings, so strict decoding as it ships rejects every override of a typed field (`docs/specs/config.md`). The default therefore adds mapstructure's `StringToBasicTypeHookFunc` beside the duration and `TextUnmarshaler` hooks that stay on in both modes: `CREDO_SERVER__PORT=9090` decodes into an `int`. Conversions across kinds stay refused — a boolean into a number, a number into a string, a scalar into a slice. The hook does not know a value's source, so a quoted number in a file decodes too; parsing a string by its target type is not a conversion between kinds.
- **`config.WithWeakDecoding()`** is the opt-in, and its contract is one sentence: mapstructure's weak coercion. `WithStrictDecoding` goes.

**Tests.**

- An environment override of an `int`, `bool`, `float64`, `time.Duration` and a `TextUnmarshaler` field decodes; a boolean into an `int`, a number into a `string` and a scalar into a slice fail, with the remedy.
- `WithWeakDecoding()` restores today's default behaviour, unknown keys included.
- A reload's candidate decodes in the instance's mode.

## R4: typed keys over one context head

**Change.**

- **Typed keys for request values and route meta:**

  ```go
  var Tenant = credo.NewKey[*TenantInfo]("tenant")
  c.Set(Tenant, t)       // a value of another type does not compile
  t, ok := c.Get(Tenant) // t is a *TenantInfo

  var RequiredScopes = credo.NewKey[[]Scope]("auth.scope")
  route.SetMeta(RequiredScopes, []Scope{"admin"})  // the value type is checked at compile time
  scopes, ok := c.Route().GetMeta(RequiredScopes) // the route, then its groups, then the App
  ```

  One key type serves request values and route meta. The name is for diagnostics; identity is the key value, so the keys of two packages never collide. Two `NewKey` calls with one name are two keys, while two `MessageKey` values with one text are one catalog key (R2), and both godocs say so. A zero `Key[T]`, declared without `NewKey`, panics in every method that takes a key, naming the method, since all zero keys of one type would be one context key. `Set`, `Get`, `SetMeta` and `RemoveMeta` keep their names and take a key, as generic methods whose type parameter is inferred from it, and `LookupMeta` becomes `GetMeta`, returning `(T, bool)` as `GetUser` does. Credo reads and writes values only through these methods; code that holds only a `context.Context` reads one with the standard `Value` and its key, which is the context key, and Credo adds no reader of its own. The string-keyed forms and the `map[string]any` meta go. The middleware meta constants (`MetaAccept`, `MetaMaxBody`, `MetaRequireHeaders`, `MetaRequireQuery`, `MetaScope`, `MetaAPIVersion`) and `credo.MetaAccessLog` become typed meta keys, and the request ID moves from its string key to a typed one.
- **One head, owned by the Context.** The Context holds the request's current `context.Context`; `c.Context()` and `c.Request().Context()` return it. `c.Set` replaces the head with a `context.WithValue` node over it, so no request is copied for a value, and no custom `Value` implementation exists. A context handed to a goroutine is a fixed node, so successive `Value` calls on it agree. A key set again and again, as a server-sent-events or WebSocket loop may set one, does not lengthen the chain without bound. When the head is the node the Context built for that key, the new node is built over that node's parent. Keys set in turn add a node each, so once the nodes the Context built over the request's context, or over a scope's, number twice the keys set there, it rebuilds them from the record of `Set` calls, which keeps one entry per key. Neither modifies a node, so a context handed out before keeps its values.
- **Scopes.** A layer that derives a context derives it from the head and makes the result the head of the inner chain: `middleware.Timeout`'s deadline and a span a stdlib middleware adds through `WrapStdMiddleware` are visible through `c.Context()`. When the layer returns or panics, the head reverts to the outer one, so a deadline or span ends with its scope, and the values set through `c.Set` inside it are applied again over the outer head: a user or a tenant is a fact about the request, not about one layer. The Context keeps the order of its `Set` calls for that, and reapplies them in a deferred call, so when the handler panics, a user set inside the scope is still the request's user for the error rendering, the observers and the access record.
- **`c.Within(ctx, next)` opens a scope.** `func (c *Context) Within(ctx context.Context, next Handler) error` makes `ctx` the head of the inner chain, keeps the embedded request in step with one copy per scope, runs `next`, and reverts as above when `next` returns or panics. The `middleware` package cannot reach an unexported head, so without a public scope `middleware.Timeout` and an application's own deadline or tracing middleware would have only `WrapStdMiddleware`, with its request copy and adapter per request; with it `middleware.Timeout` is one call. `ctx` is derived from `c.Context()`; one that is not is the unrelated context of the edges below. A value the scope owns, such as a transaction or a span, goes into the context given to `Within` and ends with it, while `c.Set` records a fact about the request, which outlives the scope: a transaction stored with `c.Set` would still be found after its commit. Today's idiom, assigning `c.Request().Request` a request with a new context (`middleware/timeout.go:71`), still compiles and no longer moves the head, so in debug mode the Context reports, once per route, an embedded request it did not install. Rejected: the name `WithContext`, since `With` names construction options in Credo and the standard library's `WithContext` returns a copy where this runs a chain; and adopting a replaced request's context as the head, which no scope would ever revert.
- **The stdlib boundary.** `c.Request().Std()` is the one accessor for the standard request: the embedded `*http.Request` when it already carries the head, otherwise a copy with the head that replaces the embedded request, so a second call without a new `Set` copies nothing, and a multipart form that stdlib code parses on the copy stays under the request-end cleanup. `WrapStdMiddleware` and `Mount` hand the request on through it, and take the context of the request the stdlib code passes on as the head of the inner chain. `Within` keeps the embedded request in step, as `middleware.Timeout` does by hand today. `c.Request().Request` stays the embedded field, and its `Context()` is the context it was built with, which lags the head after a `Set`: `Std()`'s godoc says in its first sentence that the call may replace the embedded request, and the `Request` type's godoc points to `c.Context()` for the head.
- **Edges of the head**, each pinned by a test:
  - A Credo middleware that calls `next` again, as a retry does, runs the second attempt over the head the first left: the values the failed attempt set are visible to the second and, unless it sets them again, to the observers. Rejected: reverting an attempt's values when `next` returns an error, since the Context cannot tell a retry from a middleware that handles the error and goes on, and a user set before the failure is still the request's user.
  - A stdlib middleware that runs the next handler on another goroutine, as `http.TimeoutHandler` does, is outside `WrapStdMiddleware`'s contract, which its godoc names in place of today's promise of any existing Go community middleware: the Context is not safe for concurrent use, and the goroutine would move the head while the outer layer reverts it. `middleware.Timeout` sets its deadline on the request's own goroutine.
  - A stdlib middleware that passes on a context not derived from the request's, which drops the request's cancellation too, cuts the handlers after it off from the values set before it, through `c.Get` as through `Value`. Today's string store, which ignored the request, kept them.
  - A mounted Credo App has a Context of its own. The mount hands it the request through `Std()`, so it reads what was set before the mount, the user included; what it sets stays in its own Context, and the parent's observers and access record do not see it.
- **User accessors.** `SetUser`/`GetUser[T]`/`RequireUser[T]` stay, as shortcuts over a generic key; the request copy behind `SetUser` goes. Their key stays unexported, so the user has no `context.Context` accessor, as ADR-012 decides.
- **Meta snapshot.** A route's meta is resolved into a per-route snapshot when its chain is compiled, so a request-time lookup no longer walks route, group and root. Registration order still never decides membership.
- **Meta methods aligned.** Every meta method changes its signature here, so the shapes are aligned in the same break: `Group.SetMeta` returns its `*Group`, as `Route.SetMeta` and `StaticRoute.SetMeta` return theirs, and `Route` and `StaticRoute` gain the `RemoveMeta` that `App` and `Group` have, which removes the route's own value so that its group's shows through.
- **Documentation and examples write `c *credo.Context`**, since `ctx` conventionally names a `context.Context`.

**Tests.**

- The acceptance test, written before the storage changes: in the handler, `c.Context()` and `c.Request().Context()` carry a deadline set by `middleware.Timeout` and a span added by a wrapped stdlib middleware; a user set inside either scope is visible to the outer layers after it returns; a wrapped stdlib middleware reads a value set before it with `Value` and its key, and the request it passes on still carries the user, which the handler after it reads with `GetUser`.
- `Std()` copies at most once per boundary and not at all when the request already carries the head; a multipart form parsed on the copy is cleaned up at request end.
- `Within`: the inner chain reads `ctx` through `c.Context()` and `c.Request().Context()`; after it returns, and after it panics, the head is the outer one, a value set inside is reapplied over it, and a value put into the given context is gone; `middleware.Timeout` built on it passes the acceptance test; in debug mode a handler that assigns `c.Request().Request` is reported once per route.
- Typed meta: a route value overrides a group value, the snapshot matches the walk it replaces, and a named string type in a meta value no longer fails `ContractGuard` open. `Group.SetMeta` chains, and `RemoveMeta` on a route lets its group's value show through.
- The edges: a user set inside a scope before the handler panics is visible to the observers after recovery; one key set a thousand times keeps one node for it in the chain, two keys set in turn a thousand times keep at most four, and a context taken before keeps its value; a Credo middleware that calls `next` twice runs the second attempt over the first one's values; a stdlib middleware that passes on `context.Background()` hides the values set before it from the handler after it; a zero `Key[T]` panics in each method that takes a key, naming the method; a mounted Credo App reads the parent's user, and a value it sets does not reach the parent's observers.
- **Benchmark, criteria fixed in advance**, on a nested chain: a stdlib middleware adding a span through `WrapStdMiddleware`, then `middleware.Timeout`, then authentication, then a handler setting one more value, with a hook reading the user after the response. It runs against the same chain on today's code, which loses the user, so the comparison prices the behaviour. The storage ships when the acceptance test passes and the chain's time and bytes per request are no worse than today's; allocations are reported. Expected in advance: each `Set` stops copying the request, and a value set inside a scope costs one more node each time an enclosing scope ends, so allocations may rise by one or two while bytes fall. If the time regresses, the remedy is in the implementation — reapply at the first read after a scope ends — not in the contract.

**Documentation.** ADR-008, ADR-007 and ADR-012; the context, router, middleware and auth specs; the godocs of `WrapStdMiddleware`, `Request`, `Std()` and `Within`; the guides that use `Set`, `Get`, string meta or `ctx`. Migration rows: `ctx.Set("name", v)`/`ctx.Get("name")` become `c.Set(key, v)`/`c.Get(key)` with a `credo.NewKey[T]`; `SetMeta("name", v)` becomes `SetMeta(key, v)` with the same kind of key, and `LookupMeta("name")` becomes `GetMeta(key)`, which returns the typed value; the middleware meta constants keep their names and change type; code that took the request with `c.Request().Request` for a stdlib API takes `c.Request().Std()`, a middleware that assigned `c.Request().Request` a request with a new context calls `c.Within(ctx, next)`, and code that read `c.Request().Request.Context()` reads `c.Context()`. Release notes, first: a user set inside `middleware.Timeout` or a wrapped stdlib middleware now reaches the outer layers, and a deadline or span a stdlib middleware adds is now visible to the handler through `c.Context()`; a stdlib middleware that passes on a context not derived from the request's now hides the values set before it from the handlers after it; and a middleware that assigns `c.Request().Request` a request with a new context no longer changes `c.Context()`.

## R5: typed configuration sections

**Change.**

```go
var AppSection = config.Section[AppConfig]("app")

app.Provide(AppSection.Decode)       // a snapshot of the section, bound in DI
cfg := app.MustGetConfig(AppSection) // the same descriptor in the composition root
```

- **The descriptor.** `config.Section[T]` is a named string type, `type Section[T any] string`, so `config.Section[AppConfig]("app")` names a section and its type once, by conversion. The descriptor is the receiver of the call that reads it, `AppSection.Decode(src)`, where a request key is an argument of its carrier, `c.Get(key)` (R4): the descriptor's method value is the constructor `Provide` takes, while a request value has the Context as its one carrier.
- **`Section[T].Decode(src config.RawConfig) (T, error)`** decodes the section through `Unmarshal`, which already runs the target's `Validate`; an empty key is an error. It lives in `config` and needs no root import, since `credo.RawConfig` is an alias of `config.RawConfig`. Its method value is an ordinary constructor over the framework's `RawConfig` binding, so binding a section needs no App method: a missing section or a failed validation is a constructor error at `Resolve` or at start that names the key, not a registration panic, and a second binding of one type panics with the container's message and its remedy. The bound value is the section's `T`, a snapshot, as today: a reload does not change it, and a section that must follow a reload is declared live (R15).
- **Several sections of one type.** A section that only one constructor reads is decoded in that constructor and not bound: two databases whose sections both decode into `sqldb.Config` each call their own section's `Decode` where they are opened, and the databases are what the container binds. A section that business code receives is bound once, or under a type of its own.
- **`OnConfigChange` is not retyped:** R15 replaces it with live sections, declared through the same descriptor.
- **`testutil`'s empty configuration honours the missing-key contract:** `Unmarshal` returns the not-found error a real `*config.Config` returns, and `Exists` stays false.
- **One reader per holder.** `Config.Get[T]` and `Config.MustGet[T]` go: `section.Decode(cfg)` reads a section from a `*config.Config`, so the getter would be its second spelling. `App.GetConfig` and `App.MustGetConfig` stay for the composition root, which holds the App rather than its configuration, and take the descriptor: `app.GetConfig(AppSection)` infers `T`, and `app.GetConfig[AppConfig]("app")` keeps compiling, since the untyped constant converts.

**Tests.** A section bound through `Provide` with `Decode` resolves the decoded value; a missing section and an invalid one fail the start with the key and the error; a second binding of one section type panics; `Decode` with an empty key fails; `testutil`'s empty configuration returns the not-found error; `app.GetConfig(section)` returns the decoded section, `MustGetConfig` panics naming a missing key, and a call written with a literal key compiles.

**Documentation.** ADR-005, the config spec and the configuration guide, which shows a section read by the one constructor that opens a database. Migration rows: an `Unmarshal`-ing constructor can become `Provide(section.Decode)`; a test that relied on `testutil`'s empty configuration accepting any key provides the section; `cfg.Get[T]("app")` becomes `config.Section[T]("app").Decode(cfg)`, and `cfg.MustGet[T]("app")` that call with its error handled; `app.GetConfig[T]("app")` keeps compiling.

## R6: validation names fields by their source and validates slices and nested values

**Change.**

- **Field names follow the binding source.** A violation names a field the way the client sent it: the `json` name for a JSON body, the `form` name for a form or multipart body, and the `query` name for `BindQuery`. Today `getErrorFieldName` reads the `json` tag whatever the source (`validation/rule.go`), so a query struct reports names the client never sent. The mechanism is the implementation's, within the rule that reflection stays on the cold path, cached.
- **Slices and arrays of structs are validated like a nested struct.** An element that is `Validatable`, or a struct reachable by pointer, is validated, and its violations carry the index in `Each`'s form, `items[0].name`. Today such elements pass unless the rule list says `Each`.
- **A nested value's `Validate` runs after its field's rules.** A field with rules runs its value's `Validate` once the rules pass, as ozzo-validation does, so `validation.Field(&r.Address, validation.NotNil[Address]())` checks that the address is present and then validates it. Today a rule list replaces the nested validation, so a presence rule on an optional nested field silently stops validating its content. A field whose rules fail reports their violations only.

**Tests.** A query-bound struct and a form body report their tag names; a JSON body reports `json` names; a nested field joins the names of its source. A slice of `Validatable` elements and a slice of structs report `items[i].field`; an `Each` rule on the same field still runs, and the two do not report one violation twice. A nested field with `NotNil` reports the nested violations of a present value and only `NotNil`'s for a nil one, and a field whose rules fail does not run `Validate`.

**Documentation.** ADR-011, the validation spec and guide. Release notes, first: query and form violations change their field names, a request with an invalid element in a slice of structs now fails with 422, and so does one whose nested value fails its `Validate` behind a field with rules.

## R8: application modules

**Change.**

```go
// Module is a part of an application: its services, then its handlers.
type Module interface {
	Services(app *App) // Provide, ProvideValue, Manage, workers
	Handlers(app *App) // routes and other entry points; may Resolve
}

app.UseModules(users.Module{}, billing.Module{})
```

`UseModules` runs every module's `Services` in order, then every module's `Handlers`. The two phases exist whatever the type count, since handlers close over resolved services, and running all services first is what keeps the implicit `Finalize` safe in a modular application: the first `Resolve` inside a `Handlers` method comes after every registration. The second phase is named for what it registers, the application's entry points: routes now, and the gRPC services and event handlers of the planned packages, which register through the App as routes do. Both methods are required; a module with nothing for one phase leaves that method empty, since an optional phase interface would let a misspelled method go unnoticed. `UseModules` is called once: a second call would register services after the first call's handlers had finalized the container. A module composed of others calls their methods from its own. A test passes the modules it needs to `testutil.WithModules(mods...)`, which hands them to `UseModules` with one more module last, whose `Services` applies the test's overrides: they land after every module's services and before any module's handlers resolve, with no seam beyond the public API. An override given beside a `UseModules` call in `WithWiring` would come after the handlers had finalized the container and panic, and a `UseModules` in the wiring beside `WithModules` is a second call. `Module` also takes the place of the roadmap's controller registration (TODO Phase 4.10): a controller's routes are a method that its module's `Handlers` calls on a group. Rejected: collecting the modules and running them later — at the App's preparation, a `MustResolve` in the composition root would finalize the container before any module had registered; at `Finalize`, the first `Resolve` would register routes as a side effect — and either moves registration panics away from the call that caused them; and a registration interface of its own for controllers, with `app.Register(controllers...)`, a second pattern for the composition `Module` expresses.

**Tests.** Services of a later module are registered before handlers of an earlier one resolve; a module whose `Handlers` registers a service panics with the message naming what finalized the container; a second call panics, naming the remedy of passing every module to one call; under `testutil.WithModules`, `WithOverride` replaces a service a module provides and the module's handlers resolve the replacement, while `WithModules` beside a `UseModules` in `WithWiring` panics as a second call.

**Documentation.** ADR-003, the container spec's sequential-bootstrap section, the getting-started and dependency-injection guides, which show a modular composition root, and the `testutil` godoc and the dependency-injection guide's testing section, which show `WithModules` with an override. TODO: Phase 4.10 closes as superseded by `Module`, Phase 5.1's `credo make:controller` generates a module, and the v1 Gate's post-v1 list and the deferred-features entry drop controller registration.

## R9: `sqldb` without Bun's private fields

**Change.**

- **The private-field layer goes:** `bun_select_clone.go` with its offset discovery and `unsafe` writes, the layout check in `Open`, and `bun_select_hooks.go`'s hook replay. The curated forwarders, transaction injection and error mapping at the terminals, the typed `One`/`All`/`Page` terminals and the `Apply`/`Unwrap` escape hatches stay; `ApplyQueryBuilder` gives way to `ApplyFilter` (below).
- **Snapshots and connections.** Terminals keep their snapshot semantics through Bun's own `Clone()`, complete from v1.3.0, and the public `Clone()` forwards to it. Whether a connection was set explicitly comes from the wrapper's `Conn`, as on the other three query types: a `Conn` set inside an `Apply` closure is overridden by transaction injection on all four, where today `SelectQuery` alone honours it through a private read.
- **`Page`'s total.** `Total` is the number of rows the data query returns without its `LIMIT` and `OFFSET`, or an error, never another number. `Count` and `Page` run Bun's native `Count` on a query the wrapper can prove: built without `Apply`, `Unwrap` or a `Relation` callback; whose root model's type does not implement `BeforeSelectHook`; and that either carries `GroupExpr` or `Distinct` or has no raw `ColumnExpr` and no `Having`. Every other query fails before I/O with `ErrUnsupportedCountQuery`, and the caller pages it with `PageWithCount` (below). No count Credo runs sorts or locks.
- **`BeforeAppendModelHook` keeps the total.** On a SELECT, Bun calls it only for values already in the destination, `Page` scans into an empty slice of its own, and `Count` runs no hook, so the hook never sees a query whose total Credo computes, and a model that sets timestamps in it keeps its automatic total. A conformance test pins both facts against the pinned Bun, so a release that changes either fails this module's tests, not an application's count.
- **`ApplyFilter(fn func(*sqldb.Filter))`** replaces `ApplyQueryBuilder` on `SelectQuery`, `UpdateQuery` and `DeleteQuery`. `Filter` is Credo's type with the predicate methods and nothing else — `Where`, `WhereOr`, `WhereGroup`, whose callback takes a `*Filter`, `WherePK`, `WhereDeleted` and `WhereAllWithDeleted` — so a callback has no Bun type to assert and no builder to return: a query built with it keeps its automatic total whatever the callback does, and one function scopes a select, an update and a delete. `Filter` forwards only the methods it names, so a method a later Bun adds to its builder changes nothing here. A callback that needs more than predicates uses `Apply`, whose query `Count` and `Page` cannot prove.
- **`PageWithCount[T](ctx, req, count func(context.Context) (int, error))`** pages a query with the caller's count: it validates the request as `Page` does, runs `count` — another query's `Count` passes as it is — and the data query with the page's window, and builds the page with `NewPage`. The count's sort and lock clauses are the caller's, in the caller's code.
- **The error is part of the API.** `ErrUnsupportedCountQuery`'s message names the rule that made the query unknown, its culprit — the escape hatch, the raw `ColumnExpr`, the model type and its `BeforeSelect` hook — and the remedy, `PageWithCount`; `errors.Is` keeps matching the sentinel, and no exported reason type is added.

**Acceptance.** The removal ships when every criterion passes:

- a connection chosen through the wrapper's `Conn` is kept, and a `Conn` inside `Apply` is overridden by injection, on all four query types;
- every count Credo runs drops `ORDER BY`, `LIMIT`, `OFFSET` and `FOR`;
- on every provable query `Total` matches today's count source, which is the oracle;
- a query whose root model implements `BeforeSelectHook` is unknown, and one whose model implements only `BeforeAppendModelHook` keeps its total, with the conformance test above; a tenant scope applied through `ApplyFilter` limits both the count and the data, and the same function scopes an update and a delete;
- `PageWithCount` validates the request as `Page` does, returns the given count as `Total`, and runs the data query with the page's window;
- an unknown query fails before I/O in `Count` and `Page`, with the message above;
- the count runs on the query's own connection;
- `Limit` and `Offset` keep Bun's zero and negative semantics, with no new check, and the MySQL 1060 mapping stays.

**Documentation.** ADR-015 and ADR-002, the store and pagination specs, the data-access guide, `store/sqldb/doc.go`, whose deferral of a custom count goes, and CONTRIBUTING's "Updating Bun" section, whose layout gate goes. Migration rows: a paginated query with a raw escape hatch, a raw projection without `GroupExpr` or `Distinct`, or a model with a `BeforeSelect` hook takes `PageWithCount`; `ApplyQueryBuilder(fn)` becomes `ApplyFilter(fn)`, whose callback takes a `*sqldb.Filter` and returns nothing, and a callback that needs more than predicates moves to `Apply`; a `Conn` set inside `Apply` moves to the wrapper's `Conn`.

## R10: the Context is not pooled

**Change.** The pool and its reset go, and with them the cross-request aliasing behind the "must not be retained" caveats: a `*Context` kept past its request no longer reads the next request's state, `GetUser` included. The hook godocs say what remains: a `*Context` is not safe for concurrent use, since R4's head moves as scopes return, and its response cannot be written after the handler returns, as `net/http` forbids for every `ResponseWriter`. The Context folds today's five pooled allocations — the Context, its `Request` and `Response`, and the two parameter arrays — into one, embedding the `Request` and `Response` by value and keeping the first parameters in fixed arrays.

**Measurement.** Run after R4, it prices the change and does not decide it: the pooled build against the unpooled one, with a CPU-bound realistic handler such as a small JSON encode, at saturation — requests per second, CPU and allocations per request — and p99 at a fixed load; a handler that waits on I/O would hide the difference by construction. ADR-008 records the numbers. Expected in advance: a cost well inside 5%, since one allocation is small against the ones `net/http` makes per request; a larger cost is answered in the layout, not by keeping the pool. Rejected: keeping the pool when the unpooled build is more than 5% worse, which would price a read of another tenant's user against throughput; and detecting use after release instead, which a counter inside the object cannot do, since a retained bare pointer reads the reused object's new counter.

**Tests.** A `*Context` kept past its request reads that request's values after the next request on the same connection has run; the benchmark pair (Verification).

**Documentation.** ADR-008 and the context spec; the godocs of `Context()` and of the hooks, which drop the pool as their reason. CHANGELOG Changed, and the release notes put first that a `*Context` kept past its request no longer reads the next request's state; no migration row.

## R12: observers of the final response

**Change.**

- **`Observer`** sees one immutable record, `*Exchange`, after the response is final: the method, the path and the original path, the route pattern and name, the remote address and the user agent, the final status, the bytes after compression, the duration, the classified error code, whether a panic was recovered, the request ID, and the request's values. `app.AddObserver(o)` adds one, and panics on a nil observer and after preparation, as the other registrations do. Observers run where the access log is observed today, after finalization, in registration order. `Exchange` is valid only during `Observe`; an exporter copies what it keeps, apart from the request's context (below).
- **Request values through the head.** `Exchange.Context()` returns R4's head as it stands when the response is final: the values set through `c.Set`, read with `Value` and their keys, and a span that a wrap enclosing the observers put there, from which the OpenTelemetry SDK takes exemplars when a metric records through that context (`Record(ctx, …)`). The head is made of immutable nodes, so an exporter may keep it beyond `Observe`; it is cancelled when the request ends. `Exchange.Get(key)` reads a typed key's value from the head, `(T, bool)` as `c.Get` returns it, with `T` inferred from the key, so an observer reads a value without a type assertion. The user is read with `Exchange.GetUser[T]`, as on the Context, since its key stays unexported (ADR-012). Where the tracing wrap sits is decided with the observability release.
- **The classified error code** is a string with a fixed meaning: the code the pipeline classified, captured before the renderer runs; for a recovered panic, the code of the 500 it rendered; after a fallback, the fallback's code; and empty for an error returned after the response was committed or hijacked, for a handler that wrote its own error response, and for an escaped panic with recovery disabled. It is never inferred from the status.
- **A panicking observer** is contained: with recovery enabled, its panic is logged as a framework Error diagnostic and that observer is skipped for the exchange, while the observers after it still run; the response is already final. `http.ErrAbortHandler`, and every panic under `WithoutRecover`, propagate as they do today, as for `Attrs`.
- **The access log becomes an observer.** `MinLevel`, `ResultFilter` and a new `Attrs` option become options of that observer, and `UseAccessLog` stays as sugar. `ResultFilter` takes the `*Exchange`, `func(ex *Exchange) bool`, and `AccessLogEntry` goes: `Exchange` carries each of its fields, so one record has one type, and the filter reads the request's values and the user as every observer does. `Attrs` receives the `*Exchange` and returns application attributes for a record that is a candidate for emission — after `MetaAccessLog`, `MinLevel`, `ResultFilter`, and only when the logger is enabled for the level — emitted inside one `attrs` group, so an attribute never shadows a framework attribute, present or future; `attrs` is a reserved key on the access record. A panic in `Attrs` is logged and the record is emitted without the group. The returned slice passes to the framework and must not be reused.
- **Checked against its real consumers before v1.** Until the observability release, the access log is the only consumer of `Observer` and `Exchange`. The OpenTelemetry and Prometheus adapters written for that release's decision run on them before the stability window opens, so a change they need lands before v1 freezes the record (TODO, R1).

**Tests.** An observer sees the final status after error rendering, recovery and compression, and the user and a value set inside a scope (R4), through `GetUser`, `Get` and `Exchange.Context()`, whose values stay readable when the context is kept past `Observe`; `Get` of a key no layer set returns the zero value and false; the classified code in each case listed above; the access log as an observer keeps today's records byte for byte; `Attrs` on both logger paths, not called for skipped, silenced, filtered or disabled records, a panic keeping the base record; a panicking observer logged and skipped while the next one runs, and propagating under `WithoutRecover`; `AddObserver` with a nil observer and after preparation panics; a `ResultFilter` reads from the `*Exchange` each field the entry carried; a benchmark pair for the access-log path.

**Documentation.** ADR-010 (the access log behind `Observer`, the `attrs` group and its narrow guarantee) and ADR-014 (`Exchange.Context()`, `Get` and `GetUser`); the HTTP features spec. Migration rows: a `ResultFilter` written as `func(ctx *credo.Context, e credo.AccessLogEntry) bool` becomes `func(ex *credo.Exchange) bool`, reading the same values from the `Exchange`, and the request's values through `ex.Get`, `ex.GetUser` and `ex.Context()`. Rejected, as ADR-010 records: an open `Stage` or rank registry; `Attrs` as a field of the framework contract; top-level placement of the returned attributes; a group named `app`; a public constant for the access record's message.

## R13: a routed middleware tier

**Change.** `app.Middleware(m...)` adds middleware that runs on every route registered through the App — directly, in a group, in a host group, as a static route or as a mount — after the match and before group and route middleware:

```go
app.Middleware(middleware.ContractGuard()) // reads every route's meta; never runs for a 404 or a 405
```

A pre-routing middleware cannot read route meta, so today a meta-driven middleware such as `ContractGuard` does nothing as global middleware and is repeated on every group. The method delegates to the root group's `Middleware`: the App's routes, groups and host groups descend from that group, and group middleware is collected when the chain is compiled, so a middleware added after a group was created applies to its routes too. It does not run for the router's own 404 and 405, which reach the pre-routing tier only. The user tiers become PreRouting → routed → Group → Route. Rejected: an open stage or rank registry, as ADR-010 records; the tier is ordinary middleware in registration order.

- **A mount is a route.** A request a `Mount` matches carries a `*Route` of kind mount — the mount's pattern, the App's meta, no name — so `HasRoute` is true for it, and its handler runs inside the routed tier, through a chain compiled as a route's is. A mount belongs to no group and has no route value of its own, so group and route middleware still do not apply to it. Today a mounted handler is dispatched raw, outside the compiled chain, and receives pre-routing middleware only, so authentication added to the routed tier would let a mounted path through.
- **`GlobalMiddleware` becomes `PreRouting`**, named for when it runs: before the match, on every request, the router's own 404 and 405 included.
- **What stays before routing.** A middleware that acts before the match, or on a request no route matches, stays on `PreRouting`: `CORS` answers a preflight, an `OPTIONS` request for which the router has no route, so on the routed tier the router's 405 would answer it instead; `Rewrite` changes the path that routing matches; and `Secure`'s headers and `RateLimit`'s limit cover the router's 404 and 405 too. `CSRF` needs no route and works on either tier; authentication and `ContractGuard` go on the routed tier. The middleware guide shows the tier of each in one table.
- **`ContractGuard` fails closed without a route.** Registered before routing, it sees no route on any request, and today it lets every request through, which its godoc calls a safe no-op. It answers 500 through the error pipeline instead and logs one Error naming its registration before routing and the remedy: `app.Middleware`, a group or a route. Rejected: a warning at preparation, which lets every request through until someone reads the log, and which the framework could emit only by identifying one middleware among the functions it is given.

**Tests.** A routed middleware runs on a route of the App, of a group, of a host group, on a static route and on a mount, before group and route middleware, and reads the route's meta; it does not run for a 404 or a 405; one added after a group's routes were registered applies to them; after preparation the call panics, as every registration does. An authentication middleware on the routed tier answers 401 for a mounted path; a mounted request sees the mount as its route, with the App's meta, and its access record names the mount's pattern. `PreRouting` runs for a 404 and a 405, and `CORS` there answers a preflight for a path that has no `OPTIONS` route, which on the routed tier gets the router's 405. `ContractGuard` registered with `PreRouting` answers 500 for every request and logs one Error.

**Documentation.** ADR-010's user tiers and rejected alternatives; the middleware, router and HTTP features specs; the middleware and routing guides, the middleware guide with its table of the tier each of Credo's middleware belongs to; `Mount`'s godoc, whose middleware scope names the routed tier; `HasRoute`'s, whose example fails closed; `ContractGuard`'s, which drops the safe no-op; and every document, godoc and example that names `GlobalMiddleware`. CHANGELOG Added for the tier, Changed for the rest. Migration rows: `app.GlobalMiddleware(m...)` becomes `app.PreRouting(m...)`; a middleware there that reads route meta moves to `app.Middleware`, while `CORS`, `Rewrite`, `Secure` and `RateLimit` stay. Release notes, first: a `ContractGuard` registered before routing answers 500 for every request; a mounted request carries its mount as its route, so `HasRoute` is true for it, App-level meta such as `MetaAccessLog` applies to it, and its access record names the mount's pattern.

## R15: live configuration sections; certificates rotate on change

**Change.**

```go
var Limits = config.Section[LimitsConfig]("limits")

app.Provide(Limits.Live) // decoded and validated when built, replaced whole by each reload that changes it

func NewOrderService(limits *config.Live[LimitsConfig]) *OrderService // the signature says the value is live

l := s.limits.Load() // once per operation: one atomic load, a value no reload changes
```

- **Static by default, live by declaration.** A section bound through `Decode` (R5) is a snapshot, and a change to it takes a restart. `Section[T].Live(src config.RawConfig) (*config.Live[T], error)` decodes and validates the section as `Decode` does and registers the handle with the configuration it read; each reload that changes a key under the section replaces the handle's value whole. No other binding changes at a reload, and no singleton is rebuilt (ADR-004).
- **`config.Live[T]`.** `Load() T` returns the current value with one atomic load, and a consumer calls it once per operation. `OnChange(fn func(ctx context.Context, prev, next T) error)` registers a callback for state derived from the section — a limiter, a compiled pattern, a `slog.LevelVar` — run after the new value is published. `config.Fixed(v)` returns a handle whose value is `v` and never changes, for a consumer's unit test.
- **All or nothing for validation, one generation for reads.** Every live section the reload changes is decoded and validated against the candidate before anything is published, and one failure aborts the reload with every old value current. The snapshot and the changed sections are then published as one generation: once a `Load` returns a reload's value for one section, every later `Load` of that configuration returns that reload's values or newer ones. Two `Load` calls can still straddle a reload, so values that must agree within one operation belong to one section.
- **The report names what was not applied.** A live section covers every key under it, since its whole value is replaced; every other key whose value differs from the one the start read, a key of a section bound through `Decode` included, is reported as needing a restart. A key whose file value changed while a later source, `.env` or the process environment, keeps it is reported with that source.
- **One nature per section.** A section is static or live within one configuration. Every read through its descriptor records the section's nature in the `*config.Config` it reads — `Decode`, `GetConfig` and `MustGetConfig` as static, `Live` as live — and the framework's read of `server` counts as static. A read of the other nature fails, naming the section and both reads: a constructor at its construction, the composition root at its call. A section nested in another, or one that contains it, counts as the same section, since the keys it reads are the other's. Read both ways, one section would run in two generations: the live handle would take a reload's value while the snapshot kept the old one, and the report would count the section's keys as applied. Keys that need a restart and keys a reload applies are therefore separate sections. A raw `Unmarshal` with a string key is outside the check, and the configuration guide says so.
- **The callbacks** run in registration order, for the sections the reload changed, with the reload's context, which the caller's deadline or the drain cancels; an error or a recovered panic is joined into the reload's result, the later callbacks still run, and nothing rolls back. No callback is skipped when the caller's deadline passes, since the next reload's diff would not show its change again. The drain waits for a reload in flight, its callbacks included, before the internal tier, as it does today.
- **What the type does not enforce** is documented with it: `Load` in each operation and derived state in `OnChange`, and a value's slices and maps read, never written, since every `Load` of one reload shares them.
- **The configuration holds its live sections.** `Config.Reload(ctx)` re-reads the sources, validates the changed live sections, publishes, runs the callbacks and returns what changed, the sections it replaced, the keys that need a restart and the keys a later source keeps; `App.Reload` keeps the trigger, the slot and the drain's step, logs that result and returns it (below). Over a configuration that cannot reload, `Section.Live` fails at construction and `App.Reload` returns an error. `config.Reloader`, `Stager`, `Staged` and `Config.Stage` leave the public API.
- **The triggers stay:** `App.Reload(ctx)`, SIGHUP under `Run` bounded by `WithReloadTimeout` or `server.reload_timeout`, and `WithoutReloadSignals`; `RunContext` and `ServeContext` stay signal-free, and configuration files are not watched.
- **`OnConfigChange`, `OnReload` and the framework's reload participants go.** Certificate rotation leaves the reload.
- **Certificate files rotate when they change.** With `WithTLSFiles` or `server.tls.*`, `GetCertificate` checks the two files at most once a second, on the handshake that finds the last check older than that, while concurrent handshakes serve the current pair without waiting: `os.Stat` on each file, compared with the last load by `os.SameFile`, modification time and size. A change loads the pair with `tls.LoadX509KeyPair` and swaps it atomically; a pair that fails to load keeps the old one and is logged once per change, so a half-written pair is retried when its other file changes. `os.Stat` follows symbolic links, so the link a Kubernetes Secret volume swaps on an update is a change, and no signal is needed. The paths are read at start, so a reload that changes `server.tls.*` reports a restart. `WithTLSConfig` stays the caller's, untouched.
- **`App.Reload` returns the reload's result**, the one `Config.Reload` returns, beside its error, and logs it as before, so an endpoint behind `ExecReload` or an orchestrator's hook answers the operator with what needs a restart. The keys that need a restart are computed against the snapshot the start read: those whose value differs from it and that no live section covers. A reload that changes nothing keeps reporting them, and one that reverts a key to its start value clears it, as PostgreSQL's `pg_settings.pending_restart` does. A reload that a live section's validation aborts returns a result that says nothing was applied and why, beside its error. No accessor reads that state between reloads, and a metric of it waits for the observability release.
- **A trigger under Kubernetes is the application's.** A ConfigMap or Secret volume file changes in place and no signal reaches the process, so a live section follows it only if something calls `App.Reload`. Credo provides no endpoint, whose authentication is the application's, and no watcher, which would apply a change at each kubelet's sync rather than when the operator decides, on every replica within that window and with no readiness gate. The deployment guide shows three triggers: a handler behind the application's authentication that calls `App.Reload` and returns its result; a job that calls that handler on each pod in turn; and a sidecar that sends SIGHUP when the volume changes, which `Run` maps to a reload and which needs no endpoint, at the cost of sharing the pod's process namespace (`shareProcessNamespace`), which the guide names.

**Tests.**

- A live handle returns the new value after a reload that changes its section and keeps its value after one that changes another; `Section.Live` fails as `Decode` does for a missing section, an invalid one and an empty key, and over `testutil`'s configuration or a custom `RawConfig` it fails naming the type.
- A reload that changes two live sections, one of them invalid, publishes neither and names the key; under concurrent loads, once a `Load` returns one section's new value, a `Load` of another section the reload changed returns its new value.
- `OnChange` runs once per reload that changes its section, after the publish, with the previous and the new value; an error and a panic are joined and the later callbacks run; a callback still runs, with the cancelled context, after the caller's deadline has passed; a drain that begins during a callback cancels its context and waits for it before the internal tier.
- A changed key outside every live section, a key of a `Decode`-bound section and a `server.tls.*` path included, is reported as needing a restart, and a live section's key is not; a file change under an environment override is reported with the variable.
- One section read through `Decode` and through `Live`, in either order, fails at the second read, naming the section and both reads; so do a static read of a section nested in a live one or containing one, and a live `server` section; two `Decode` reads of one section, and two `Live` reads, do not fail.
- `config.Fixed(v)` returns `v` and runs no callback; SIGHUP under `Run` reloads, and under `WithoutReloadSignals` it is logged at Info.
- `App.Reload` returns the result `Config.Reload` returns: after a reload that changed a static key, a reload that changes nothing reports the key again, and one that reverts it reports none; a reload that a live section's validation aborts returns a result that applied nothing, naming the section, with its error.
- A certificate pair rewritten on disk is served at the first handshake after the check interval; a pair whose key does not match its certificate keeps the old pair and logs once, and the fixed pair is picked up when its second file changes; a link swapped to a new directory is a change; concurrent handshakes run one check per interval.

**Documentation.** ADR-020 is rewritten around live sections, keeping its rejected alternatives; ADR-005 states that a section is a snapshot unless it is declared live; ADR-006 drops `OnReload`, and the lifecycle spec states the reload's steps with live sections; the config spec states live sections and the reload's result and drops staging; the root and `config` package docs follow. The configuration guide shows a static and a live section with the rule the type does not enforce, and that a section has one nature, a raw `Unmarshal` being outside that check; the worker guide's reloadable settings take a live section in place of the holder an `OnConfigChange` swaps; the getting-started, dependency-injection and middleware guides and README replace `OnConfigChange` and `OnReload`; the deployment guide keeps `ExecReload` and the admin endpoint, which returns the reload's result, shows a rollout for a structural change and the three Kubernetes triggers, and states the file check for certificates. `examples/saas` declares its log level a live section whose `OnChange` sets the `slog.LevelVar`, and `app` stays static, so a reload that changes `app.name` reports a restart. Migration rows: `app.OnConfigChange(key, fn)` becomes a live section, `app.Provide(section.Live)`, with the consumer calling `Load` where it read its holder and `fn` an `OnChange` when it derives state; an `OnReload` hook that refreshed derived state becomes its section's `OnChange`, and one that reopened a file installs its own SIGHUP handler; a custom `RawConfig` that implemented `Stager` or `Reloader` no longer reloads, so the configuration is loaded with `config.Load`; `cfg.Reload()` becomes `cfg.Reload(ctx)` and returns its result, and `app.Reload(ctx)` returns the same result beside its error; `Config.Stage` has no replacement. Release notes, first: certificate files rotate when they change on disk, without a signal, and a reload no longer moves the pair to new `server.tls.*` paths, which take a restart.
