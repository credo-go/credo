# ADR-020: Reload Signal, Partial Config Reload, and TLS Certificate Rotation

**Status:** Accepted **Date:** 2026-08-23 **Depends on:** ADR-005, ADR-006 **Related:** ADR-004, ADR-014, ADR-024 **Specification:** [Lifecycle spec](../specs/lifecycle.md#appreloadctx-contextcontext-configreloadresult-error), [Config spec](../specs/config.md#reload-and-its-result) **Guide:** [Configuration guide](../guides/configuration.md#reloading-configuration), [Deployment guide](../guides/deployment.md)

## Context

Credo applications run as long-lived services under systemd, container orchestrators, and process supervisors. All of these offer a "reload" verb (`systemctl reload`, `kill -HUP`) that operators expect to mean "pick up changed configuration and rotated certificates without dropping connections". A Go process that does not handle SIGHUP terminates on it, so a unit file with `ExecReload=kill -HUP $MAINPID` kills an unprepared service — the opposite of what the operator asked for.

Three constraints shape the design:

1. **ADR-005 makes config a startup snapshot.** `config.Load()` produces a `*config.Config`; each section is decoded once through its descriptor at the boundary and the typed value is injected through DI. A service that received `DBConfig` by value at construction cannot observe a later change to the underlying snapshot. A "reload everything" promise is structurally unfulfillable: server port, DI graph, middleware order and route tables are restart-only. A reload that silently applies some values and not others is worse than no reload at all.

2. **What a reload applies must be visible in the code and to the operator.** A value a consumer holds by copy cannot follow a reload, and a holder each consumer builds by hand lets it apply only the fields it chooses while its whole section counts as applied, so a key it ignores is neither applied nor reported. A constructor's signature should say whether the value it receives can change. A report of what needs a restart must hold until the restart, not only for the reload that made the change, and the caller of a reload — an admin endpoint, an orchestrator's hook — needs that report as a value to answer the operator with, not only as a log line.

3. **TLS is server config (ADR-006).** A key pair loaded once at startup keeps serving a stale certificate after on-disk rotation, and short-lived certificates (ACME, internal PKI with 24h–90d validity) rotate on disk while the process keeps running. Under Kubernetes a Secret update changes the files in place and sends the process no signal, so a rotation that waits for a reload keeps the renewed certificate unused. The owner of a `*tls.Config` (`WithTLSConfig`) can rotate through its own `GetCertificate`; a file-based source (`WithTLSFiles`, `server.tls.*`) needs the framework to do it.

## Decision

### A section is a snapshot unless it is declared live

A reload has one trigger, `app.Reload(ctx)` (SIGHUP under `Run`), and what it changes is declared per section:

```go
var Limits = config.Section[LimitsConfig]("limits")

app.Provide(Limits.Live) // decoded and validated when built, replaced whole by each reload that changes it

func NewOrderService(limits *config.Live[LimitsConfig]) *OrderService // the signature says the value is live

l := s.limits.Load() // once per operation: one atomic load, a value no reload changes
```

- **Static by default, live by declaration.** A section bound through its descriptor's `Decode` ([ADR-005](005-configuration-architecture.md#a-section-is-named-once-configsectiont)) is a snapshot, and a change to it takes a restart. `Section[T].Live(src config.RawConfig) (*config.Live[T], error)` decodes and validates the section as `Decode` does and registers the handle with the configuration it read; each reload that changes a key under the section replaces the handle's value whole. No other binding changes at a reload, and no singleton is rebuilt ([ADR-004](004-dependency-injection-and-infra.md)).
- **`config.Live[T]`.** `Load() T` returns the current value with one atomic load, and a consumer calls it once per operation. `OnChange(fn func(ctx context.Context, prev, next T) error)` registers a callback for state derived from the section — a limiter, a compiled pattern, a `slog.LevelVar` — run after the new value is published. `config.Fixed(v)` returns a handle whose value is `v` and never changes, for a consumer's unit test. What the type does not enforce is documented with it: `Load` in each operation, derived state in `OnChange`, and a value's slices and maps read, never written, since every `Load` of one reload shares them.
- **One nature per section.** A section is static or live within one configuration. Every read through its descriptor records the section's nature in the `*config.Config` it reads — `Decode`, `GetConfig` and `MustGetConfig` as static, `Live` as live — and the framework's read of `server` counts as static. A read of the other nature fails, naming the section and both reads: a constructor at its construction, the composition root at its call. A section nested in another, or one that contains it, counts as the same section, since the keys it reads are the other's. Read both ways, one section would run in two generations: the live handle would take a reload's value while the snapshot kept the old one, and the report would count the section's keys as applied. Keys that need a restart and keys a reload applies are therefore separate sections. A raw `Unmarshal` with a string key is outside the check.

Rejected: removing runtime reload, which would leave an application whose operational values — a log level, a rate limit, a timeout, a maintenance flag — must change without a restart to build the trigger, the staging, the validation and the drain's step itself, the toolkit answer the all-in-one framework exists to spare it, while ConfigMap and Secret volume files change in place under Kubernetes too; a per-section subscription that receives the decoded value, which keeps a callback that applies the fields it chooses while its whole section counts as covered, and the holder each subscriber builds; a hook, or a component capability, run at every reload, since derived state follows its section through `OnChange` and a refresh unrelated to configuration installs its own SIGHUP handler, which `signal.Notify` serves beside Credo's; every section live, which makes every read an atomic load and hides from the constructor which values can change; liveness per field, since the value a consumer holds is a copy and applying part of a section is the defect live sections remove; the live sections held by the App, with a staging interface kept for a custom configuration, which needs the configuration bound through a wrapper that `Resolve[RawConfig]` would return in place of the caller's value, for an extension only a test implements; and `Get` for the read, a name Credo gives lookups by key.

### SIGHUP triggers `Reload` — on Unix, under `Run()` only

`Run()` registers SIGHUP alongside SIGINT/SIGTERM. A SIGHUP calls `app.Reload` with a context bounded by `WithReloadTimeout` (default 30s; also settable through the `server.reload_timeout` config key, mirroring `server.shutdown_timeout`). Signal-triggered reloads run off the signal loop's goroutine, so the loop stays responsive: a SIGINT/SIGTERM that lands during a long reload starts the drain immediately and resets signal delivery at once (a second signal force-kills as usual), rather than waiting for the reload to return. At most one reload runs at a time; signals that arrive while one is in flight are coalesced into at most one follow-up reload. SIGHUP never terminates the process, and a failed reload never terminates the process either: a service that keeps running on its previous configuration is strictly better than one that dies because an operator fat-fingered a YAML file.

`RunContext` and `ServeContext` install no signal handler; their callers use `app.Reload(ctx)` directly (for example from an admin endpoint or an orchestrator hook). On Windows there is no SIGHUP; live sections and `app.Reload` work identically, only the signal path is absent.

**Opting out — `credo.WithoutReloadSignals()`**: disables the reload trigger under `Run` with subscribe-and-ignore semantics — SIGHUP is still captured, but the handler logs an Info line instead of calling `Reload`. Still-subscribed is deliberate and follows the rule that keeps the signal channel subscribed through the drain: under `Run`, SIGHUP must never fall through to its default action and terminate the process non-gracefully (a stray logrotate postrotate or a forgotten `ExecReload` would otherwise kill production). The three signal policies are each one API away: reload (`Run`, default), logged no-op (`Run` + `WithoutReloadSignals`), raw Unix disposition (`RunContext`/`ServeContext`). Rejected alternative: not installing the handler at all — "honest" default disposition, but it makes the middle policy unreachable and turns a stray HUP into an immediate, drain-less death; anyone who wants that semantics already has the signal-free entry points. Programmatic `app.Reload` is unaffected; signal policy is a code-level decision, so there is deliberately no `server.*` config key for it.

### `Reload` is running-only, serialized, and never partially visible

`app.Reload` succeeds only in the `running` state: before it there is nothing to reload, and a stopping App must not start new work against components that are being torn down. Concurrent calls are serialized by a capacity-one slot rather than a mutex, so waiting is context-aware: a queued caller gives up on its own context, or returns the not-running error without reloading when shutdown begins, and the drain can take the slot and keep it. A caller that waits performs its own full reload, which gives the one guarantee callers need: after `Reload` returns, the snapshot is at least as new as when it was called. The snapshot swap is atomic, so readers observe the old or the new snapshot, never a mix. States, errors and their signal-path treatment: [lifecycle spec](../specs/lifecycle.md#appreloadctx-contextcontext-configreloadresult-error).

### Reload and shutdown are coordinated; cancellation is cooperative

`OnChange` callbacks may be using internal components (re-opening a log sink, swapping a client), so a reload in flight when shutdown begins is coordinated with the drain in tiers ([ADR-006](006-application-lifecycle.md), [ADR-024](024-lifecycle-components.md)). Every callback receives the reload's context, which ends with either the caller's context or the App's session, and the drain cancels the session first, which tells the reload to stop. After the HTTP drain and the ingress tier, and before the internal tier, the drain waits for the in-flight reload, its callbacks included, and keeps the slot so no later reload can start. If the shutdown deadline expires first, the reload is logged and reported as still in flight (`credo: shutdown: reload still in flight`) and teardown proceeds, the same contract as an abandoned stop hook. Sequence: [lifecycle spec](../specs/lifecycle.md#shutdown-in-tiers).

Cancellation is cooperative: a Go callback cannot be forcibly stopped, so a callback that ignores its context can still overlap the internal tier's teardown, and the reported error is the framework's honest account of that. Rejected: making the reload wait a hard barrier that is never abandoned — a stuck callback would then hold the whole process open past the shutdown budget, which is worse for an operator than a logged overlap. Work with a genuine live-dependency requirement belongs to a component that depends on what it uses: its `Shutdown` stops admitting new reload work and waits for the in-flight callback, and it stops before its dependencies because the drain follows the dependency order — not the dependency's teardown, which would close the resource before the reload is even told to stop.

### All or nothing for validation, one generation for reads

Every live section the reload changes is decoded and validated against the candidate before anything is published, and one failure aborts the reload with every old value current. Typed decode thus doubles as the schema check that the untyped config store lacks, and a bad edit can never half-apply. The snapshot and the changed sections are then published as one generation: once a `Load` returns a reload's value for one section, every later `Load` of that configuration returns that reload's values or newer ones. Two `Load` calls can still straddle a reload, so values that must agree within one operation belong to one section.

The `OnChange` callbacks run in registration order, for the sections the reload changed, with the reload's context, which the caller's deadline or the drain cancels. An error or a recovered panic is joined into the error `Reload` returns beside its result, the later callbacks still run, and nothing rolls back: earlier callbacks may already have applied their values, and a half-rolled-back state is harder to reason about than a reported partial failure ([Rejected Alternatives](#rejected-alternatives)). No callback is skipped when the caller's deadline passes, since the next reload's diff would not show its change again. The drain waits for a reload in flight, its callbacks included, before the internal tier.

### The report names what was not applied

A live section covers every key under it, since its whole value is replaced; every other key whose value differs from the one the start read, a key of a section bound through `Decode` included, is reported as needing a restart. A key whose file value changed while a later source, `.env` or the process environment, keeps it is reported with that source. Key paths are reported, never values, since they may be secrets. This is the central promise of the design: an operator who changes `server.port` and reloads learns immediately that a restart is needed instead of discovering it at the next incident.

`Config.Reload(ctx)` and `App.Reload(ctx)` return the same `config.ReloadResult` beside their error: `Published`, whether anything was published; `Aborted`, why nothing was, naming the live section or the source that failed; `Changed`, the changed leaf keys; `Replaced`, the live sections whose value the reload replaced; `RestartRequired`, the keys that need a restart; and `Overridden`, a list of `config.OverriddenKey{Key, Source}`. Its JSON names are snake_case (`restart_required`), so an endpoint behind `ExecReload` or an orchestrator's hook answers the operator with it. `App.Reload` also logs it. The keys that need a restart are computed against the snapshot the start read: a reload that changes nothing keeps reporting them, and one that reverts a key to its start value clears it, as PostgreSQL's `pg_settings.pending_restart` does. No accessor reads that state between reloads, and a metric of it waits for the observability release.

### The configuration holds its live sections

`Config.Reload(ctx)` re-reads the sources, validates the changed live sections, publishes, runs the callbacks and returns its result. `App.Reload` keeps the trigger, the slot and the drain's step, logs that result and returns it. `RawConfig` stays a two-method interface ([ADR-005](005-configuration-architecture.md)): over a configuration that cannot reload — `testutil`'s, or a custom `RawConfig` — `Section.Live` fails at construction and `App.Reload` returns an error, each naming the configuration's type and `config.Load`. The triggers are `App.Reload(ctx)`, SIGHUP under `Run` bounded by `WithReloadTimeout` or `server.reload_timeout`, and `WithoutReloadSignals`; `RunContext` and `ServeContext` stay signal-free, and configuration files are not watched. Interfaces and semantics: [config spec](../specs/config.md#reload-and-its-result).

### Certificate files rotate when they change

With `WithTLSFiles` or `server.tls.*`, the key pair is served through a `GetCertificate` callback backed by an `atomic.Pointer[tls.Certificate]` (one atomic load per handshake), and preflight loads and validates the initial pair, so a missing or mismatched pair fails the start. `GetCertificate` checks the two files at most once a second, on the handshake that finds the last check older than that, while concurrent handshakes serve the current pair without waiting: `os.Stat` on each file, compared with the last load by `os.SameFile`, modification time and size. A change loads the pair with `tls.LoadX509KeyPair` and swaps it atomically; new handshakes see the new certificate and open connections are unaffected. A pair that fails to load keeps the old one and is logged at Error once per change, with both files and the error — the old pair still serves, but the change on disk did not take effect — so a half-written pair is retried when its other file changes. `os.Stat` follows symbolic links, so the link a Kubernetes Secret volume swaps on an update is a change, and no signal is needed. The paths are read at start, so a reload that changes `server.tls.*` reports a restart. `WithTLSConfig` stays the caller's, untouched: its owner rotates through its own `GetCertificate`. `WithHTTPRedirect` is unaffected (it serves plaintext).

Configuration files stay unwatched ([below](#rejected-alternatives)); certificate files are the exception, because a Secret update sends the process no signal, and the check at the handshake adds no dependency and no goroutine, a partial write fails to load and keeps the old pair, and `os.Stat` follows the link swap of a Secret volume.

### A trigger under Kubernetes is the application's

A ConfigMap or Secret volume file changes in place and no signal reaches the process, so a live section follows it only if something calls `App.Reload`. Credo provides no endpoint, whose authentication is the application's, and no watcher, which would apply a change at each kubelet's sync rather than when the operator decides, on every replica within that window and with no readiness gate. The [deployment guide](../guides/deployment.md) shows three triggers: a handler behind the application's authentication that calls `App.Reload` and returns its result; a job that calls that handler on each pod in turn; and a sidecar that sends SIGHUP when the volume changes, which `Run` maps to a reload and which needs no endpoint, at the cost of sharing the pod's process namespace (`shareProcessNamespace`).

### Observability

Reload is a lifecycle event, not a request: it writes framework records to the App logger — an Error for an aborted reload and for each failed callback, a Warn naming the keys that need a restart and one per key a later source keeps, and an Info summary per reload ([lifecycle spec](../specs/lifecycle.md#appreloadctx-contextcontext-configreloadresult-error)). A certificate rotation logs at Info and a failed one at Error. The observability release ([ADR-014](014-observability.md)) is to add a `credo_reload_total{result}` counter and a reload-duration histogram through the same `Infra` carrier; nothing in this decision depends on them.

## Rejected Alternatives

The rejections of the live-section design are in [its section](#a-section-is-a-snapshot-unless-it-is-declared-live).

- **Whole-config hot reload (mutate the snapshot in place).** Incompatible with ADR-005: typed structs already injected cannot see the change, so "reload" would apply an undefined subset. Declaring sections live makes the applied subset explicit and the unapplied remainder loud.
- **Restart-on-reload (re-exec with socket inheritance, à la nginx binary upgrade).** Correct in principle, but it is a deployment strategy, not a framework hook; containers and systemd already provide zero-downtime restarts. Out of scope.
- **Filesystem watching (fsnotify / polling) for configuration files.** Adds a dependency and a background goroutine, fires on partial writes, behaves differently on bind mounts and Kubernetes ConfigMap symlink swaps, and removes operator control over _when_ a change applies. Reload stays trigger-driven; an application that wants watching can call `app.Reload` from its own watcher. Certificate files are checked at the handshake instead ([above](#certificate-files-rotate-when-they-change)).
- **SIGUSR1/SIGUSR2 for reload.** SIGHUP is the convention every supervisor and operator already knows; USR signals stay free for application use.
- **Rollback of `OnChange` callbacks on partial failure.** Requires every callback to expose an inverse and still cannot undo side effects (re-opened files, already-served handshakes). Validate-before-publish prevents the common failure (bad input); the remaining failures are logged and returned.
- **Re-deriving `CREDO_ENV` on reload.** Changing environment swaps entire file sets and almost always implies restart-only sections; the environment name is fixed at first load and switching it is a restart.

## Consequences

- `systemctl reload` / `kill -HUP` is safe and useful for Credo services: SIGHUP never kills the process under `Run()`.
- ADR-005's "config is a startup snapshot" remains true for every section not declared live.
- The process environment is re-read, but a supervisor's `EnvironmentFile=` is applied only at process start, so env-sourced changes require a restart ([deployment guide](../guides/deployment.md#systemd)).
- `systemctl reload` cannot report reload failure (signal delivery is the only thing systemd observes). Teams that need synchronous failure expose `app.Reload` behind an authenticated admin endpoint that returns the reload's result and use `ExecReload=curl …` ([deployment guide](../guides/deployment.md#reload-without-a-signal)).
